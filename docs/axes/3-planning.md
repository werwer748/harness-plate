# 3축. 계획하기 — 계획 / 실행 / 검증을 함께 계획한다

> [HANDOFF.md](../../HANDOFF.md)에서 나눈 6축 문서다. 표시(기본값·결정·보류·남음)의 뜻과 기호(J, R, M1–M4)는 HANDOFF.md에 있다. 결정을 확정하거나 바꾸면 아래 표와 [결정 기록](../decisions.md)을 함께 고친다.

**다루는 질문**: 계획서에 "어떻게 할지"와 함께 "어떻게 실행하고, 어떻게 확인할지"가 들어가는가.

| | 레퍼런스와 내 자산 |
|---|---|
| 흐름 | **J**: `/harness` A–E 단계(탐색 → 논의 → step 설계 → 파일 생성 → 실행)<br>**R**: 0단계 점검(신규/확장/유지)과 1단계 제어 흐름 질문<br>**M**: plan mode를 매우 많이 쓴다(`~/.claude/plans/` 23개). `feature-cycle`은 범위를 확정한 뒤에 상태 파일을 만든다 |
| 단위 | **J**의 step 설계 원칙 6+1([부록 D](../references.md)) |
| 산출물 | **J**: `step.md`(읽을 파일/작업/AC/검증 절차/금지사항)<br>**M**: plan 파일(Context/진단/구현/검증) |

**결정과 처리**

| # | 결정 | 처리 |
|---|---|---|
| 1 | 계획 산출물 형식: plan 파일 하나 / `phases/step.md` 묶음 / 작업 크기에 따라 둘 다 | **기본값**: 작업 크기에 따른다. 작은 수정은 산출물이 없다. 보통 작업은 plan mode의 계획 하나다. 큰 기능은 스펙 하나를 쓴 뒤 새 세션에서 구현한다. `phases/step.md` 묶음은 무인 실행을 켤 때만 쓴다 |
| 2 | AC를 **하네스가 직접 실행하는 bash 블록**으로 강제할 것인가(M3 #10: zsh에서 glob이 먼저 풀리는 문제) | **기본값**: 성공 기준과 확인 방법은 항상 적되 형식은 강제하지 않는다(테스트, 실제 실행, 화면 확인). 무인 실행에서는 실행 가능한 검사가 필수이고 `bash -e`로 통일한다 |
| 3 | 사람이 승인하는 지점과, 계획 밖에서 내린 결정의 기록 방식(`DECISIONS.md`, `needs_human`) | **결정**: 상호작용 세션에는 규칙을 더하지 않는다. 최종 메시지가 바로 읽히고, 전역 `CLAUDE.md` 1번이 가정을 드러내라고 이미 요구한다. 결정이 묻히는 일이 반복되면 그때 추가한다. 무인 실행을 켤 때는 구조화 출력의 `decisions`·`needs_human`을 `DECISIONS.md`에 누적한다(M3 #5: 10 step 중 8개의 결정이 읽히지 않는 곳에 묻혔다). 사람 승인 지점은 plan mode 승인과 권한 확인을 그대로 쓴다 |
| 4 | 계획 단계에서 실행 모드(4축)와 검증 방식(5축)을 반드시 명시하게 할지 | **기본값**: 강제하지 않는다. 기본(메인 직접, 작업자 검증)에서 벗어날 때만 적는다 |
