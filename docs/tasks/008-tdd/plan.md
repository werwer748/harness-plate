# TDD와 엣지케이스 논의

## 요청
6단계: TDD와 엣지케이스 논의. 질문 라운드에서 정한 것: (1) TDD는 규칙+훅 둘 다. phase가 실패하는 테스트→구현→통과 순서로 하고 실패·통과 출력을 phase-N.md에 기록, 회고·검증이 확인. (2) plan이 매번 "엣지케이스를 논의할까요?"만 묻는다(후보를 먼저 추천하지 않음). 아니면 테스트는 수행 에이전트가 알아서 쓰고, 그렇다면 후보 선택지를 주거나 더할 케이스를 묻는다. 고른 것은 phase의 테스트 TODO, 뺀 것은 범위 밖. 따로 보강 스킬은 두지 않는다. (3) plan이 phase마다 "테스트 먼저" 여부를 적고 아니면 이유 한 줄. 리팩터링은 기존 테스트 전후 통과를 통과 조건으로. (4) 훅은 플러그인(plugins/plate/hooks/)에 담는 Claude Code 훅(PreToolUse Edit/Write). 테스트 먼저인 phase에서 이 작업의 테스트 변경 없이 구현 파일을 고치려 하면 막는다. setup 안 된 프로젝트와 테스트 없는 프로젝트에서는 아무것도 안 한다. (5) 남은 phase가 있는 작업이 없을 때 코드 편집은 훅이 막는다("계획부터"). (6) PRD 핵심 기능에 6~9단계 로드맵(6 TDD·엣지케이스, 7 자동 사이클, 8 푸시 전 평가, 9 정리·리팩터링 스킬, 그 뒤 1.0.0)을 적고, 범위 밖의 훅 줄과 목표의 "도구가 끊는 장치는 두지 않는다"를 바꾼다.

## 목표
테스트가 있는 프로젝트에서 테스트 먼저인 phase는 실패하는 테스트 → 구현 → 통과 순서로 수행되고 두 출력이 기록에 남는다. 플러그인의 Claude Code 훅이 그 순서와 "계획부터"를 지키고, 같은 이유로 세 번 막히면 멈춰 까닭과 해결책을 논의하게 한다. plan은 phase마다 테스트 먼저를 적고 엣지케이스를 논의할지 묻는다. 맥락 문서가 이를 반영하고 버전은 0.9.0이다.

## 범위 밖
- 검증 없는 종료를 막는 훅. v1.0 뒤에 한다
- Bash 명령(리다이렉트, `sed -i` 등)으로 고치는 편집. 훅은 파일 편집 도구의 호출만 본다
- 훅을 끄는 스위치(환경 변수, 프로젝트 파일)
- 엣지케이스를 따로 보강하는 스킬
- Codex·Grok Build의 훅
- 7~9단계(자동 사이클, 푸시 전 평가, 정리·리팩터링 스킬)와 커버리지·보안 기준

## 완료 조건
1. 훅이 아래 경우대로 한다. setup이 안 된 프로젝트에서는 통과시킨다. 코드 파일이 아닌 파일은 통과시킨다. 남은 phase가 없을 때 코드 파일은 막고 계획부터(`plate:plan`)라고 알린다. 테스트가 없는 프로젝트에서도 같다. 테스트가 있는 프로젝트에서 지금 phase가 테스트 먼저 "예"이고 커밋되지 않은 변경에 테스트 파일이 없으면, 테스트 파일이 아닌 코드 파일은 막고 실패하는 테스트부터라고 알린다. 커밋되지 않은 테스트 파일 변경이 있거나, 테스트 먼저가 "아니오"이거나 표시가 없거나, 테스트가 없는 프로젝트이거나, 고치는 파일이 테스트 파일이면 통과시킨다. 같은 phase의 계획이 바뀌지 않은 동안 같은 파일을 테스트 먼저 때문에 세 번째 막을 때는, 더 시도하지 말고 막힘으로 멈춰 까닭과 원하는 해결책을 기록에 적으라고 알린다.

## 결정
- PRD 목표·범위 밖과 ARCHITECTURE의 "훅은 두지 않는다"를 바꾼다. 이유: 규칙이 기본이고 Claude Code 훅이 TDD와 계획 없는 편집을 더 막는다.
- 훅은 Python 3 표준 라이브러리로 쓴다. 이유: JSON을 표준 라이브러리로 안전하게 읽고 unittest로 테스트하며 설치할 것이 없다.
- 같은 파일을 테스트 먼저 때문에 세 번 막으면 멈춰서 까닭과 해결책을 논의하고, 훅을 끄는 길은 두지 않는다. 이유: 왜 막히는지 설명하고, 이유를 찾았으면 그 해결책을 논의하면 된다. 테스트 먼저를 아예 끄는 것은 말이 안 된다.
- 세 번은 같은 phase의 계획(기록 절 위의 항목)이 바뀌지 않은 동안 센다. 이유: 논의로 계획을 고치면 다시 센다. (추천안으로 정함)
- 세 번을 세는 것은 테스트 먼저 때문에 막을 때뿐이다. 이유: 계획부터로 막는 까닭은 늘 분명하고, 잘못 막는 일은 테스트 먼저 판정에서 생긴다. (추천안으로 정함)
- 코드 파일은 `.md`가 아니고 `.worktrees/` 아래가 아닌 모든 파일이다. 계획 없는 편집 차단은 테스트가 없는 프로젝트에도 걸고, 테스트 먼저 검사만 테스트가 있는 프로젝트에 건다. 이유: PRD의 "예외 없이 모든 작업이 파이프라인을 거친다"에 맞다.
- 테스트 변경은 커밋되지 않은 변경에서 본다. 이유: phase 스킬은 phase가 끝날 때만 커밋하므로 그것이 지금 phase의 변경이고, phase마다 테스트부터 손대게 한다.
- 지금 phase는 지금 브랜치가 `task/NNN-slug`이면 그 작업의, 아니면 번호가 가장 작은 끝나지 않은 작업의 남은 첫 phase다. 이유: run이 작업을 고르는 규칙과 같다. (추천안으로 정함)
- 테스트 파일은 `tests/`, `test/`, `__tests__/` 아래이거나 이름이 `test_*`, `*_test.*`, `*.test.*`, `*.spec.*` 꼴인 파일이다. 테스트가 있는 프로젝트와 setup된 프로젝트는 plan 스킬의 낱말과 0번의 기준을 따른다. 이유: plan 스킬의 예를 여러 언어로 넓혔다. (추천안으로 정함)
- 테스트 먼저 표시가 없는 phase(표시가 생기기 전의 계획)는 테스트 먼저로 보지 않는다. 이유: 이미 세운 계획을 막지 않는다. (추천안으로 정함)
- 엣지케이스 물음은 테스트 먼저인 phase가 하나라도 있는 계획에서만 낸다. 이유: 고른 케이스는 테스트 TODO가 되므로, 테스트를 쓰지 않는 계획에는 물을 것이 없다. (추천안으로 정함)
- 훅은 파일 편집 도구의 호출만 본다. 이유: 명령의 글로는 어느 파일을 고치는지 믿을 만하게 가릴 수 없다. (추천안으로 정함)
- 훅의 테스트는 레포 최상위 `tests/`에 두고, 이 레포는 테스트가 있는 프로젝트가 된다. 이유: 버전 관리되고, 하네스 자신의 TDD 훅이 훅 코드에도 걸린다.
- 판정은 단위 테스트와 헤드리스 셋(tdd-plan, tdd-run, tdd-edit)으로 한다. 이유: 에이전트가 실제로 그렇게 도는지와 서브에이전트에서 훅이 도는지를 본다.
