# CI용 코드 평가와 판정 규칙

## 목표
review를 PR 모드로 부르면 tasks 머리 없이 PR에서 바뀐 코드를 평가해 평가서 파일과 등급 묶음을 낸다. 판정 스크립트는 그 등급 묶음으로 자동 머지, 머지 요청, 닫기 가운데 하나를 고른다. 명령 절에는 설치 줄이 생긴다.

## 범위 밖
- 워크플로 파일과 setup의 물음. `002-ci-workflow`에서 한다
- 평가서 댓글을 달고 PR을 머지하거나 닫는 일. 워크플로가 판정 스크립트의 답으로 한다
- 판정 스크립트에서 따로 다루는 것: 등급 묶음을 받지 못했을 때, 코드 변경이 없는 PR, 설치 명령의 실패

## 완료 조건
1. 명령 절의 정의가 설치, 빌드, 린트, 테스트 네 줄이 되고(없는 명령은 "없음"), plan이 명령 절을 챙길 때 설치 명령도 찾거나 묻는다. 설치 명령은 CI의 review만 돌리고 check, retro, tasks 끝의 review는 돌리지 않는다. 이 저장소의 명령 절에 `- 설치: 없음`이 있다.
   - 확인: `grep -n "설치" plugins/plate/skills/plan/SKILL.md plugins/plate/skills/check/SKILL.md plugins/plate/skills/retro/SKILL.md plugins/plate/skills/review/SKILL.md`가 네 파일 모두에서 명령 절 정의의 설치 줄을 낸다
   - 확인: `grep -c "^- 설치: 없음$" docs/ARCHITECTURE.md`가 `1`
   - 확인: `plugins/plate/skills/plan/SKILL.md`의 3번과 5번을 읽어 설치 명령도 찾거나 묻는다. check, retro, review의 명령을 돌리는 절을 읽어 tasks 끝까지는 설치 명령을 돌리지 않는다
2. review를 PR 모드로 부르면 tasks 머리 없이, 기준 브랜치에서 갈라진 곳부터 바뀐 코드 파일만 평가한다. 재기 전에 명령 절의 설치 명령을 돌리고, 명령 절, 커버리지, 네 범주(신뢰성, 보안, 유지보수성, 테스트 적절성), 게이트를 매기며, 기능 적합성은 매기지 않는다. 평가서를 파일로 쓰고, 판정 스크립트가 읽을 등급 묶음을 구조화 출력으로 돌려주며, 커밋하지 않고 묻지 않는다. tasks 끝의 코드 평가 절차는 바뀌지 않는다.
   - 확인: `plugins/plate/skills/review/SKILL.md`의 PR 모드 절을 읽어 위의 것과 등급 묶음의 꼴(키와 값)이 적혀 있다
   - 확인: `git diff "$(git log --format=%h -1 --grep='^001-ci-review: phase 1$')^" -- plugins/plate/skills/review/SKILL.md`를 읽어 tasks 끝 코드 평가의 절차(0~9번)가 명령 절 정의 말고는 바뀌지 않았다
3. 판정 스크립트가 등급 묶음을 받아 세 규칙대로 자동 머지, 머지 요청, 닫기 가운데 하나를 낸다. 커버리지가 "보지 않음"이면 다른 조건이 맞을 때 자동 머지를 막지 않는다. `docs/ARCHITECTURE.md`의 디렉터리 구조에 판정 스크립트와 그 테스트가 적혀 있다.
   - 확인: `python3 -m unittest discover -s tests`가 통과한다
   - 확인: 판정 스크립트의 테스트 파일을 읽어 규칙마다의 경계(커버리지 79%와 80%, 신뢰성·보안·유지보수성의 A와 B, 보안의 B와 C, 모름, 빌드·린트·테스트의 실패)와 커버리지 "보지 않음"의 경우를 본다
   - 확인: `docs/ARCHITECTURE.md`의 디렉터리 구조를 읽어 판정 스크립트와 그 테스트가 있다

## 결정
- CI의 판정은 셋이다. 자동 머지는 빌드·린트·테스트 통과, 새 줄 커버리지 80% 이상, 신뢰성·보안·유지보수성 A, 모름 없음이 모두 맞을 때다. 닫기는 빌드·린트·테스트 가운데 실패가 있거나 보안이 C 이하일 때다. 그 밖은 평가서로 머지를 요청한다. 이유: 말하지 않음.
- CI의 review는 코드만 본다. 기능 적합성은 매기지 않고, "모름"은 자동 머지 조건에 든 항목(빌드·린트·테스트, 커버리지, 신뢰성·보안·유지보수성)의 "측정 못함"이나 "판단 못함"이다. 명령 절에서 "없음"인 명령은 실패도 모름도 아니다. 이유: 세 규칙에 기능 적합성이 없고, 완료 조건은 tasks 끝의 review가 이미 봤다. "없음"은 review가 이미 실패가 아니라고 정해 두었다.
- review는 평가만 하고, 판정과 댓글, 머지, 닫기는 워크플로가 판정 스크립트로 한다. 이유: 세 규칙은 숫자와 등급만 보므로 스크립트가 늘 같은 답을 내고, PR 코드에 숨은 지시가 있어도 에이전트에게는 머지 권한이 없다.
- 판정 스크립트는 `plugins/plate/` 아래의 Python 3 표준 라이브러리 스크립트로 두고 `tests/`의 unittest로 시험한다. 이유: 규칙의 경계를 테스트로 볼 수 있고, 규칙을 고치면 플러그인 업데이트로 모든 프로젝트에 간다.
