- `001-ci-review` 문제: task 머리(`docs/tasks/001-ci-review/plan.md`)의 완료 조건 1의 확인은 review의 "명령을 돌리는 절"을 읽어 설치를 돌리지 않는지 보고, 완료 조건 2의 확인은 review의 0~9번이 "명령 절 정의 말고는" 바뀌지 않았는지 본다. 둘을 함께 맞추려고 phase 1이 review의 "설치를 돌리지 않는다"를 2번이 아닌 낱말의 명령 절 정의에 두어, 3번에 둔 check, retro와 적은 자리가 다르다(`done-phase-1.md`의 하네스에서 걸린 것)
- `001-ci-review` 문제: task 머리와 tasks 머리의 결정("review는 평가만 하고 판정과 머지는 워크플로가 판정 스크립트로 한다")은 "PR 코드에 숨은 지시가 있어도 에이전트에게는 머지 권한이 없다"를 이유로 들지만, 자동 머지를 정하는 것은 review의 PR 모드가 내는 등급 묶음이라 PR이 바꾼 코드나 `AGENTS.md`의 지시가 등급을 올리게 할 길이 남는다. review의 절대 규칙("프로젝트의 지침 파일의 규칙이 부딪히면 프로젝트의 규칙을 따른다")에 PR 모드의 예외가 없고, PR 모드 절(`plugins/plate/skills/review/SKILL.md`)에 이를 막는 글이 없다(`done-phase-2.md`의 하네스에서 걸린 것. 002나 tasks 끝에서 볼 거리)
- `001-ci-review` 문제: plate의 스킬 본문을 고치는 tasks에서 phase 1 뒤에 띄운 에이전트가 고치기 전의 본문을 받았다. phase 2와 phase 3의 확인 에이전트에 실린 check 본문과 이 회고 에이전트에 실린 retro 본문이 명령 절을 세 줄로 정의하고 3번에 "설치는 돌리지 않는다"가 없는 phase 1 전의 것이었고, 저장소의 `plugins/plate/skills/check/SKILL.md`와 `plugins/plate/skills/retro/SKILL.md`는 네 줄 정의다. 이 저장소의 설치가 "없음"이라 판정에는 걸리지 않았다(`done-phase-2.md`, `done-phase-3.md`의 확인 1의 하네스에서 걸린 것)
- `002-ci-workflow` 문제: setup 3번의 "CI 워크플로"(`plugins/plate/skills/setup/SKILL.md` 84줄)는 편집 훅을 피하려고 워크플로를 `AGENTS.md`보다 먼저 쓰게 하지만, 이미 셋업된 프로젝트에서 setup을 다시 불러 CI 에이전트를 승인하면 남은 phase가 없는 한 `plugins/plate/hooks/edit_guard.py`가 `.github/workflows/plate-review.yml`의 Write를 "계획부터 세운다"로 막는다(회고에서 훅에 그 입력을 넣어 종료 코드 2를 봤다). setup 본문에 막혔을 때의 길이 없다(`done-phase-1.md`의 하네스에서 걸린 것. 수행 에이전트는 회고에서 논의할 거리로 남겼다)
- `002-ci-workflow` 문제: task 머리(`docs/tasks/002-ci-workflow/plan.md`)의 완료 조건 1의 확인은 setup 본문의 글만 읽어서, 수행 기록이 하네스에서 걸린 것에 적은 훅과의 충돌을 보지 못한 채 phase가 통과했다. phase의 읽을 것에 `edit_guard.py`가 있었지만 완료 조건에 이미 셋업된 프로젝트에서 setup을 다시 부르는 경우가 없다
- `002-ci-workflow` 문제: 수행 에이전트가 ADR-021의 앞선 언급을 찾으려고 저장소 전체를 `grep`해 phase 스킬의 "다른 phase의 파일은 읽지 않는다"를 어겼다. 결과에 `005-publish-verify/phase-2.md`, `phase-3.md`, `001-ci-review/done-phase-2.md`의 줄이 섞였고 그 내용은 쓰지 않았다(`done-phase-1.md`의 하네스에서 걸린 것)
- `002-ci-workflow` 문제: 이 회고 에이전트에 실린 retro 본문이 `001-ci-review` 전의 것이었다. 명령 절을 빌드·린트·테스트 세 줄로 정의하고 3번에 "설치는 돌리지 않는다"가 없는데, 저장소의 `plugins/plate/skills/retro/SKILL.md`는 29줄에 네 줄 정의, 60줄에 "설치는 돌리지 않는다"가 있다. `001-ci-review`의 같은 문제가 다시 났고, 이 저장소의 설치가 "없음"이라 판정에는 걸리지 않았다
- `002-ci-workflow` 문제: `001-ci-review`가 "002나 tasks 끝에서 볼 거리"로 남긴 것(PR이 바꾼 코드나 `AGENTS.md`가 review의 등급 묶음을 올려 자동 머지를 이끌 길)을 002의 워크플로는 막지 않는다. setup 양식의 `review` 잡은 PR의 체크아웃에서 `--allowedTools "Bash,Read,Write,Glob,Grep"`로 돌고 그 구조화 출력이 그대로 판정 스크립트에 간다. ADR-021의 트레이드오프는 PR 코드가 Claude 토큰을 읽을 수 있는 것만 적고 이 길은 적지 않는다(`docs/ADR.md`)
- `002-ci-workflow` 문제: 고칠 phase(`docs/tasks/002-ci-workflow/done-phase-2.md`, 커밋 77deb39)의 통과 조건은 회고 1이 적은 곳을 다시 돌리고 완료 조건을 돌리는 것뿐이라, 고친 훅(`plugins/plate/hooks/edit_guard.py`)의 예외가 테스트 먼저의 막음까지 건너뛰는 것을 보지 못한 채 phase 2가 통과했다. 더한 테스트(`test_setup_writes_new_ci_workflow`)도 남은 phase가 없는 프로젝트만 본다. 회고 2가 훅에 입력을 넣어 찾았다
- `002-ci-workflow` 스킬 후보: setup 양식 절의 워크플로를 뽑아(`python3`, `awk`, `sed -n`) `ruby -ryaml`로 파싱하고, `claude_args`를 `shlex`로 나눠 `--json-schema`를 `verdict.py`에 대어 보고, `verdict` 잡의 run을 가짜 `gh`로 돌리는 묶음을 phase 1 수행·확인, 회고 1, phase 2 수행·확인, 회고 2가 저마다 새로 짰다(`done-phase-1.md`, `done-phase-2.md`의 한 일과 확인 1). 이 묶음을 스크립트나 테스트로 두면 task 머리 완료 조건 2의 확인이 명령 하나로 같게 돈다
