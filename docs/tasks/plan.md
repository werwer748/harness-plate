# 하네스 eval이 낸 plate 이슈 8개를 고친다

**이름**: eval-issues

## 요청
요청: 열린 GitHub 이슈 8개(#46, #47, #48, #49, #50, #51, #52, #53 — 지난 release-prep tasks의 하네스 eval이 낸 plate 자체 고칠 거리)를 모두 고친다. 그리고 이 tasks 끝의 코드 평가(review)의 다섯 범주와 하네스 eval의 여섯 기준이 모두 최소 B가 나와야 한다. 지난 tasks에서 B 아래였던 것: review 신뢰성 C(run description 1024자 초과), eval 효율 C(되풀이 몫 25.6%, 주로 헤드리스 장면 다시 돌리기), 사람 개입률 C(멈춤 3/30), 실패 양상 D(tasks 끝에서 잡힌 실패 1개, 같은 유형 FM-2.4 8번). eval 등급은 실행 이력으로 매기므로 계획이 되풀이·멈춤·회고나 tasks 끝에서 잡히는 실패가 나지 않게 짜여야 한다(예: 장면 차림과 기대를 미리 정확히, 시각 대신 해시 확인, description 길이 확인, 같은 유형 실패 두 번 이하).

## 목표
열린 이슈 8개(#46~#53)를 plan, run, phase, check, retro, review, eval 본문에서 고치고, 고친 규칙마다 글이 빠지면 실패하는 테스트를 `tests/test_skill_rules.py`에 더한다. 묻지 않는 retro, eval, phase의 고친 동작은 임시 복제본에서 헤드리스로 돌려 `docs/TOOLS.md`에 남긴다. 버전은 0.18.0이 되고, 맥락 문서와 README가 고친 동작에 맞춰진다.

## 결정
- 고친 동작은 규칙 글 테스트로 보고, 헤드리스 장면은 지난 기록 커밋으로 차릴 수 있고 묻지 않는 retro(#49), eval(#50), phase(#51 두 갈래)만 돌린다. plan과 run은 `돌리지 않음`으로 둔다. 이유: 지난 tasks의 실패, 멈춤, 되풀이 대부분이 장면 차림에서 났고, plan과 run은 사람에게 묻는 스킬이다
- 버전은 0.18.0이다. PR 전에 main이 먼저 0.18.0 이상이 되면 PR에서 다음 마이너로 맞춘다. 이유: 스킬 동작이 바뀌는 tasks마다 마이너를 올려 왔고, 1.0.0은 cleanup 뒤 별도 릴리스 tasks에서 낸다
- #49는 이슈의 해결책(`경계 밖`으로 적는다) 대신, eval 2번의 `남은 것:` 규칙과 같게 회고가 "문제"로 판정한 줄만 `FRICTION.md`의 `문제`로 모은다. 이유: eval의 셈과 글자 그대로 같아지고 `경계 밖`의 뜻이 섞이지 않는다
- #51은 phase, check, retro, review, eval 다섯 스킬과 run이 맡기는 글 다섯을 모두 고치고, 표지 줄은 `부른 쪽: plate:run`이다. 이유: 원인이 같은 글이 다섯 스킬에 있어 셋만 고치면 같은 결함이 남는다
- #47은 run 8번과 낱말 "작업 트리의 스킬 줄"의 명령 치환을 모두 두 단계로 적는다. 이유: 같은 원인으로 지난 장면 B·C·D의 run 메인이 낱말의 명령에서도 막혔다
- 장면은 `mktemp -d`의 복제본에서 `--permission-mode bypassPermissions`로 돌린다. 이유: 허용 목록 빠짐과 이은 Bash의 막힘이 지난 tasks의 FM-2.4 실패를 낳았고, 대상 셋은 푸시하지 않는 스킬이다
- 계획을 쓰기 전에 사용자가 `git switch main`과 `git merge --ff-only origin/main`으로 로컬 main을 origin의 것(`bf8ee2c`)에 맞춘다. run이 로컬 main을 origin의 것으로 되돌릴지 물으면 승인한다. 이유: 지금 브랜치 `tasks/release-prep`은 이미 머지됐고 로컬 main이 `509b234`라, 그대로 두면 코드 평가의 갈라진 곳이 release-prep 앞이 된다
- run을 시작하기 전에 사용자가 plan 모드를 끄고 bypassPermissions로 둔다. 이유: `AGENTS.md`의 작업 규칙(`plugins/plate/skills/` 편집이 auto mode에서 막힌다)
- 실행 방식은 tasks 일괄이다. 이유: 사용자가 "작업도 전부 일괄로 진행"이라고 했다
- 다섯 스킬은 `부른 쪽: plate:run` 줄과 작업 트리의 스킬 줄 가운데 하나라도 있으면 run이 띄운 것으로 본다. 이유: 일괄 실행에서는 run 세션이 띄울 때의 run 본문(표지 줄 없음)으로 맡기는데, run은 tasks가 바꾼 스킬에 작업 트리의 스킬 줄을 늘 붙인다(`docs/TOOLS.md`의 "세션 도중의 스킬 본문 고침")
- 같은 확인이나 회고가 세 번 실패해 멈추면, 해결책은 그 실패가 걸린 완료 조건(과 그 통과 조건)을 계획에서 빼고 실패의 글과 나온 task를 `docs/BACKLOG.md`에 남긴 뒤 잇는 것이다. 이유: 사용자가 "3번 실패시 backlog 남기고 넘어가"라고 했다
