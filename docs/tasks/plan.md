# 이슈 #80의 남은 부분을 고치고 1.0.0을 낸다

**이름**: repeat-names

## 요청
이슈 #80의 남은 부분을 고친다: plan의 초안 점검·조건 규칙과 retro 4번의 "지난 tasks의 같은 이름" 규칙을, 이름을 작업 트리나 지금 브랜치만 보고 고르거나 찾는 동작이면 같은 이름이 합쳐지지 않은 다른 브랜치(로컬과 origin)에 있는 경우도, 한 동작이 이름을 여럿 만들면 이름마다 확인으로 덮게 넓힌다(#80의 다시 나옴 댓글). 함께, retro의 "task의 커밋" 낱말(메시지가 task 이름으로 시작하는 커밋)이 지난 tasks에 남은 같은 이름의 커밋까지 잡는 꼴과, 결정이 정한 동작이 목표를 해쳐도 경계 밖으로만 적혀 회고 판정이 통과되는 꼴(cleanup-branch 003-fixes의 헤드리스 retro 시험에서 나옴)도 고친다. 문제가 없으면 이어서 버전을 1.0.0으로 올린다.

## 목표
plan과 retro가 이름이 남을 수 있는 모든 곳(지난 tasks, 합쳐지지 않은 다른 브랜치)과 한 동작이 만드는 이름마다를 확인하고 회고한다. retro는 이번 task의 커밋만 보고, 결정이 목표를 해치는 꼴을 문제로 판정해 run이 계획이 틀린 것으로 멈추게 한다. 그 뒤 plate를 1.0.0으로 낸다. 바뀐 동작은 맥락 문서와 맞춘다.

## 범위 밖
- BACKLOG의 하네스 고칠 거리(plan이 맥락 문서의 옛 글을 찾아 고칠 자리로 넣는 것)
- 이슈 #80을 닫는 것. PR을 머지한 뒤 사람이 닫는다
- git 태그나 GitHub 릴리스를 만드는 것
- Codex와 Grok Build에서 확인하는 것(v1.0 뒤, ADR-018)

## 완료 조건
1. 테스트 묶음이 모두 통과한다.
   - 확인: `python3 -m unittest discover -s tests` → 마지막 줄이 `OK`
2. plan의 초안 점검("6. 초안을 보여 주고 승인받는다")과 "적는 규칙"의 **조건**, retro의 "4. task의 변경을 점검한다"가 이름이나 번호로 고르거나 찾는 동작마다 세 경우를 확인 하나씩으로 덮게 한다: 지난 tasks의 같은 이름, 합쳐지지 않은 다른 브랜치(로컬과 origin)의 같은 이름, 한 동작이 만드는 이름마다. 테스트가 그 글을 지킨다.
   - 확인: `grep -n '합쳐지지 않은 다른 브랜치' plugins/plate/skills/plan/SKILL.md plugins/plate/skills/retro/SKILL.md` → plan의 6번과 **조건**, retro 4번에 저마다 한 줄 이상
   - 확인: 그 글을 지키는 `tests/test_skill_rules.py`의 시험이 있고, 그 줄을 지운 `cp -R` 사본에서 돌리면 그 시험이 실패한다
   - 돌리지 않음: plan은 초안마다 사용자에게 묻는 스킬이라 헤드리스로 끝까지 돌리지 않는다
3. retro의 "task의 커밋"이 그 task 머리 `plan.md`를 마지막으로 더한 커밋 뒤의 커밋만 센다. 그래서 지난 tasks에 남은 같은 task 이름의 커밋이 들지 않는다.
   - 확인: 헤드리스 시험(작업 트리의 `--plugin-dir`)에서 지난 tasks의 `001-x: phase 1` 커밋이 남은 시험 레포의 이번 task `001-x`에 retro를 돌린다. 기대: 회고 절이 지난 커밋이 바꾼 파일을 점검 대상으로 적지 않는다
4. retro는 결정이나 완료 조건이 정한 동작이 2의 세 경우에서 목표를 해치면 회고 절의 "문제"에 적고(기준: 계획, 고칠 쪽: 계획) 판정을 "문제 있음"으로 낸다. run 8번은 고칠 쪽이 계획인 문제를 계획이 틀린 것으로 보고 고칠 phase를 더하지 않고 멈춘다.
   - 확인: 헤드리스 시험에서 결정대로 지난 tasks의 같은 이름 커밋을 집는 꼴을 둔 시험 레포에 retro를 돌린다. 기대: `판정: 문제 있음`이 나오고 문제 줄에 `기준: 계획`이 있다
   - 확인: `grep -n '고칠 쪽' plugins/plate/skills/run/SKILL.md` → 8번 "고칠 phase를 더한다"와 "멈춘다"에 저마다 한 줄 이상. 그 글을 지키는 시험이 있다
   - 돌리지 않음: run은 에이전트를 띄우고 묻는 스킬이라 헤드리스로 끝까지 돌리지 않는다
5. 맥락 문서가 바뀐 동작과 맞다: PRD 핵심 기능 7(멈추는 자리), ARCHITECTURE의 run 문단, 데이터 흐름의 실행, 그 아래 멈춤 문단, 디렉터리 구조의 `test_skill_rules.py` 줄.
   - 확인: `grep -n '고칠 쪽' docs/PRD.md docs/ARCHITECTURE.md` → PRD 핵심 기능 7, ARCHITECTURE의 run 문단, 데이터 흐름의 실행, 멈춤 문단에 저마다 한 줄 이상
6. 두 매니페스트의 버전이 1.0.0이고, PRD의 1.0.0 줄이 낸 것으로 맞다.
   - 확인: `grep -n '"version"' plugins/plate/.claude-plugin/plugin.json plugins/plate/.codex-plugin/plugin.json` → 두 줄 모두 `"version": "1.0.0"`
   - 확인: `grep -n '1.0.0' docs/PRD.md` → 핵심 기능 아래의 줄이 1.0.0을 냈다고 적는다

## 결정
- retro의 "task의 커밋"은 그 task 머리 `plan.md`를 마지막으로 더한 커밋 뒤의 것만 센다. 이유: 편집 훅이 이미 같은 기준을 쓰고(ARCHITECTURE의 패턴과 규칙, 훅 문단), 브랜치나 원격이 없어도 돈다
- 결정이 정한 동작이 목표를 해치면 retro는 경계 밖이 아니라 문제로 판정한다(기준: 계획, 고칠 쪽: 계획). run은 그것을 계획이 틀린 것으로 보고 멈춘다. 이유: 목표를 해치는 결함이 회고 판정을 통과하지 않게 한다
- 1.0.0은 이 tasks의 마지막 task로 올린다. 앞 task의 회고가 통과해야 시작한다. 이유: tasks 끝의 코드 평가와 PR 하나에 함께 든다
- 스킬 본문을 고치는 tasks라, run을 시작하기 전에 plan 모드를 끄고 bypassPermissions로 바꾸거나 묻는 모드로 둔다. phase의 수행과 확인은 run이 넘긴 판의 본문을 따르고, 고친 retro의 동작은 헤드리스 시험으로 본다. 헤드리스 시험의 저장소 불변 확인은 `docs/tasks/RUNLOG.md`와 그 phase가 고치는 파일을 빼고 본다. 이유: AGENTS.md의 작업 규칙과 `docs/TOOLS.md`의 "플러그인 폴더의 편집과 권한 모드", "세션 도중의 스킬 본문 고침" (추천안으로 정함)
