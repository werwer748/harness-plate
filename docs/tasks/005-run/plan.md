# 레일 4단계: 실행 스킬 (run, phase, retro)

## 요청
4단계 진행하자

2026-10-13에 더한 요청: 확인해둔사실이나 포기한것 이런걸 기록하는 이유는 사실 그래서 이번 작업에서 구현하려고하는게 뭐지? 그걸 구현하려는 의도는 뭐야? 가 핵심인데 지금은 오히려 기록이 너무나 커져서 배보다 배꼽이 커진거같아. 마치 매 페이즈마다 프로젝트 하나 수준의 기록이 생기는 느낌이거든 관점을 아에 바꿔서 여기에 대한 논의가 길어지더라도 간소화에 초점을 맞춰보자. 다시 말하지만 중요한건 정확한 작업내용의 인식과 이 작업이 필요한 이유를 아는거야

## 목표
계획된 작업을 phase 하나씩 실행하는 스킬 셋(조율 `plate:run`, 수행 `plate:phase`, 점검 `plate:retro`)이 있고 실제 실행으로 판정을 통과한다. 계획은 머리(`plan.md`)와 phase마다의 파일(`phase-N.md`)로 쓰이고, 이 레포의 `docs/ADR.md`에는 프로젝트 수준의 결정만 남는다. 세 스킬의 본문과 plan 스킬의 네 곳 수정은 끝나 있고(커밋 `5b98a8c`), 남은 일은 계획을 파일로 떼는 것, 판정, 문서와 ADR의 정리다.

## 범위 밖
- 검증과 `verify.md`, 막는 장치(`AGENTS.md`의 규칙, 훅). 5단계에서 한다
- setup 스킬과 context 스킬을 고치는 것. context 스킬은 자기 적용(004의 실행)이 고치고, setup은 자기 적용에서 찾은 지도 문구의 예외 한 문장만 고친다
- plan의 코드 읽기와 context의 스캔을 에이전트에게 맡기는 것. 큰 저장소에서 써 보고 v1.0 뒤에 다시 본다
- 도구별 에이전트 정의 파일
- Codex와 Grok Build에서의 확인. v1.0 뒤에 한다
- `004-context-rules`의 검증. 5단계의 자기 적용이다
- `main` 병합. 끝에 따로 확인받는다
- phase마다의 기록(`phase-N.md`의 기록 다섯 절, 회고 절, 커밋 셋)을 줄이는 것
- 001, 002, 003의 단계 기록을 새 꼴로 옮기는 것. 끝난 단계이고 v1.0에서 지운다
- second brain 추천과 `docs/LESSONS.md`를 줄이는 일. 5단계 뒤의 추가 기능이다
- 실행으로 판정하지 않는 것: 확인은 통과하지만 계획과 다른 코드를 점검 에이전트가 찾아내는지, 고치기를 두 번 한 뒤에 멈추는 것, 합치다 충돌했을 때 되돌리는 것
- 5단계 라운드에서 묻는다: run의 끝에서 검증으로 이어갈지 묻는 물음
- 5단계 라운드에서 묻는다: 검증을 합치기 앞에 둘지. 지금은 검증하지 않은 작업이 원래 브랜치에 합쳐질 수 있다
- 5단계 라운드에서 묻는다: 검증이 프로젝트 전체 테스트를 돌릴지. 회고는 통과 조건의 확인만 돌린다
- 5단계 라운드에서 묻는다: 전체 지시로 실행한 작업은 코드 점검이 한 번도 없다. 검증이 그것을 맡을지
- 5단계 라운드에서 묻는다: phase가 하나뿐인 작업에서 회고와 검증의 겹치는 확인을 줄일지
- 5단계 라운드에서 묻는다: git 레포가 아닌 프로젝트의 작업 폴더에 남는 `done-phase-N.md`
- 5단계 라운드에서 묻는다: 프로젝트의 규칙으로 단계를 건너뛸 수 있는가
- 5단계 라운드에서 묻는다: 5단계의 계획을 어떤 꼴로 쓸지. 이 양식을 추천안으로 낸다

## 완료 조건
1. `run-small`(`plan-base`에 `.gitignore` 요청을 계획한 phase 하나짜리 작업, 회고를 승인): 커밋이 수행, 회고, 통과의 순서로 셋 생기고 어느 것에도 `plan.md`가 들지 않는다. 작업 폴더에 `plan.md`만 남고 `git status`가 비어 있다. 메인은 TODO를 직접 하지 않는다.
   - 확인: `runcheck.py run-small` → 모두 통과
2. `run-big`(세 명령 요청을 계획한 phase 둘 이상의 작업, 답을 미리 주지 않고 여러 턴): Phase 1의 수행 뒤에 회고할지 묻고 멈춘다. "회고한다" 뒤에 지우고 이을지 묻고 멈춘다. "잇지 않는다" 뒤에 보고로 끝난다. 새 세션에서 다시 부르면 남은 첫 phase부터 잇고 `phase-N.md`의 번호가 그대로다. phase마다 에이전트가 새로 뜬다.
   - 확인: `runcheck.py run-big` → 모두 통과
   - 확인: `logs/run-big-*.jsonl`에서 턴마다의 마지막 답글(물음 둘, 보고)을 읽는다
3. `run-all`(2번의 계획 직후, "모든 phase를 처리하라"를 붙여 부름): 회고할지도 이을지도 묻지 않고 끝까지 간다. 회고 절의 방식이 모두 "확인만"이고 모든 `phase-N.md`가 지워진다.

4. `run-skip`(1번의 계획 직후, 회고를 거절): 회고 절의 방식이 "확인만"이고 확인과 판정만 있다. 통과하고 지워진다.

## 결정
- 계획의 결정은 계획 안에만 둔다. ADR로 옮기지 않고 ADR 항목에 계획이나 작업 폴더를 적지 않는다. 이유(사용자의 말): "ADR은 프로젝트에서 중요도가 높은 결정들에 대한 기록인데 (…) plan상에서의 결정들은 어디까지나 해당 기능 구현을 위해 결정한 것들일 뿐이야"
- 계획하다가 정한 것이 context 스킬의 다섯 범주(언어와 런타임, 프레임워크, 저장소, 외부 서비스, 빌드와 배포)에 들 때만 초안에서 "ADR 후보"로 결정과 따로 보여 주고, 승인한 것만 ADR 항목을 더하는 TODO가 된다. 이유: ADR이 실제와 어긋나지 않게 하는 문은 남기되 기능 수준의 결정이 들어가지 않게 한다.
- 결정은 "정한 것. 이유: …" 한 줄로 적는다. 고르지 않은 안, 추천안이었는지, 질문 번호는 적지 않고, 완료 조건이나 TODO에 드러난 것은 다시 적지 않는다. 추천안과 다른 안을 고르면 그 자리에서 이유를 한 번 묻는다. 이유: 네 단계의 원장 218행 가운데 고르지 않은 안을 적은 행이 111, 이유를 적은 행이 11이었고, 빈 이유를 채우려고 44번 다시 물었다.
- 계획에 만들 것의 본문(절차, 양식, 규칙의 글)을 옮겨 적지 않는다. 만들 파일에 바로 쓰고 확인은 그 파일을 놓고 받는다. 이유: 같은 글이 설계 문서, 스킬 본문, "본문을 쓰면서 더한 것"으로 세 번 나왔다.
- 머리 다섯 절은 `plan.md`에 두고 phase의 계획은 `phase-N.md`로 뗀다. plan 스킬이 계획 네 항목을 쓰고, 수행 에이전트가 그 아래에 기록을, 점검 에이전트가 회고를 덧붙이며, 통과하면 그 파일 하나를 지운다. 이유: 한 파일이라서 걸린 것이 셋이었다. 코드 블록 안의 `## Phase` 줄 때문에 끝난 작업이 끝나지 않은 작업으로 잡혔고, run이 통과한 phase를 지우려고 `plan.md`에서 절을 잘라 냈고, 수행 에이전트가 체크박스 때문에 승인받은 `plan.md`를 고쳤다.
- 판정은 헤드리스 실행에 요청과 답 파일을 주어 돌린다. 기계로 볼 수 있는 것은 판정 도구(`~/plate-rail-test/bin/`의 `runcheck.py`, `plancheck.py`)로 보고, 사용자에게 보인 글은 요청·답 파일과 나란히 놓은 표로 사용자에게 보여 준다. 보여 준 뒤에 받아야 하는 승인은 같은 세션의 다음 턴으로 보낸다. 이유: 3단계와 같은 방식이다.
- 자기 적용은 사용자가 `claude --plugin-dir plugins/plate`로 연 새 세션에서 run을 직접 불러서 하고, 확인은 다른 세션이 그 세션의 기록과 커밋을 읽어서 한다. 이유: 기대값이 적힌 계획을 읽지 않은 세션이 돌려야 "스킬만 보고 그렇게 했다"가 근거가 된다.
- 이 작업의 phase는 세션이 `phase-N.md`를 읽고 직접 수행한다. `plate:run`으로 돌리지 않는다. 수행한 세션이 기록 다섯 절을 덧붙여 `005-run: phase N`으로 커밋하고, 통과 조건이 모두 통과하면 그 파일을 지워 `005-run: phase N 통과`로 커밋한다. 이유: 4단계는 run 자체를 만들고 판정하는 단계다. (추천안으로 정함)
- 커밋은 브랜치 `run`에 하고 phase가 통과할 때마다 `origin/run`으로 푸시한다. 이유: 3단계와 같은 방식이다.
- setup의 지도 문구에 "하네스의 스킬이 위치를 정해 둔 기록은 묻지 않는다"를 더한다. 이유: run은 `docs/LESSONS.md`를 본문에 박아 두어 위치를 묻는 것이 고를 것이 없는 물음인데, 같은 문구에서 자기 적용은 묻고 `run-lessons` 판정은 묻지 않았다.
