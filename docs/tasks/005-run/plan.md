# 레일 4단계 설계: 실행 스킬 (run, phase, retro)

> 진행 순서와 체크는 [TODO.md](TODO.md)에 있다. 이 파일은 TODO를 하다가 "무엇을, 왜, 어떤 규격으로"가 필요할 때 읽는다.

## 배경

3단계까지로 요청 하나가 `docs/tasks/NNN-slug/plan.md`로 계획된다(plan). 4단계의 결과물은 그 계획을 phase 하나씩 실행하는 스킬 셋이다.

| 스킬 | 역할 | 누가 따르는가 |
|---|---|---|
| `plate:run` | 조율: 묻기, 승인받기, 에이전트 띄우기, 지우기, 잇기 | 메인 세션 |
| `plate:phase` | 수행: phase 하나의 TODO를 끝내고 `phase-N.md`를 쓴다 | run이 띄운 새 에이전트 |
| `plate:retro` | 점검: 확인을 다시 돌리고 코드와 하네스를 본다 | run이 띄운 다른 새 에이전트 |

파이프라인의 모양은 3단계에서 정해 두었다(ADR-022): phase마다 수행하고 회고하고, 통과한 phase는 `plan.md`의 그 절과 `phase-N.md`를 지운다.

4단계의 질문 라운드는 2026-10-12에 열어 2026-10-13에 닫았다. 정한 것은 이 문서 끝의 결정 원장(157~218)에 있다. 218은 구현 중(A2)에 물어 정했다. 추천안과 다르게 정한 것은 아홉이다(원장 157, 159, 160, 161, 168, 170, 184, 186, 192).

## 실행의 흐름

```
/plate:run [작업] [모든 phase를 처리하라]

메인 (run)              수행 에이전트 (phase)        점검 에이전트 (retro)
──────────────────      ────────────────────────     ────────────────────────
대상 작업, 시작 조건
남은 첫 phase ────────▶ 머리와 그 절을 읽는다
                        TODO를 하나씩 끝내고 체크한다
                        통과 조건의 확인을 돌린다
                        phase-N.md를 쓴다
                        커밋 "NNN-slug: phase N"
          ◀── 다섯 줄 ──┘
회고할지 묻는다 ────────────────────────────────────▶ 확인을 다시 돌린다
(거절, 전체 지시: 확인만)                              (회고: 코드 점검, 하네스의 문제점)
                                                     phase-N.md에 회고 절을 적는다
                                                     커밋 "NNN-slug: phase N 회고"
          ◀───────────────────────────── 판정 ──────┘
문제 있음 → 묻지 않고 새 수행 에이전트에게 고치게 한다 → 새 점검 에이전트 (두 번까지)
통과     → docs/LESSONS.md로 옮기고, 그 절과 phase-N.md를 지운다
           커밋 "NNN-slug: phase N 통과"
다음 phase를 이을지 묻는다 (전체 지시: 묻지 않는다)
```

- 메인은 수행도 확인도 직접 하지 않는다. 메인의 컨텍스트에 들어오는 것은 `plan.md`, 수행 에이전트의 다섯 줄, 점검 에이전트의 세 줄, 옮길 줄뿐이다(원장 163, 167, 172).
- phase마다 수행 에이전트와 점검 에이전트를 새로 띄운다. 수행한 에이전트가 점검하지 않는다(원장 160, 167).
- 상태는 모두 파일에 있다(`plan.md`의 체크박스, `phase-N.md`, 회고 절, 커밋). 세션을 끊고 다시 불러도 파일만 보고 잇는다(원장 203).

## 만들고 고칠 파일

```
plugins/plate/skills/run/SKILL.md          # 새로 만든다
plugins/plate/skills/phase/SKILL.md        # 새로 만든다
plugins/plate/skills/retro/SKILL.md        # 새로 만든다
plugins/plate/skills/plan/SKILL.md         # 네 곳을 고친다 ("plan 스킬에서 고치는 곳")
plugins/plate/.claude-plugin/plugin.json   # version 0.7.0, 설명에 세 스킬
plugins/plate/.codex-plugin/plugin.json    # version 0.7.0, 설명에 세 스킬 (ADR-018: 함께 갱신)
README.md                                  # 스킬 표와 부르는 법
docs/PRD.md, docs/ARCHITECTURE.md, docs/ADR.md   # E 묶음에서 4단계 상태로 갱신
docs/TOOLS.md                              # 새로 확인한 도구 사실
docs/LESSONS.md, AGENTS.md                 # 자기 적용에서 옮길 것이 생기면 run이 만들고 지도에 행을 더한다
plugins/plate/skills/context/SKILL.md      # 자기 적용(004의 실행)이 고친다. 4단계의 구현은 건드리지 않는다
```

setup 스킬은 고치지 않는다. 그래서 1단계의 판정을 다시 돌리지 않는다. context 스킬은 자기 적용이 고치고, 그 판정은 004의 계획(Phase 2)이 한다.

## 낱말

세 스킬의 본문이 함께 쓰는 낱말이다. plan 스킬의 낱말(작업, 맥락 문서, 머리, phase)은 그대로 쓴다.

- **끝나지 않은 작업**: `plan.md`에 코드 블록 밖에서 `## Phase`로 시작하는 줄이 남아 있는 작업 폴더(원장 197). 3단계의 기준에 "코드 블록 밖에서"를 더한 것이다.
- **남은 첫 phase**: 대상 작업의 `plan.md`에서 코드 블록 밖의 첫 `## Phase N:` 절.
- **수행 에이전트**: run이 phase 하나의 수행을 맡기려고 새 컨텍스트로 띄운 에이전트. `plate:phase`를 불러 따른다.
- **점검 에이전트**: run이 phase 하나의 회고나 확인을 맡기려고 새 컨텍스트로 띄운 에이전트. `plate:retro`를 불러 따른다. 그 phase를 수행한 에이전트와 다른 에이전트다.
- **전체 지시**: run을 부른 요청에 든, 남은 phase를 모두 처리하라는 지시(원장 160).
- **확인만**: 회고 가운데 통과 조건의 확인만 다시 돌리는 방식. 코드 점검과 하네스의 문제점 보기를 건너뛴다(원장 159, 172).
- **원래 자리**: worktree가 아닌 주 작업 트리.
- **프로젝트의 지침 파일**: 저장소의 `AGENTS.md`와 그것을 불러오는 `CLAUDE.md`(원장 187).

## 네 스킬에 함께 넣는 문장 (원장 187, 188, 189, 215)

run, phase, retro, plan의 절대 규칙 절 첫머리에 넣는다. setup과 context에는 넣지 않는다.

> 프로젝트의 지침 파일(`AGENTS.md`, `CLAUDE.md`)에 적힌 규칙이 이 스킬의 규칙과 부딪히면 프로젝트의 규칙을 따른다. 아래의 절대 규칙도 그렇다. 따른 곳은 보고에 적는다. 단계를 건너뛰라는 규칙은 여기에 들지 않는다.

- 셋째 문장은 스킬마다 적는 곳만 다르다. run과 plan은 "보고에 적는다", phase는 "`phase-N.md`의 '하네스에서 걸린 것'에 적는다", retro는 "회고 절의 '하네스의 문제점'에 적는다". run이 그것을 보고에 옮긴다.
- 맥락 문서(PRD, ARCHITECTURE, ADR)와 저장소 밖의 지침(사용자 전역 설정)은 프로젝트의 규칙으로 보지 않는다. 맥락 문서와 어긋나는 것은 계획의 물음(ADR-028)과 회고의 코드 점검이 다룬다.
- 단계를 건너뛰는 것은 5단계 라운드에서 훅의 탈출구와 함께 정한다(ADR-033).

## 조율 스킬 `plate:run`의 규격

**쓰는 방식**: setup, context, plan과 같다. 한국어로 쓰고, 도구 이름 대신 동작으로 쓰고("새 컨텍스트의 에이전트를 띄운다"), 양식은 본문 안에 적는다(원장 201).

**설명(description)의 초안**: 계획된 작업을 phase 하나씩 실행한다. phase마다 새 컨텍스트의 에이전트에게 수행을 맡기고, 끝나면 회고할지 묻고, 통과한 phase는 `plan.md`의 그 절과 `phase-N.md`를 지운다. 계획을 쓴 뒤에, 또는 "실행해줘", "phase 진행하자", "작업 이어서 하자", "모든 phase 처리해줘"라고 할 때 쓴다. 계획이 없는 요청에는 쓰지 않는다.

**막는 실패**: 한 세션이 계획부터 끝까지 다 하면 컨텍스트가 불어나고, 수행한 쪽이 스스로 끝났다고 하면 확인되지 않은 결과가 다음 phase의 바탕이 된다.

### 절대 규칙

(첫머리에 "네 스킬에 함께 넣는 문장")

1. **수행도 확인도 직접 하지 않는다.** phase의 TODO를 하지 않고 통과 조건의 확인을 돌리지 않는다. 수행은 수행 에이전트에게, 확인과 점검은 점검 에이전트에게 맡긴다.
2. **phase마다 에이전트를 새로 띄운다.** 앞 phase를 수행한 에이전트를 이어 쓰지 않는다. 수행한 에이전트에게 점검을 맡기지 않는다.
3. **판정이 통과가 아닌 phase는 지우지 않는다.** 지우기 전에 `plan.md`의 그 절과 `phase-N.md`가 커밋돼 있어야 한다.
4. **`plan.md`의 머리와 통과 조건은 승인 없이 고치지 않는다.** 고칠 안을 답글로 보여 준 뒤에 받은 답만 승인이다.
5. **직접 고치는 파일은 `plan.md`, `docs/LESSONS.md`, `AGENTS.md`의 문서 지도, `.worktrees/.gitignore`뿐이다.** 커밋에는 자기가 고친 파일만 넣는다. 푸시하지 않는다.

### 절차

0. **대상 작업을 정한다.** (원장 202)
   - 번호나 이름을 받았으면 그 작업 폴더다.
   - 받지 않았고 지금 브랜치가 `task/NNN-slug`이면 그 작업이다.
   - 그 밖에는 끝나지 않은 작업을 찾는다. 하나면 그것이고, 여럿이면 폴더 이름을 보여 주고 묻는다. 하나도 없으면 실행할 계획이 없다고 알리고 계획부터 하라고 안내한 뒤 끝난다. 셋업이 안 된 프로젝트도 같다.
   - 요청에 남은 phase를 모두 처리하라는 뜻("모든 phase", "전부", "끝까지")이 있으면 전체 지시로 적어 둔다. 분명하지 않으면 전체 지시가 아니다.
   - 대상 작업의 worktree(`.worktrees/NNN-slug`)가 이미 있고 지금 자리가 원래 자리이면: 그 안의 `plan.md`에 phase가 남아 있지 않으면 "합친다"로 간다. 남아 있으면 그 폴더에서 세션을 열어 부르라고 안내하고 끝난다.
1. **시작 조건을 본다.**
   - git 레포가 아니면 커밋하지 않고 지우지 않는다고 알리고 2번으로 간다(원장 192, 214). 아래 셋은 건너뛴다.
   - 대상 작업의 `plan.md`가 커밋돼 있지 않으면 그 파일만 커밋한다(`plan: NNN-slug`).
   - worktree: 지금 브랜치가 `task/NNN-slug`(대상 작업의 것)이면 건너뛴다. 아니고, 대상 작업보다 번호가 작은 끝나지 않은 작업이 있으면 worktree를 만들고 끝난다(원장 180~183).
     - `.worktrees/.gitignore`가 없으면 `*` 한 줄로 만든다. worktree 폴더가 추적되지 않게 하는 것이다. `.git/info/exclude`와 프로젝트의 `.gitignore`는 고치지 않는다(원장 218).
     - `git worktree add .worktrees/NNN-slug -b task/NNN-slug`. 브랜치는 지금 커밋에서 가른다.
     - 만든 위치와 브랜치를 알리고, 그 폴더에서 세션을 열어 run을 다시 부르라고 안내한다. 이 세션에서는 실행하지 않는다.
   - 커밋하지 않은 변경이 있으면 파일 목록을 보여 주고 그대로 진행할지 묻는다. 진행하면 그 변경은 건드리지 않는다. 거절하면 아무것도 하지 않고 끝난다(원장 194).
2. **남은 첫 phase의 상태를 본다.** 파일만 보고 정한다(원장 203).

   | 상태 | 갈 곳 |
   |---|---|
   | `phase-N.md`가 없다 | 3번 |
   | 체크되지 않은 TODO가 있다 | 3번 (이어 한다) |
   | TODO가 모두 체크됐고 회고 절이 없다 | 4번 |
   | 마지막 회고 절의 판정이 "문제 있음"이다 | 5번 |
   | 마지막 회고 절의 판정이 "통과"다 | 6번 |

3. **수행을 맡긴다.** 새 컨텍스트의 에이전트를 띄워 아래 글을 그대로 넘긴다. 고칠 문제가 있을 때만 넷째 줄을 붙인다.

   ```
   plate의 phase 스킬(`plate:phase`)을 불러 그 절차를 따른다.
   작업 폴더: docs/tasks/NNN-slug
   phase: N
   고칠 문제: phase-N.md의 마지막 회고 절에 적힌 문제 목록
   ```

   돌아온 다섯 줄을 사용자에게 전한다.
   - 상태가 "끝남"이면 4번으로 간다.
   - "계획이 틀림"이면 "계획을 고친다"로 간다.
   - "막힘"이면 `phase-N.md`의 "남은 것"을 보여 주고 묻는다: 새 에이전트에게 다시 맡긴다 / 멈춘다. 전체 지시여도 묻는다(원장 204, 205).
4. **회고나 확인을 맡긴다.**
   - 전체 지시가 아니면 회고할지 묻는다(원장 158). 승인하면 방식은 "회고", 거절하면 "확인만"이다(원장 159). phase가 하나뿐인 작업도 같다(원장 178).
   - 전체 지시이면 묻지 않고 "확인만"이다(원장 161).
   - 고친 뒤에 다시 올 때는 묻지 않고 앞의 방식 그대로다.
   - 그 phase를 수행한 에이전트와 다른 새 에이전트를 띄워 아래 글을 그대로 넘긴다.

   ```
   plate의 retro 스킬(`plate:retro`)을 불러 그 절차를 따른다.
   작업 폴더: docs/tasks/NNN-slug
   phase: N
   방식: 회고
   ```

   돌아온 판정이 "통과"면 6번, "문제 있음"이면 5번으로 간다.
5. **문제가 나오면 고치게 한다.** 사용자에게 묻지 않고 3번으로 가서 문제 목록 전부를 새 수행 에이전트에게 고치게 한 뒤 4번으로 돌아온다(원장 170). 확인만의 실패도 같다(원장 205).
   - 회고 절이 셋이고(처음 한 번, 고친 뒤 두 번) 마지막 판정이 "문제 있음"이면 고치게 하지 않고 멈춘다. 남은 문제를 보여 주고 묻는다: 한 번 더 고치게 한다 / 남은 문제를 고치지 않기로 하고 지운다 / 멈춘다.
   - 둘째 선택지는 실패한 확인이 없을 때만 낸다. 고르면 `phase-N.md`의 마지막 회고 절 아래에 "사용자가 남은 문제를 고치지 않기로 했다"를 적고 그 파일만 커밋한 뒤 6번으로 간다.
6. **통과한 phase를 지운다.**
   - `phase-N.md`에 커밋되지 않은 변경이 있으면 그 파일만 먼저 커밋한다(`NNN-slug: phase N 회고`).
   - `docs/LESSONS.md`로 옮긴다("`docs/LESSONS.md`" 절). 회고 방식이면 마지막 회고 절의 "배운 것"과 "하네스의 문제점"을, 확인만 방식이면 `phase-N.md`의 "하네스에서 걸린 것"을 옮긴다(원장 173, 174, 200). "없음"이면 옮기지 않는다.
   - `plan.md`에서 그 phase 절을 지운다. `## Phase N:` 줄부터 다음 `## `로 시작하는 줄의 앞까지이고, 마지막 phase면 파일 끝까지다. 남은 phase의 번호는 다시 매기지 않는다. `phase-N.md`를 지운다.
   - 이 변경(`plan.md`, 지운 `phase-N.md`, 고쳤으면 `docs/LESSONS.md`와 `AGENTS.md`)만 한 커밋으로 넣는다(`NNN-slug: phase N 통과`).
   - git 레포가 아니면 지우지 않는다. 그 절의 제목을 `## (통과) Phase N: 이름`으로 바꾸고 `phase-N.md`는 남긴다(원장 192, 193). 그 줄은 `## Phase`로 시작하지 않으므로 끝나지 않은 작업의 기준이 그대로 통한다.
7. **잇는다.** (원장 160)
   - 남은 phase가 없으면 8번으로 간다.
   - 전체 지시이면 묻지 않고 2번으로 간다.
   - 아니면 지운 phase를 알리고 다음 phase(`Phase M: 이름`)를 이을지 묻는다. 승인하면 2번으로 가고, 거절하면 8번으로 간다.
8. **보고한다.** (원장 207)
   - 이번에 지운 phase와 남은 phase
   - 커밋. 커밋하지 않았으면 그 까닭
   - `docs/LESSONS.md`에 옮긴 줄
   - 프로젝트의 규칙을 따른 곳. 에이전트가 `phase-N.md`에 적은 것도 옮긴다(원장 189)
   - worktree에서 모든 phase가 지워졌으면: 원래 자리에서 run을 부르면 합칠지 묻는다고 적는다(원장 185)

   보고로 끝난다. 검증으로 이어갈지 묻는 물음은 5단계에서 더한다.

**계획을 고친다** (3번에서 상태가 "계획이 틀림"일 때. 원장 179, 212)
- `phase-N.md`의 "계획과 달라진 점"과 "남은 것"을 읽는다. 틀린 곳과 고칠 안(`plan.md`의 어느 글을 어떻게 바꾸는지)을 답글로 보여 주고 멈춘다. 설계의 선택이 새로 생긴 것이면 선택지와 추천안을 낸다.
- 승인받으면 `plan.md`를 고치고, 머리의 결정에 고친 것과 까닭을 한 줄 더한 뒤 그 파일만 커밋한다(`plan: NNN-slug 수정`). 3번으로 가서 새 에이전트에게 맡긴다. 새 에이전트는 체크되지 않은 TODO부터 잇는다.
- 승인받지 못하면 고치지 않고 8번으로 간다.
- 전체 지시여도 멈춰서 승인받는다(원장 205).

**합친다** (0번에서, 원래 자리이고 대상 작업의 worktree에 phase가 남아 있지 않을 때. 원장 184, 185, 213)
- 합칠 브랜치(`task/NNN-slug`)와 합칠 곳(원래 자리에 체크아웃된 브랜치)을 보여 주고 합칠지 묻는다. 거절하면 그대로 두고 8번으로 간다.
- 원래 자리에 커밋하지 않은 변경이 있으면 1번의 물음대로 먼저 묻는다.
- `git merge task/NNN-slug`로 합친다. squash하지 않는다. phase의 근거가 이력에 남아야 하기 때문이다.
- 충돌하면 풀지 않는다. `git merge --abort`로 되돌리고 충돌한 파일을 알린 뒤 8번으로 간다.
- 합쳐졌으면 `git worktree remove .worktrees/NNN-slug`와 `git branch -d task/NNN-slug`로 치운다. 치우지 못하면 까닭을 보고에 적는다.

## 수행 스킬 `plate:phase`의 규격

**설명(description)의 초안**: 계획의 phase 하나를 수행한다. `plan.md`의 머리와 그 phase 절만 읽고 TODO를 차례로 끝내며, 통과 조건의 확인을 돌리고, 한 일을 `phase-N.md`로 남기고 그 phase에서 바꾼 것만 커밋한다. 실행 스킬(`plate:run`)이 띄운 에이전트가 부른다. 사용자가 직접 부를 일은 드물다. 계획을 세우거나 회고하는 일에는 쓰지 않는다.

**막는 실패**: 수행하는 쪽이 계획에 없는 것까지 하면 결과가 승인한 계획과 달라지고, 기록 없이 끝내면 다음 컨텍스트가 무엇이 됐는지 알 수 없다.

### 절대 규칙

(첫머리에 "네 스킬에 함께 넣는 문장")

1. **자기 phase의 TODO만 한다.** 다른 phase의 일과 머리의 범위 밖에 든 일은 하지 않는다.
2. **사용자에게 묻지 않는다.** 정할 수 없는 것을 만나면 멈추고 보고한다.
3. **`plan.md`에서는 자기 phase의 체크박스만 고친다.** 머리, 통과 조건, 다른 phase 절은 고치지 않는다.
4. **확인을 돌리지 않고 통과로 적지 않는다.** 돌린 명령과 나온 결과를 적는다.
5. **이 phase에서 바꾼 파일만 커밋한다.** 푸시하지 않는다. 브랜치를 만들거나 바꾸지 않는다.

### 절차

1. **읽는다.** 넘겨받은 작업 폴더의 `plan.md`에서 머리와 넘겨받은 번호의 phase 절을 읽는다. 그 절의 "읽을 것"을 읽는다. 다른 phase 절은 따르지 않는다. `phase-N.md`가 이미 있으면 읽는다(이어 하는 경우다). 고칠 문제를 넘겨받았으면 `phase-N.md`의 마지막 회고 절의 문제 목록을 읽는다(원장 208).
2. **TODO를 차례로 끝낸다.** 체크되지 않은 항목부터 한다. 항목 하나를 끝낼 때마다 `plan.md`의 그 항목을 `- [x]`로 바꾼다(원장 165). 고칠 문제를 넘겨받았으면 TODO 대신 문제 목록을 차례로 고친다.
   - 계획이 실제와 다른 것을 만나면 둘로 가른다(원장 179).
     - 머리(목표, 범위 밖, 완료 조건, 결정)나 이 phase의 통과 조건을 바꿔야 한다, 또는 설계의 선택이 새로 생겼다: 더 하지 않고 4번으로 간다. 상태는 "계획이 틀림"이다.
     - 그 밖의 차이(TODO에 적힌 파일 경로가 다르다, 읽을 것의 위치가 바뀌었다): 진행하고 "계획과 달라진 점"에 적는다.
3. **통과 조건의 확인을 모두 돌린다.** 실패하면 고쳐서 다시 돌린다. 같은 확인이 세 번 실패하면 더 하지 않고 4번으로 간다. 상태는 "막힘"이다. 스스로 풀 수 없는 것(권한에 막힌 명령, 없는 도구)을 만났을 때도 "막힘"이다(원장 204).
4. **`phase-N.md`를 쓴다.** 양식은 아래에 있다. 이미 있으면 다섯 절을 지금 상태로 고쳐 쓰고 회고 절은 건드리지 않는다.
5. **커밋한다.** 상태가 "끝남"일 때만 한다. 이 phase에서 만들거나 고치거나 지운 파일과 `plan.md`, `phase-N.md`만 넣는다. 시작할 때 이미 커밋되지 않은 채 있던 다른 파일은 넣지 않는다. 메시지는 `NNN-slug: phase N`이고, 고칠 문제를 넘겨받았으면 `NNN-slug: phase N 고침`이다(원장 166, 206). "막힘"이나 "계획이 틀림"이면 커밋하지 않고 바꾼 것을 그대로 둔다. git 레포가 아니면 커밋하지 않는다.
6. **다섯 줄을 돌려준다.** 이 다섯 줄 말고는 돌려주지 않는다(원장 163).

   ```
   상태: 끝남 | 막힘 | 계획이 틀림
   기록: docs/tasks/NNN-slug/phase-N.md
   TODO: 끝낸 수/전체 수
   통과 조건: 통과한 수/전체 수
   계획과 달라진 점: 없음 | 있음
   ```

### `phase-N.md`의 양식 (원장 164)

`N`은 phase의 번호다. 절은 다섯이고 순서를 바꾸지 않는다. 적을 것이 없는 절은 "없음"으로 적는다.

````markdown
# Phase N: {plan.md의 그 phase 이름}

## 한 일
- {TODO 항목의 글}: {무엇이 어떻게 바뀌었는지} ({바꾼 파일의 경로})

## 확인 결과
- {통과 조건의 글}
  - {돌린 명령, 또는 본 곳} → {나온 결과}. {통과 | 실패}

## 계획과 달라진 점
- {계획에 적힌 것, 실제로 한 것, 그 까닭}

## 남은 것
- {끝내지 못한 TODO나 막힌 곳, 그 까닭}

## 하네스에서 걸린 것
- {계획의 어느 곳, 또는 어느 스킬의 어느 규칙 때문에 무엇이 걸렸는지}
````

- "하네스에서 걸린 것"은 수행한 쪽만 아는 것을 적는다: 계획의 읽을 것이 틀렸다, 확인 명령이 돌지 않았다, 스킬의 규칙이 프로젝트의 규칙에 밀렸다("프로젝트의 규칙을 따름: …"으로 적는다).
- 사용자가 `plate:phase`를 직접 부르면 그 세션이 같은 절차로 수행한다. 지우는 일은 run을 불러야 이어진다(원장 210).

## 점검 스킬 `plate:retro`의 규격

**설명(description)의 초안**: 수행이 끝난 phase 하나를 회고한다. 통과 조건의 확인을 다시 돌리고, 그 phase에서 바뀐 코드를 계획과 맥락 문서에 대어 점검하고, 하네스의 문제점을 찾아 `phase-N.md`의 회고 절에 적는다. 고치지는 않는다. 실행 스킬(`plate:run`)이 띄운 에이전트가 부르고, "회고하자", "phase 점검해줘"라고 할 때도 쓴다. 작업 전체를 완료 조건에 대어 보는 검증에는 쓰지 않는다.

**막는 실패**: 수행한 쪽이 스스로 통과를 선언하면 확인되지 않은 결과가 다음 phase의 바탕이 된다.

### 절대 규칙

(첫머리에 "네 스킬에 함께 넣는 문장")

1. **고치지 않는다.** 코드도 `plan.md`도 고치지 않는다. 쓰는 것은 `phase-N.md`의 회고 절뿐이다.
2. **확인을 직접 돌린다.** `phase-N.md`의 "확인 결과"를 옮겨 적지 않는다. 돌리지 않은 확인을 통과로 적지 않는다.
3. **적힌 기준에 대어 본다.** 취향에 드는 것(이름, 문체, 더 나은 구조)은 문제로 적지 않는다.
4. **사용자에게 묻지 않는다.** 판정과 기록까지만 한다.
5. **`phase-N.md` 하나만 커밋한다.** 푸시하지 않는다.

### 절차

0. **대상과 방식을 정한다.** 넘겨받은 작업 폴더와 phase 번호를 쓴다. 방식을 "확인만"으로 받았으면 3번과 4번을 건너뛴다. 사용자가 직접 불러서 받은 것이 없으면, 끝나지 않은 작업의 남은 첫 phase 가운데 `phase-N.md`가 있고 TODO가 모두 체크된 것이 대상이고 방식은 회고다. 그런 phase가 없으면 회고할 phase가 없다고 보고하고 끝난다(원장 210).
1. **읽는다.** `plan.md`의 머리와 그 phase 절, `phase-N.md`, 그 phase의 커밋(메시지가 `NNN-slug: phase N`으로 시작하는 것)이 바꾼 것. git 레포가 아니면 `phase-N.md`의 "한 일"에 적힌 파일을 읽는다. 회고 방식이면 문서 지도의 맥락 문서도 읽는다(원장 209).
2. **통과 조건의 확인을 모두 돌린다.** 그 phase의 통과 조건에 적힌 확인만 돌린다. 프로젝트 전체 테스트는 돌리지 않는다(원장 168).
3. **코드를 점검한다.** 넷을 본다(원장 169).
   - TODO와 머리의 결정대로 됐는가
   - 범위 밖과 다른 phase의 일을 건드리지 않았는가
   - 맥락 문서(ARCHITECTURE의 규칙, ADR의 결정, DESIGN)와 어긋나지 않는가
   - 동작이 틀리는 결함이 있는가
4. **하네스의 문제점과 배운 것을 찾는다.** `phase-N.md`의 "하네스에서 걸린 것"과 "계획과 달라진 점", 점검하며 본 것(통과 조건이 약했다, 읽을 것이 빠졌다)에서 하네스의 문제점을 모은다. 배운 것에는 맥락 문서에 없고 다음 작업이 알아야 할 것만 적는다(원장 211).
5. **회고 절을 적는다.** `phase-N.md`의 끝에 더한다. 이미 회고 절이 있으면 지우지 않고 그 아래에 다음 번호로 더한다(원장 171).
6. **커밋한다.** `phase-N.md` 하나만 넣는다. 메시지는 `NNN-slug: phase N 회고`다. git 레포가 아니면 커밋하지 않는다.
7. **세 줄을 돌려준다.**

   ```
   판정: 통과 | 문제 있음
   문제: N개
   기록: docs/tasks/NNN-slug/phase-N.md
   ```

   사용자가 직접 불렀으면 이 셋에 문제 목록을 더해 보여 주고, 지우거나 고치는 일은 run을 부르면 이어진다고 적는다. 지우지 않는다.

**판정**: 실패한 확인이 없고 문제 목록이 비어 있으면 "통과"다. 그 밖에는 "문제 있음"이다.

### 회고 절의 양식 (원장 171, 209)

````markdown
## 회고 {몇 번째}: {회고 | 확인만}

**확인**
- {통과 조건의 글}
  - {돌린 명령, 또는 본 곳} → {나온 결과}. {통과 | 실패}

**문제**
- {무엇이 어디서 어떻게 틀렸는지} ({파일의 경로}). 기준: {계획 | 범위 | 맥락 문서 | 결함 | 확인 실패}

**배운 것**
- {맥락 문서에 없고 다음 작업이 알아야 할 것}

**하네스의 문제점**
- {어느 스킬의 어느 규칙, 또는 계획의 어느 곳이 어떻게 걸렸는지}

**판정**: {통과 | 문제 있음}
````

- 없는 항목은 "없음"으로 적는다.
- 확인만 방식에서는 "확인", "문제"(실패한 확인만), "판정"만 적는다.
- 실패한 확인은 "문제"에도 적는다. 기준은 "확인 실패"다.

## `docs/LESSONS.md` (원장 173~177, 200, 211)

회고에서 배운 것과 하네스의 문제점을 모으는 경험 문서다(ADR-023). run이 6번에서 옮길 것이 처음 생겼을 때 만든다. setup은 이 문서를 만들지 않는다.

````markdown
# 회고에서 배운 것

## 프로젝트에서 배운 것
- ({작업 폴더의 이름}, phase {N}) {배운 것 한 줄}

## 하네스의 문제점
- ({작업 폴더의 이름}, phase {N}) {문제점 한 줄}
````

- 항목은 한 줄이다. 앞에 작업과 phase를 괄호로 적는다(예: `- (004-context-rules, phase 1) …`). 옮길 때 뜻을 바꾸지 않는다.
- 옮길 것이 없는 절은 제목만 둔다.
- 문서를 만들 때 `AGENTS.md`의 문서 지도 표에 행을 더한다. `docs/tasks/NNN-slug/` 행의 앞에 넣는다. setup은 다시 돌려도 사용자가 더한 행을 그대로 두므로 이 행도 남는다.

  ```
  | `docs/LESSONS.md` | 회고에서 배운 것과 하네스의 문제점 | 작업을 계획하거나 회고할 때 |
  ```

- 지도에 행이 있으므로 계획 스킬이 스킬을 고치지 않아도 이 문서를 읽는다(ADR-024).
- 하네스의 문제점 절의 항목은 사용자가 손으로 하네스 레포에 옮겨 계획의 요청 글로 쓴다. 스킬은 프로젝트 밖으로 아무것도 보내지 않는다(원장 177). 그래서 항목은 그대로 복사해 쓸 수 있게 어느 스킬의 어느 규칙인지를 적는다.

## plan 스킬에서 고치는 곳 (원장 186, 190, 197, 215)

넷이다. 그 밖의 글은 고치지 않는다.

1. **절대 규칙 절의 첫머리**에 "네 스킬에 함께 넣는 문장"을 넣는다.
2. **끝나지 않은 작업의 기준.** 낱말 절과 2번 절의 글을 "`plan.md`에 코드 블록 밖에서 `## Phase`로 시작하는 줄이 남아 있는 작업 폴더"로 고친다.
3. **완료 조건의 번호 목록.** 양식의 완료 조건을 아래 꼴로 바꾸고, 적는 규칙의 "조건"에 세 문장을 더한다: 완료 조건은 번호 목록으로 적는다. phase의 통과 조건이 머리의 조건을 가리킬 때는 "완료 조건 2"처럼 번호로 가리킨다. 통과 조건은 `- ` 항목으로 적는다.

   ```
   ## 완료 조건
   1. {작업 전체가 끝났을 때 참이어야 하는 것}
      - 확인: {돌릴 명령과 기대 결과, 또는 무엇을 어디서 보는지}
   ```

4. **끝 물음.** 8번 보고 뒤에 실행으로 이어갈지 묻는다. 승인하면 새 세션에서 부를 것(plate의 run 스킬 `plate:run`과 작업의 번호)을 안내하고 끝난다. 끝나지 않은 다른 작업이 있으면 실행이 worktree에서 이루어지고 run이 그것을 만든다는 것도 함께 알린다. 거절하면 그대로 끝난다. 어느 답이든 이 세션에서 실행을 시작하지 않는다. "보고로 끝난다. 계획한 일을 이어서 실행하지 않는다"는 문장은 이 물음에 맞게 고친다.

8번 보고의 "이 작업의 실행은 worktree에서 한다"는 그대로 둔다. 새 계획의 번호가 항상 가장 크므로 run의 기준(원장 180)과 같다.

**기계로 보는 것** (`bin/runcheck.py`를 새로 만든다)
- 커밋의 순서와 메시지: phase마다 `NNN-slug: phase N` → `… 회고` → (`… 고침` → `… 회고`)가 0번 이상 → `… 통과`
- 수행 커밋에 다른 phase의 `phase-M.md`가 없다. 회고 커밋에 든 파일이 `phase-N.md` 하나다. 통과 커밋에 든 파일이 `plan.md`, 지운 `phase-N.md`, 있으면 `docs/LESSONS.md`와 `AGENTS.md`뿐이다
- 통과 커밋 뒤의 `plan.md`에 `## Phase N:`이 없고 남은 phase의 번호가 그대로다. 모든 phase가 지워진 `plan.md`는 머리의 다섯 절만 있다
- 통과 커밋 직전의 `phase-N.md`(`git show`로 꺼낸다): 제목, 다섯 절의 순서, 회고 절의 항목과 판정 줄
- 끝난 뒤 `git status`가 비어 있다(11번은 손댄 파일 하나만 남는다)
- `docs/LESSONS.md`: 제목, 절 둘, 항목의 꼴. `AGENTS.md`의 지도에 행이 있다
- 실행 기록(jsonl): 에이전트를 띄운 횟수와 넘긴 글. 메인이 직접 고친 파일이 `plan.md`, `docs/LESSONS.md`, `AGENTS.md`, `.worktrees/.gitignore`뿐이다
- worktree: 폴더, 브랜치, `.worktrees/.gitignore`. 합친 뒤에는 폴더와 브랜치가 없고 원래 브랜치에 phase의 커밋이 있다
- git 레포가 아닌 폴더: `.git`이 없고 `## (통과) Phase` 줄이 있다

**읽어서 보는 것**: `phase-N.md`의 "한 일"이 실제 변경과 맞는지, 회고의 문제가 기준 넷에 드는지, 계획에 없는 것을 했는지, 사용자에게 보인 글(다섯 줄, 물음, 보고)을 표로 적어 사용자에게 보여 준다.

**이 판정이 보지 못하는 것**: 점검 에이전트가 결함을 실제로 찾아내는지는 5번의 한 경우(확인이 실패하는 결함)로만 본다. 확인은 통과하지만 계획과 다른 코드를 찾아내는지는 보지 않는다. 고치기를 두 번 한 뒤에 멈추는 것과 합치다 충돌했을 때 되돌리는 것도 실행으로 보지 않는다.
