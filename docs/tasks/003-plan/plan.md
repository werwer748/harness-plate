# 레일 3단계 설계: 계획 스킬

> 진행 순서와 체크는 [TODO.md](TODO.md)에 있다. 이 파일은 TODO를 하다가 "무엇을, 왜, 어떤 규격으로"가 필요할 때 읽는다.

## 배경

2단계까지로 프로젝트에 문서의 위치 기준이 서고(setup) 맥락 문서가 채워진다(context). 3단계의 결과물은 요청 하나를 작업으로 계획하는 스킬 `plate:plan`이다. 계획은 `docs/tasks/NNN-slug/plan.md`로 남는다(ADR-006).

3단계의 질문 라운드는 2026-10-08에 열었다. 정한 것은 이 문서 끝의 결정 원장(101~147)에 있다.

라운드에서 사용자가 아이디어 셋을 더했다. 3단계의 범위를 넘는 것이라 파이프라인의 모양까지만 정하고 절차는 뒤 단계로 넘겼다(원장 104, 108, 129).

- phase마다 회고하고, 통과한 phase는 지운다(원장 102, 103, 105)
- 끝난 작업이 쌓이면 second brain 설계를 추천한다(원장 107)
- 끝나지 않은 작업이 있을 때 새 작업은 worktree에서 진행한다(원장 128)

## 파이프라인의 모양 (3단계 라운드에서 정한 것)

```
계획 → 실행 → 검증

계획:  plan.md를 쓰고 그 파일만 커밋한다                        (3단계)
실행:  Phase 1 → 회고 → 통과하면 그 phase를 지운다              (4단계)
       Phase 2 → 회고 → 통과하면 그 phase를 지운다
       …
검증:  작업 전체를 plan.md의 완료 조건에 대어 본다 → verify.md   (5단계)
```

- 바깥 단계는 ADR-003 그대로다. 실행 안쪽에 phase마다 회고가 들어간다(원장 105).
- 회고는 그 phase에서 쓴 코드와 테스트, 하네스의 문제점을 본다. 통과하면 그 phase를 지운다(원장 102).
- 지우는 것은 둘이다: `plan.md`의 그 phase 절, 그 phase의 `phase-N.md`(원장 103). 지난 phase의 근거는 git 이력에만 남는다. 그래서 지우기 전에 한 번은 커밋돼 있어야 한다.
- "phase 절이 남아 있으면 실행이 끝나지 않은 것"이다. 2단계의 "`{…}` 안내 글이 남아 있으면 끝나지 않은 것"(원장 44)과 같은 꼴이고 기계로 볼 수 있다.
- 검증까지 통과한 작업의 폴더에는 `plan.md`(머리만 남은 것)와 `verify.md`가 남는다(원장 106).

```
docs/tasks/
├── 007-login/       끝난 작업
│   ├── plan.md      요청, 목표, 범위 밖, 완료 조건, 결정 (phase 없음)
│   └── verify.md    완료 조건마다의 증거
└── 008-export/      진행 중
    ├── plan.md      머리, Phase 2, Phase 3
    └── phase-2.md
```

이 모양은 ADR-003과 ADR-006을 바꾼다. E 묶음에서 새 ADR 항목으로 적는다(원장 146).

## 만들고 고칠 파일

```
plugins/plate/skills/plan/SKILL.md         # 새로 만든다. 본문 하나
plugins/plate/.claude-plugin/plugin.json   # version 0.6.0, 설명에 plan 스킬
plugins/plate/.codex-plugin/plugin.json    # version 0.6.0, 설명에 plan 스킬 (ADR-018: 함께 갱신)
README.md                                  # 스킬 표와 부르는 법
docs/PRD.md, docs/ARCHITECTURE.md, docs/ADR.md   # E 묶음에서 3단계 상태로 갱신
docs/TOOLS.md                              # 새로 확인한 도구 사실이 있으면 더한다
docs/tasks/004-<이름>/plan.md              # E 묶음의 자기 적용에서 스킬이 만든다
```

setup 스킬과 context 스킬은 고치지 않는다. 그래서 1, 2단계의 판정을 다시 돌리지 않는다.

## 계획 스킬 규격

**쓰는 방식**: setup, context와 같다. 한국어로 쓰고, 도구 이름 대신 동작으로 쓰고, 양식과 판정 기준은 본문 안에 적는다(원장 135).

**설명(description)의 초안**: 요청 하나를 작업으로 계획한다. 문서 지도의 맥락 문서와 요청에 걸리는 코드를 읽고, 추측으로 정할 수 없는 것은 하나씩 물어서, phase로 나눈 계획을 `docs/tasks/NNN-slug/plan.md`로 쓴다. 초안을 승인받은 뒤에 쓰고 그 파일만 커밋한다. 기능을 만들거나 코드를 고치는 요청을 받았을 때 코드를 고치기 전에, 또는 "계획 세워줘", "plan 짜줘", "작업 계획하자"라고 할 때 쓴다. 코드를 고치는 일에는 쓰지 않는다.

**막는 실패**: 계획 없이 시작하면 결과물이 의도와 달라지고, 한 세션에서 끝까지 가면 컨텍스트가 불어난다. 계획이 추측으로 채워지면 틀린 계획이 실행의 근거가 된다.

### 낱말

- **작업**: 요청 하나를 계획, 실행, 검증으로 끝내는 단위. 기록은 `docs/tasks/NNN-slug/`에 둔다.
- **맥락 문서**: 문서 지도에 적힌 문서 가운데 `docs/tasks/` 행을 뺀 것.
- **안내 글**: 양식의 `{…}` 글. `{확인 필요}`와 `docs/DESIGN.md`의 토큰 참조는 안내 글이 아니다.
- **머리**: `plan.md`에서 phase 절 위의 부분. 제목과 다섯 절(요청, 목표, 범위 밖, 완료 조건, 결정)이다.
- **phase**: 실행의 한 구간. 새 컨텍스트의 에이전트 하나가 머리와 그 절만 읽고 수행한다.
- **끝나지 않은 작업**: `plan.md`에 `## Phase`로 시작하는 절이 남아 있는 작업 폴더(원장 144).

### 절대 규칙

1. 승인받지 않은 초안을 파일에 쓰지 않는다.
2. 설계의 선택이 둘 이상인데 요청이 고르지 않은 곳은 스스로 고르지 않고 묻는다. 요청, 맥락 문서, 코드, 사용자의 답 어디에도 없는 것을 계획에 적지 않는다.
3. `plan.md` 말고는 만들지도 고치지도 않는다. 코드를 고치지 않는다. 다른 스킬을 불러서 그 스킬이 하는 일은 그 스킬의 규칙을 따른다.
4. `plan.md` 하나만 커밋한다. 다른 파일은 스테이징하지 않는다. 브랜치를 만들거나 바꾸지 않는다.

### 절차

0. **셋업이 됐는지 본다.** `AGENTS.md`에 문서 지도 구간(`<!-- plate:docs-map:start -->`)이 있으면 1번으로 간다. 없으면 셋업을 먼저 할지 묻는다(원장 111).
   - 승인하면 plate의 setup 스킬(`plate:setup`)을 불러 그 절차를 끝까지 따른다. setup의 끝 물음(이어서 채울지)도 그대로 따른다. 돌아와서 1번의 "채울지 묻는다"는 건너뛴다. setup이 이미 물었기 때문이다(원장 143).
   - 거절하면 아무것도 쓰지 않고 끝난다.
1. **맥락 문서를 읽는다.** 문서 지도에 적힌 위치의 맥락 문서를 모두 읽는다(원장 113). 읽을 문서를 본문에 고정하지 않는다. 지도에 행이 더해지면 그 문서도 읽는다.
   - 표준 네 문서(`docs/PRD.md`, `docs/ARCHITECTURE.md`, `docs/ADR.md`, `docs/DESIGN.md`) 가운데 안내 글이 남은 문서가 있으면 먼저 채울지 묻는다(원장 112). 승인하면 plate의 context 스킬(`plate:context`)을 불러 그 절차를 따르고, 돌아와서 그 문서를 다시 읽는다. 거절하면 적혀 있는 내용만 근거로 삼는다.
   - `{확인 필요}`만 남은 문서는 묻지 않는다.
2. **작업 폴더를 정한다.** (원장 115)
   - 번호는 `docs/tasks/` 바로 아래 폴더 이름의 앞 세 자리 숫자 가운데 가장 큰 것의 다음이다. 폴더가 없으면 `001`이다.
   - 이름은 요청에서 영어 소문자 낱말 1~3개를 골라 하이픈으로 잇는다.
   - 끝나지 않은 작업을 찾아 적어 둔다. 지난 작업의 내용은 읽지 않는다. `## Phase` 줄이 있는지만 본다.
3. **요청에 걸리는 코드를 읽는다.** 직접 읽는다(원장 114). 요청에 걸리는 것만 읽는다.
4. **요청이 맥락 문서와 어긋나는지 본다.** 어긋나면(PRD의 범위 밖에 든다, ADR의 결정과 다르다, ARCHITECTURE의 규칙과 다르다) 어긋난 문서의 위치와 문장을 보여 주고 셋 중에 고르게 한다(원장 125).
   - 요청을 문서에 맞게 고친다
   - 문서를 바꾸기로 하고 진행한다
   - 그만둔다. 이때는 아무것도 쓰지 않고 끝난다.
5. **질문한다.** 머리의 다섯 절과 phase 분해를 요청, 맥락 문서, 코드만으로 적을 수 없는 곳만 묻는다(원장 124).
   - 한 번에 질문 하나만 내고, 답을 받은 뒤에 다음 질문을 낸다. 고를 수 있는 답은 선택지로 낸다.
   - 질문마다 추천안과 이유를 붙인다. 근거가 저장소나 맥락 문서에 있으면 경로를 적고, 없으면 이유를 글로 적는다(원장 123).
   - 요청이나 문서에 답이 있으면 묻지 않는다. 물을 것이 없으면 이 단계를 건너뛴다.
6. **초안을 보여 주고 승인받는다.** 초안 전체를 한 번에 보여 준다(원장 141).
   - 첫머리에 쓸 위치를 적는다(`쓸 위치: docs/tasks/008-csv-export/plan.md`). 번호와 이름은 여기서 함께 승인받는다.
   - 끝나지 않은 작업이 있으면 그 폴더 이름을 첫머리에 한 줄로 알린다(원장 128).
   - 고칠 곳을 말하면 고쳐서 다시 보여 준다.
7. **쓰고 커밋한다.** 승인받은 뒤에 `plan.md`를 쓰고 그 파일만 커밋한다(원장 116). 커밋 메시지는 `plan: NNN-slug`다(원장 145). git 레포가 아니면 커밋하지 않는다.
8. **보고한다.** 쓴 위치, 커밋(또는 커밋하지 않은 까닭), phase의 수, 끝나지 않은 다른 작업. 끝나지 않은 다른 작업이 있으면 "이 작업의 실행은 worktree에서 한다"고 적는다(원장 128, 129).

끝은 보고다. 실행으로 이어갈지 묻는 물음은 4단계에서 더한다(원장 142).

### `plan.md`의 양식

스킬 본문 안에 넣는다. `{…}`는 그 자리에 무엇을 적는지를 가리키고, 쓴 `plan.md`에는 `{…}`가 남지 않는다.

````markdown
# {작업의 이름}

## 요청
{스킬을 부를 때 받은 요청 글 그대로}

## 목표
{이 작업이 끝나면 무엇이 되는지 한두 문장으로}

## 범위 밖
- {이 작업에서 하지 않을 것}

## 완료 조건
- {작업 전체가 끝났을 때 참이어야 하는 것}
  - 확인: {돌릴 명령과 기대 결과, 또는 무엇을 어디서 보는지}

## 결정
- {질문에서 정한 것}. 이유: {사용자가 말한 이유, 또는 고른 추천안의 이유}

## Phase 1: {이 phase의 이름}

**목표**: {이 phase가 끝나면 무엇이 되는지 한 문장으로}

**읽을 것**
- {먼저 읽을 파일이나 문서의 경로} ({거기에 무엇이 있는지})

**TODO**
- [ ] {무엇이 어떻게 바뀌는지} ({고칠 파일의 경로})

**통과 조건**
- {이 phase가 끝났을 때 참이어야 하는 것}
  - 확인: {돌릴 명령과 기대 결과, 또는 무엇을 어디서 보는지}
````

### 적는 규칙

**머리** (원장 118)
- 절은 다섯이고 순서를 바꾸지 않는다. 적을 것이 없는 절은 "없음"으로 적는다.
- 요청에는 스킬을 부를 때 받은 글을 그대로 옮긴다. 다듬지 않는다(원장 140).
- 결정에는 4번과 5번에서 정한 것을 적는다. 이유는 사용자가 말한 것이나 고른 추천안의 것만 적고, 지어 적지 않는다(원장 140).
- 작업의 이름(제목)은 한국어로 적고, 폴더 이름은 영어 소문자로 적는다.

**조건** (원장 119)
- 완료 조건과 통과 조건은 조건마다 `확인:` 줄을 하나 이상 붙인다.
- 확인은 돌릴 명령과 기대 결과를 우선한다. 명령으로 볼 수 없는 것만 "무엇을 어디서 본다"로 적는다.
- 확인 방법을 적을 수 없는 조건은 조건으로 적지 않는다. 질문으로 분명히 한다.
- 완료 조건마다 그것을 이루는 phase가 적어도 하나 있다(원장 139).

**phase를 나누는 기준** (원장 121)
1. phase 하나는 따로 확인할 수 있는 결과 하나를 낸다. 통과 조건이 없는 phase는 없다.
2. 머리와 그 절만 읽고 할 수 있다. 다른 phase 절의 글에 기대지 않는다.
3. 앞 phase가 통과한 상태에서 시작한다. 순서대로 한다.

- 개수의 상한은 두지 않는다. 작은 작업은 phase 하나다(원장 109).
- 제목은 `## Phase N: 이름`이고 번호는 1부터다. 앞 phase가 지워져도 번호를 다시 매기지 않는다(원장 136).

**phase의 절** (원장 120)
- 항목은 넷이고 순서를 바꾸지 않는다: 목표, 읽을 것, TODO, 통과 조건.
- 읽을 것에는 계획을 세우며 읽은 것 가운데 그 phase에 필요한 파일과 문서의 경로를 적는다. 뒤 phase가 앞 phase의 결과를 쓰면 그 위치를 경로로 적는다(원장 137). 읽을 것이 없으면 "없음"으로 적는다.

**TODO** (원장 122)
- 항목 하나는 무엇이 어떻게 바뀌는지를 결과로 적는다. 고칠 파일을 알면 끝에 경로를 괄호로 붙인다.
- 코드를 적지 않는다. 구현 방법은 실행하는 쪽이 정한다.
- 통과 조건의 확인이 아직 없는 테스트를 가리키면, 그 테스트를 쓰는 일을 같은 phase의 TODO에 넣는다(원장 138).
- 작업이 맥락 문서의 내용을 바꾸면 그 문서를 고치는 일을 해당 phase의 TODO에 넣는다(원장 126).
  - 머리의 결정 가운데 이 작업 밖에서도 지켜야 하는 것(기술 선택, 구조 규칙): `docs/ADR.md`에 항목을 더한다
  - 폴더나 모듈이 생기거나 구조 규칙이 바뀐다: `docs/ARCHITECTURE.md`를 고친다
  - 4번에서 "문서를 바꾸기로 하고 진행한다"를 골랐다: 어긋난 그 문서를 고친다

**그 밖**
- 요청에 이미 답이 적혀 있는 물음은 다시 묻지 않는다(원장 141).
- 맥락 문서가 지도에 다른 경로로 적혀 있으면 그 경로의 것을 읽는다.

**11번에서 계획할 작업** (원장 132): 2단계에서 미룬 둘을 작업 하나로 계획한다.
- 칸이 문장 중간에 있거나 한 칸이 여럿을 물을 때의 규칙을 context 스킬에 더한다. 2단계의 자기 적용에서 본 것은 셋이다: 칸 앞에 쉼표가 더해졌다, "없음" 답이 끊긴 문장이 됐다, 일부만 답한 칸이 닫혔다.
- context 스킬이 스캔 목록 밖의 파일(레포 밖의 메모리 파일)을 읽지 않게 하는 규칙을 더한다.

이 계획은 끝나지 않은 작업으로 남는다. 4단계의 자기 적용이 실행하고 5단계의 자기 적용이 검증한다.

**기계로 보는 것** (`bin/plancheck.py`를 새로 만든다)
- 위치: `docs/tasks/NNN-slug/plan.md`. `NNN`은 세 자리 숫자, `slug`는 영어 소문자 낱말 1~3개를 하이픈으로 이은 것
- 첫 줄이 `# `로 시작한다
- 머리의 `## ` 절이 요청, 목표, 범위 밖, 완료 조건, 결정의 순서다. 그 뒤에 `## Phase 1: `부터 번호가 1씩 는다
- 완료 조건의 항목마다 들여쓴 `- 확인:` 줄이 하나 이상 있다
- phase 절마다 `**목표**:`, `**읽을 것**`, `**TODO**`, `**통과 조건**`이 이 순서로 있다. TODO에 `- [ ]` 항목이 하나 이상 있고, 통과 조건의 항목마다 `- 확인:` 줄이 있다
- `{…}` 안내 글이 남아 있지 않다
- phase 절 안에 여러 줄 코드 블록이 없다
- 커밋: 판정 전보다 커밋이 하나 많고, 그 커밋에 든 파일이 `plan.md` 하나이고, 메시지가 `plan: NNN-slug`다. 판정 전에 깨끗하던 폴더는 판정 뒤에도 `git status`가 비어 있다

**읽어서 보는 것**: 결과를 요청과 답 파일과 나란히 놓고, 답에 없는 내용이 더해졌는지, 빠진 답이 있는지, phase 분해가 기준 셋에 맞는지를 표로 적어 사용자에게 보여 준다.

**이 판정이 보지 못하는 것** (원장 130의 트레이드오프): 코드를 읽고 적는 "읽을 것"과 코드에 기대는 phase 분해. 빈 폴더에는 코드가 없다. 11번이 스킬 본문이 있는 이 레포에서 한 번 본다.
