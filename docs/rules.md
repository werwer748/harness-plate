> [HANDOFF.md](../HANDOFF.md)에서 나눈 문서다. 장치를 만들거나 고치기 전에 읽는다. 기호(J, R, M1–M4, ADV)는 HANDOFF.md의 "재료" 표에 있다.

## 기본 흐름과 확장 조건 (2026-10-04)

**원칙**: 일반 작업은 메인 에이전트가 한 세션에서 직접 끝낸다. 계획 문서, 위임, 세션 분리, 별도 리뷰, 자동 회고는 아래 "확장할 조건"이 있을 때만 켠다. 켠 장치는 실패 감소나 시간 절감이 확인될 때 유지한다.

| 항목 | 기본값 | 확장할 조건 | 직접 만들기 전에 쓸 내장 기능 |
|---|---|---|---|
| 실행 | 메인이 직접 한다 | 대량 탐색이나 긴 출력(테스트 로그 등)을 격리할 때, 서로 독립인 작업을 나눌 때 | 서브에이전트. 맥락을 이어받아야 하면 fork(`/subtask`) |
| 계획 | diff를 한 문장으로 말할 수 있으면 계획 없이 실행한다 | 접근이 불확실하거나, 여러 파일을 고치거나, 낯선 코드일 때. 큰 기능은 스펙 하나를 쓰고 새 세션에서 구현한다 | plan mode |
| 맥락 | 짧은 `CLAUDE.md`(200줄 미만)와 필요할 때 읽기 | 일부 작업에만 필요한 지식이 생길 때 | 스킬, `paths:` 규칙 |
| 세션 | 한 작업은 한 세션에서 이어 가고, 작업이 바뀌면 `/clear` 한다 | 재개, 같은 문제를 두 번 교정해도 실패(맥락 오염), 스펙 → 구현 경계, 실행 격리 | `/clear`, `--continue`, `/rewind` |
| 검증 | 작업자가 실행 가능한 검사를 돌리고 명령과 출력을 증거로 보고한다 | 고위험 변경, 검사로 확인하기 어려운 품질, 무인 실행. 이때 새 컨텍스트 리뷰어 1명을 붙이고 정확성·요구사항 결함만 지적하게 한다 | `/code-review`, `/verify` |
| 반복 | 구체적 결함을 고쳤을 때 그 부분만 다시 확인한다. 상한은 한 층에만 둔다 | 새 증거가 추가 시도를 정당화할 때 | Stop 훅 연속 차단 상한(8회), `/goal` 조건의 턴 상한, `--max-budget-usd` |
| 개선 | 실행 기록만 모은다 | 같은 피드백·실패가 2회 이상, 모델 교체, 사용자 요청 | `/usage`, `/insights`, `/doctor`, M4 |

**확장을 가르는 축은 작업 크기만이 아니다.** 사람이 지켜보지 않는 시간이 길수록, 실패 비용이 클수록 장치가 값을 한다. M3의 P0(자기보고 완료 판정, 모델에 전달되지 않는 Stop 훅)는 무인 실행에서 생긴 문제다. 그래서 무인 실행을 켜는 시점에 해당 장치를 함께 켜고, 상호작용 세션의 기본값에는 넣지 않는다.

**한 세션에서 끝내는 비용은 세션 길이에 따라 커진다.** 2026-10-04 집계에서 토큰이 가장 많이 든 곳은 길게 이어진 대화형 세션이었다([부록 H](research-2026-10-04.md)). 한 작업이 끝나면 `/clear` 하고, 한 세션에 여러 작업을 잇지 않는다.

**내장 기능을 먼저 쓴다.** 설치된 Claude Code(2.1.289)에 `/goal`, `/code-review`, 동적 워크플로, fork, Stop 훅 차단 상한이 이미 있다. 같은 일을 하는 executor·리뷰어·재시도 루프를 직접 만드는 것은 내장 기능이 실측에서 부족했을 때로 미룬다.

**v0.1에서 기본으로 켜지 않는 것**: Team(지속형 에이전트, 워크플로, 에이전트 팀), 적대적 검증의 과반 판정과 심사위원단, loop-until-dry, 교차 모델 검증, step별 새 세션, 조율 전용 메인, `docs/` 전체 주입, 모든 작업의 plan·step·AC 파일, `CLAUDE.md` 안의 변경 이력, 매 작업 회고. 근거는 [부록 H](research-2026-10-04.md)에 있다.

## 진행 방식

- **순서** (2026-10-04 변경): 6축을 모두 결정한 뒤 만드는 대신, 기본 흐름을 먼저 돌리고 확인된 실패에만 장치를 더한다.
  1. 평소대로 작업한다. 전용 시험 프로젝트나 시험용 작업을 두지 않는다
  2. M4 보고서에서 튀는 세션을 고른다: 캐시 읽기가 큰 세션, 서브에이전트 비중이 큰 세션. 원인을 본다(긴 세션, 위임, 반복 탐색, 같은 검사의 재실행). 사용자 개입 횟수와 완료 뒤 발견한 결함은 작업당 한 줄로 적는다([task-log.md](task-log.md))
  3. 같은 원인이 2회 이상 나오면 그에 대응하는 장치나 습관을 하나 더한다. 내장 기능을 먼저 쓴다
  4. 품질·비용·시간을 보고 유지 여부를 정한다
  5. 결과를 [결정 기록](decisions.md)에 적고, 보류 조건이 충족된 결정을 연다
- **측정에도 비용이 든다**: 모든 장치를 통제 실험으로 비교하지 않는다. 실제 작업의 기록을 먼저 보고, 유지 여부가 갈리는 장치만 같은 대상으로 A/B를 잰다(M2의 리뷰어 측정 방식). 한 번의 실행 차이를 결론으로 삼지 않고, 검증을 줄여 결함을 놓친 것을 절감으로 세지 않는다.
- **축 검토**: 축별 표의 **남음** 항목과 보류 조건이 충족된 항목을 다룰 때는 종전 방식 그대로 한다. 레퍼런스 원문과 내 자산 코드를 근거로 선택지와 트레이드오프를 제시하고, 결정할 질문을 묻고, 확정한 결정을 [결정 기록](decisions.md)에 적는다.
- **확인 기준**: 켠 장치마다 "어떤 실패를 막는지"와 "어느 파일이나 메커니즘으로 구현되는지"가 한 줄로 적혀 있어야 하고, 결정 목록이 서로 모순되지 않아야 한다.
