# 아키텍처

## 기술 스택
- 마크다운 스킬(`SKILL.md`), JSON 매니페스트, Claude Code 훅으로 이루어진 플러그인이다.
- 훅 스크립트(편집 훅 `edit_guard.py`, 푸시 훅 `push_guard.py`)는 Python 3 표준 라이브러리로 쓰고 테스트는 `unittest`로 돌린다(ADR-019). 2026-10-17에 Python 3.13.2에서 테스트가 통과했다.
- 대상 도구: Claude Code(1단계는 2.1.291, 2단계의 2026-10-08 판정은 2.1.293, 3단계는 2.1.294에서 확인). Codex(0.160.0)는 2026-10-08에 확인을 멈췄고, Codex와 Grok Build로 넓히는 일은 v1.0 뒤에 한다(ADR-018). 도구별로 확인해 둔 사실은 `docs/TOOLS.md`에 있다.
- 배포: 플러그인과 마켓플레이스 목록. 레포는 GitHub의 공개 저장소 `werwer748/harness-plate`이고, `claude plugin marketplace add werwer748/harness-plate`로 마켓플레이스를 더한다. 대상 프로젝트의 CI 워크플로도 토큰 없이 여기서 plate를 받는다(ADR-022).

```
    ├── review/SKILL.md            # 코드 평가 스킬. run이 tasks 끝에 띄운 에이전트가 부른다
    ├── eval/SKILL.md              # 하네스 eval 스킬. run이 tasks 끝에 코드 평가 뒤 띄운 에이전트가 부른다
    └── cleanup/SKILL.md           # 정리 점검 스킬. 사용자가 부른다. 여섯 기준의 1라운드와 교차 검토의 2라운드를 저마다 새 에이전트에게 맡기고, 보고서를 쓰고, 발견을 tasks로 만들지 묻는다

├── test_push_guard.py             # 푸시 훅의 테스트
├── test_verdict.py                # 판정 스크립트의 테스트

├── test_manifests.py              # 두 매니페스트의 버전 줄이 같은지의 테스트
└── test_skill_rules.py            # run·plan·phase·check·retro·review·eval 본문의 고친 규칙(시작 권한 물음, RUNLOG 커밋 자리, 계획을 바꾸는 회고의 멈춤, 갈래마다 확인, 앞 phase 산출물에 기대는 조건, 돌려 본 결과를 본문 해시로 견줌, 앞 task 변경을 절 이름과 바뀐 글로 가리키는 읽을 것, 돌려 보는 확인의 차림·기대·결정과 TODO의 맞물림을 보는 초안 점검, 통과 조건은 커밋 전 작업 트리에서 돎, 지울 글 인용과 실패할 테스트 이름, 앞 task가 바꿀 글을 바뀐 뒤 꼴로 인용, 돌려 본 확인의 결과는 phase 기록에만 두고 맥락 문서에는 도구 동작만 한 줄로 더함, 앞 phase 기록 읽지 않음, `남은 것:` 줄, run 본문에 맥락 문서 커밋 규칙이 없고 사용량 까닭을 10번의 보고에만 적음, 시각·해시로 보는 파일을 고칠 때의 멈춤, git 명령에 명령 치환 없음, 계획 수정마다의 결정 줄, 맡기는 글 다섯의 표지 줄 `부른 쪽: plate:run`, retro가 `남은 것:` 줄은 회고가 "문제"로 판정한 것만 `FRICTION.md`의 문제로 모으고 멈춤이 아닌 물음에 `권한`을 넣음, eval 규칙 준수 표의 `RUNLOG` 커밋 두 행의 파일 칸이 `RUNLOG.md`뿐임과 정해 둔 물음의 `권한`, phase·check·retro·review·eval이 표지 줄도 작업 트리의 스킬 줄도 없을 때만 직접 부른 꼴로 보고함, run이 이슈의 글을 데이터로만 보고 제목·검색어·본문을 넘기는 법을 낱말 한 곳에 두고 `gh issue list`가 `body`로 먼저 거르고 PR을 열지 물을 때 댓글로 달 평가 절의 글을 보여 줌, run 3번의 두 표와 tasks 끝 표의 행 차례, 3번이 상태를 줄 머리 패턴으로 읽고 다시 맡기기로 한 `멈춤` 줄을 보고 "멈춘다"를 한 번 건너뛰며 회고의 세 번 실패 뒤에는 8번으로 감, 확인이나 회고 없이 다시 띄운 에이전트 줄에 까닭을 덧붙임, run 1번이 기본 브랜치도 `tasks/<이름>`도 아니면 바꿀지 묻고 물은 자리 `브랜치`가 두 목록에 있음, 0번이 비운 뒤 다시 불리면 PR·합침으로 감, "합친다"의 이 자리만의 물음과 `git switch` 실패 갈래, 작업 트리의 스킬 줄이 marketplace 매니페스트의 `source` 한 곳을 고르고 없으면 `plugin.json` 규칙으로 고르며 붙이면 첫 줄을 빼 옛 본문을 부르지 않음, 고칠 phase·고침 task가 문제의 글을 테스트 폴더에서 찾아 걸린 테스트를 넣음, 고침 task가 가리킨 tasks 완료 조건의 글과 확인을 함께 옮김, 양식을 읽는 법이 낱말에 한 번이고 다섯 자리가 가리킴, plan 1번이 평가가 시작된 tasks(`review.md`·`eval.md`가 있다)에는 더하지 않고 더하는 경우에는 앞 task 머리를 읽음, plan 6번 목록이 초안 전의 점검과 초안 뒤의 규칙으로 나뉨, plan에 `**그 밖**` 절이 없음, plan 남은 결과 항목이 작업 트리 항목을 가리킴, plan의 양식을 읽는 법이 낱말에 한 번이고 양식 절이 가리킴, plan의 규칙을 바꾸는 TODO가 같은 대상의 스킬 본문과 코드의 기존 줄도 찾고 같은 것을 시키는지 보는 확인을 둠, plan이 본문에 넣는 명령 예도 동작으로 쳐 돌리는 확인을 두거나 예를 뺌, run과 plan의 같은 정의 셋(테스트가 있는 프로젝트, 테스트 먼저의 기준, task 폴더 번호)이 같음)의 글이 제 절에 있는지와 모든 스킬의 앞머리가 Agent Skills 한도(description 1024자, name 64자) 안인지의 테스트
docs/                              # 이 레포의 하네스 기록. 위치는 AGENTS.md의 문서 지도를 따른다
```

## 패턴과 규칙
- 레일 규격(단계 순서, 기록 위치와 형식, 통과 조건)은 도구에 기대지 않는 파일로 두고, 서브에이전트와 훅은 도구별 구현으로 둔다. 이유: 레일을 돌리는 도구가 바뀌어도 똑같이 작동해야 한다(ADR-004).
- 스킬 본문은 하나만 두고 도구별 매니페스트가 같은 폴더를 가리킨다. 본문은 도구 이름 대신 동작으로 쓴다("사용자에게 묻는다", "파일을 옮긴다")(ADR-004).
- 양식은 스킬 본문 안에 넣는다. 이유: 별도 파일로 두면 대상 프로젝트의 작업 디렉터리 밖이라 읽기가 거부된 전례가 있다.
- 위치 규칙은 대상 프로젝트의 `AGENTS.md`에 두고 `CLAUDE.md`에는 `@AGENTS.md` 임포트만 둔다. 이유: Claude Code는 `CLAUDE.md`가 없을 때만 `AGENTS.md`를 읽고, Codex와 Grok Build는 `AGENTS.md`를 자동으로 읽는다.
- 스킬이 다른 스킬의 절차를 써야 하면 그 스킬을 이름으로 부른다(`plate:setup`, `plate:context`). 절차를 복사하지 않는다. 예외로 run은 tasks 커밋이 맡길 스킬의 `SKILL.md`를 바꿨으면 맡기는 글의 끝에 그 파일의 저장소 안 경로를 읽으라는 줄(작업 트리의 스킬 줄)을 붙인다. 그 바꿨는지는 `git merge-base`로 갈라진 곳의 해시를 먼저 얻고 그 해시를 넣어 `git diff --name-only`를 따로 불러 본다(명령 치환은 헤드리스의 권한 검사가 막는다). 맡길 때마다 다시 본다. 저장소 뿌리에 `.claude-plugin/marketplace.json`이 있고 이름이 `plate`인 플러그인의 `source`가 있으면 그 marketplace 매니페스트의 `source` 아래의 `skills/{스킬 이름}/SKILL.md` 한 곳으로 좁히고(tasks가 고친 사본이 절차를 바꾸지 못하게), 없으면 이름이 `plate`인 `.claude-plugin/plugin.json`을 둔 폴더 아래의 것을 고른다. 그 줄을 붙이면 맡기는 글의 첫 줄(이름으로 스킬을 부르는 줄)을 빼서 이름으로 옛 본문을 부르지 않는다(두 본문이 실리지 않게). run의 맡기는 글 다섯(수행, 확인, 회고, 코드 평가, 하네스 eval)의 코드 블록은 늘 표지 줄 `부른 쪽: plate:run`으로 끝나고, 작업 트리의 스킬 줄은 그 뒤에 붙는다. 이유: 세션에 실린 스킬 본문은 세션을 띄울 때의 것이라 이름으로만 맡기면 고치기 전의 절차로 돈다(`docs/TOOLS.md`의 "세션 도중의 스킬 본문 고침"). phase, check, retro, review, eval 다섯 스킬은 맡은 글에 표지 줄이나 작업 트리의 스킬 줄이 있으면 run이 띄운 것으로 가르고 정해 둔 줄만 돌려주며, 둘 다 없을 때만 사용자가 직접 부른 꼴(목록과 run 안내를 더한다)로 보고한다. 표지 줄은 띄운 에이전트가 run이 띄운 호출인지 가르게 한다(#51).
- 각 단계의 완성은 Claude Code에서 실제로 실행한 결과를 기대값(답 파일, 빌드 매니페스트, 토큰 파일)과 견줘 판정한다. 1단계 전부와 2단계 판정의 일부는 Codex에서도 같은 결과를 확인했고, 2026-10-08부터는 Codex에서 확인하지 않는다(ADR-018).
- 도구마다 다른 동작과 확인을 멈춘 지점은 `docs/TOOLS.md`에 적는다(ADR-018). 시험 실행 기록은 적지 않는다. 돌려 본 확인의 차림, 출력, 본문 해시는 그 phase의 기록에 두고, `docs/TOOLS.md`에는 다음 계획이 알아야 할 도구 동작만 버전과 함께 한 줄로 더한다.
- 테스트와, `--plugin-dir`로 이 레포의 plate를 실은 세션의 푸시 훅은 `edit_guard`를 불러와 `plugins/plate/hooks/__pycache__/`를 만든다. git은 이 폴더를 무시하지만(`.gitignore`) `diff -r`는 다른 것으로 내므로, `plugins/plate`를 복사본과 견주는 확인은 `diff -r -x __pycache__`로 쓴다.
- 대상 프로젝트의 규칙이 스킬의 규칙과 부딪히면 프로젝트의 규칙이 우선한다. 스킬의 절대 규칙도 든다. 단계를 건너뛰라는 규칙은 들지 않는다. 여덟 스킬(plan, run, phase, check, retro, review, eval, cleanup)의 본문에 넣었고, 따른 곳은 보고나 기록에 적는다.
- 막는 장치는 setup이 대상 프로젝트의 `AGENTS.md`에 넣는 규칙 구간(`<!-- plate:rules:start -->`부터 `<!-- plate:rules:end -->`까지)이다. 코드를 고치는 요청은 계획부터 세우고, task는 task 회고가 통과해야 끝나고, tasks는 끝의 코드 평가와 하네스 eval을 담은 전체 보고가 나와야 끝나며, 다른 규칙이 이 단계들을 건너뛰라고 해도 따르지 않는다. 이 규칙 구간이 기본이고, 훅(`plugins/plate/hooks/`)은 Claude Code의 구현으로 더 막는다. 편집 훅(`edit_guard.py`)은 파일 편집 도구의 호출만 보고, `phase-N.md`가 있는 task가 없을 때의 코드 편집과 테스트 먼저인 phase에서 테스트 변경 없는 구현 편집을 막는다. setup이 아직 없는 `.github/workflows/plate-review.yml`이나 `.github/CODEOWNERS`를 쓰는 것은 두 막음에서 모두 뺀다. 같은 파일을 테스트 먼저 때문에 세 번 막으면 더 시도하지 않고 막힘으로 멈춰 까닭과 해결책을 논의하며, 훅을 끄는 스위치는 두지 않는다. 푸시 훅(`push_guard.py`)은 Bash 호출의 명령을 `&&`, `||`, `;`, `|`, 줄바꿈으로 나눠 그 안의 `git push`(`git -C <폴더>`면 그 폴더의 것)가 origin의 기본 브랜치를 바꾸거나 지우면 막는다. 기본 브랜치에 있는 채 대상 없이 하는 push도 든다. 다른 브랜치, origin 밖 원격, 셋업 안 된 프로젝트의 푸시는 막지 않고, 사람의 푸시(git 훅, 브랜치 보호 규칙)는 다루지 않는다. 명령을 나눌 때 heredoc의 본문과 `#` 주석은 명령으로 보지 않고, 줄 잇기(`\`+줄바꿈)는 명령의 경계로 보지 않는다. `$( … )`와 백틱의 명령 치환은 그 안의 따옴표, 주석, heredoc을 바깥과 따로 세고, 닫는 `)`나 백틱에서 바깥(바깥 큰따옴표 안이었으면 그 안)으로 돌아오며, 치환 안의 push는 읽지 않는다. 따옴표가 어긋나 명령을 나누지 못하면(셸은 짝을 맞추는 `$'…'` 안의 `\'`도 든다) 호출한 폴더가 셋업된 프로젝트이고 명령의 글에 `push`가 있을 때 막고, push를 다른 명령과 잇지 말고 따로 하라고 알린다. 푸시 훅이 막는다고, 또는 막지 않는다고 약속하는 꼴은 `tests/test_push_guard.py`의 시험이 다루는 꼴뿐이고, 여기까지 적은 막는 것과 막지 않는 것도 그 꼴로 읽는다. 그 밖의 셸 구문과 git의 표기는 약속하지 않는다. 같은 호출에서 `cd`·`pushd` 뒤에 하는 push는 호출한 폴더에서 보고, 명령 치환이나 변수로 적은 대상과 `sh -c`·`eval`처럼 다른 명령이 감싼 push는 읽지 않으며, 매개변수 확장(`${ … }`), 산술 명령(`(( … ))`) 같은 셸 구문과, `heads/<이름>`으로 적은 대상(git은 `refs/heads/<이름>`으로 읽는데 훅은 막지 않는다), `--repo`로 적은 원격(훅은 원격을 origin으로 보고 기본 브랜치에서는 막는다) 같은 git의 표기에서 놓치거나 잘못 막는 것은 결함으로 보지 않는다. 에이전트의 푸시를 막는 기본은 스킬마다의 푸시 규칙(phase, check, retro, review, eval, cleanup은 "푸시하지 않는다", run은 "PR을 연다"에서 승인받아 `tasks/<이름>`을 origin에 올릴 때만 푸시한다)이고, 푸시 훅은 흔한 꼴을 한 번 더 막는다. 이유: 세 도구가 모두 `AGENTS.md`를 읽고 서브에이전트에도 실린다. 훅은 Claude Code에서만 돌므로 규칙을 대신하지 않고, 잘못 막을 때는 끄는 대신 까닭을 찾아 해결책을 논의한다.
- run은 첫 에이전트를 띄우기 전에 plan 모드가 켜져 있거나 쓰기가 막힐 권한 모드면 알리고 바꿀지 묻고 멈추며, 도구가 지금 모드를 알려 주지 않아 확인할 수 없으면 그렇다고 보고에 적고 잇는다. 회고의 문제를 고치려면 계획 파일의 목표나 완료 조건을 바꾸거나 좁혀야 하거나, 고칠 파일이 완료 조건이 돌린 시각이나 본문 해시로 보는 파일인데 고친 뒤 그 확인을 다시 참으로 둘 길이 계획에 없으면 고칠 phase를 더하지 않고 어느 실행 방식이든 멈추고(물은 자리는 `멈춤`), 멈춘 자리에서 계획을 고치면 수정마다 결정 줄 하나를 task 머리(tasks 머리를 고쳤으면 거기에도)에 더하고 커밋 전에 그 줄이 있는지 보고, 고칠 phase의 TODO에는 고칠 동작을 적은 맥락 문서와 README의 줄을 넣고, 계획 커밋으로 이미 고친 문제는 TODO에 넣지 않고 통과 조건에 그 커밋의 해시와 함께 따로 적는다(그 커밋은 마지막 회고 절을 더한 커밋의 해시를 먼저 얻고 그 해시를 넣은 `git log`를 따로 불러 찾는다). `RUNLOG.md`의 줄은 phase 통과, 고칠 phase, 멈춤의 커밋에 함께 넣고, 회고 에이전트와 코드 평가·하네스 eval 에이전트가 돌아오면 그 자리에서 그 파일만 넣는 커밋(`NNN-slug: RUNLOG`, `<tasks 이름>: RUNLOG`)으로 넣는다. 사용량이 돌아오지 않은 까닭은 보고에만 적는다. 이유: 띄운 에이전트는 자기 권한 모드를 바꾸지 못해 막힌 채 띄우면 수행이 되풀이되고(#40), 고칠 phase는 계획을 고치지 못하며(#34, #38), 시각이나 해시로 보는 파일을 고치면 완료 조건이 참일 수 없고(#46), 명령 치환은 헤드리스에서 막히며(#47), 결정 줄 더하기는 커밋 전에 보지 않으면 두 번째 수정에서 빠지고(#48), 커밋하지 않은 줄이 다음 에이전트의 커밋 판단에 낀다(#44).
- run은 기본 브랜치(`origin`의 HEAD, 없으면 `main`, 그다음 `master`)에서 시작하면 tasks마다 하나인 `tasks/<이름>` 브랜치를 만들어 실행하고, 기본 브랜치도 `tasks/<이름>`도 아닌 브랜치에서 시작하면 지금 브랜치를 보여 주고 `tasks/<이름>`으로 바꿀지 묻고(물은 자리 `브랜치`, 거절하면 실행하지 않고 끝난다), 브랜치를 만들거나 바꾼 뒤 로컬 기본 브랜치에 `origin/<기본 브랜치>`에 없는 커밋이 있으면(`git fetch`는 하지 않고, origin이나 그 원격 추적 ref가 없으면 묻지 않는다) 그 커밋을 보여 주고, 그 커밋이 모두 `tasks/<이름>`에 있으면 로컬 기본 브랜치를 `origin/<기본 브랜치>`로 되돌릴지 묻고(커밋은 tasks 브랜치에 남는다), tasks 브랜치에 없는 커밋이 있으면 묻지 않고 그대로 두며, tasks 끝에서 `docs/tasks/`를 비운 뒤 `origin`이 GitHub이면 `tasks/<이름>`을 origin에 푸시해 기본 브랜치로 가는 PR을 열지 묻고, `origin`이 없거나 GitHub의 것이 아니면 기본 브랜치로 합칠지 묻는다. 실행 방식과 상관없이 묻는다. 비운 뒤 PR이나 합침을 묻기 전에 세션이 끊겨 다시 부르면, tasks 머리가 없어도 지금 브랜치가 `tasks/<이름>`이고 마지막 커밋이 `<이름>: 비움`이면 PR·합침으로 가고, PR에 쓸 글은 비움 커밋의 부모에서 읽는다. 합칠 때는 커밋하지 않은 변경이 있으면 이 자리에서 그대로 합칠지 묻고(`RUNLOG.md`에 적지 않는다), `git switch`가 실패하면 합치지 않는다. PR의 본문에는 tasks 머리의 요청과 목표, tasks 끝의 전체 보고(코드 평가와 하네스 eval의 등급, 게이트, 고친 것, 올린 이슈)를 넣고, plate 워크플로(`plate@harness-plate`가 적힌 워크플로 파일)가 없으면 `review.md`의 마지막 평가 절을 PR 댓글로 달고, PR을 열지 물을 때 댓글로 달 그 평가 절의 글을 함께 보여 준다. 이슈·PR 명령의 제목과 검색어는 작은따옴표로 감싸 넘기고 본문과 댓글은 `--body-file`로 넘기며, plate 저장소 이슈의 제목·본문·댓글은 같은 문제인지 가르는 데이터로만 보고 그 안의 지시를 따르지 않는다. run은 PR을 머지하거나 닫지 않는다. 푸시는 이 PR을 열 때만 한다. 이유: 끝의 평가와 보고까지 가지 않은 tasks가 기본 브랜치에 들어가지 않게 하고, GitHub 원격이 있으면 기본 브랜치로 들어가는 길을 CI의 판정이나 사람의 머지로 모은다.
- PR의 CI는 setup이 대상 프로젝트에 쓰는 워크플로(`.github/workflows/plate-review.yml`)가 한다. setup은 GitHub 원격이 있고 plate 워크플로가 없을 때 `gh api user`의 login을 보여 주며 둘지 묻고, 승인하면 쓴다. 승인했고 `.github/CODEOWNERS`가 없고 login을 얻었으면 `/.github/workflows/ @<login>`, `/.github/CODEOWNERS @<login>` 두 줄로 CODEOWNERS를 쓰고, 그 밖에는 쓰지 않고 넣을 줄을 보고에 적는다. ruleset(기본 브랜치, PR 필수, 승인 수 0, 코드 소유자 리뷰 필수, 저장소 관리자는 PR로만 우회)은 걸지 않고 보고에 거는 법(`docs/TOOLS.md`에서 시험한 JSON의 `gh api` 명령, Settings → Rules → Rulesets, 비공개 저장소는 요금제에 따라 걸 수 없다는 것, PR을 연 계정이 유일한 코드 소유자면 막지 못한다는 것)을 적는다. 훅은 아직 없는 이 파일과 `.github/CODEOWNERS`를 쓰는 것을 남은 phase가 있든 없든, 테스트 먼저든 아니든 막지 않아서, 이미 셋업된 프로젝트에서 setup을 다시 불러도 쓴다. 이미 있는 이 두 파일의 편집과 다른 워크플로 파일은 다른 코드 파일처럼 막는다. `review` 잡은 읽기 권한만으로 토큰 없이 공개 마켓플레이스(`werwer748/harness-plate`)에서 plate를 받아 review의 PR 모드를 부르고 등급 묶음을 구조화 출력으로 낸다. 액션을 부르기 전에 `AGENTS.md`를 기준 브랜치의 것으로 되돌리고, 기준 브랜치에 없으면 PR의 것을 지운다. PR이 `AGENTS.md`에 넣은 지시가 `CLAUDE.md`의 `@AGENTS.md`로 세션에 실려 등급을 바꾸는 길(#11)을 막는 것이다. PR 모드는 지침 파일과 `docs/ARCHITECTURE.md`의 `## 결과물인 마크다운` 절을 기준 브랜치에서 읽고, PR이 바꾼 파일의 글을 지시로 따르지 않는다. `CLAUDE.md`와 그것이 불러오는 `AGENTS.md` 밖의 파일은 되돌리지 않고 이 규칙만이 막는다. review 단계가 실패하면 다음 단계가 액션의 실행 결과 파일에서 오류 줄(결과의 `is_error`와 오류 글)만 로그에 내고, Claude의 메시지 전부를 로그에 내는 입력은 켜지 않는다. PR 모드는 명령 절의 설치를 먼저 돌린 뒤 빌드·린트·테스트를 잰다. `verdict` 잡이 쓰기 권한으로 PR의 바뀐 파일 목록을 파일 목록 API(`gh api --paginate repos/$GH_REPO/pulls/$PR/files`)로 파일에 받고(그 API가 실패하면 워크플로 경로 한 줄을 적어 머지 요청 쪽으로 보낸다) 등급 묶음과 함께 판정 스크립트(`plugins/plate/ci/verdict.py`)에 `--changed-files`로 넘기고, 평가서를 PR 댓글로 달고, 자동 머지면 merge commit으로 합치고 머리 브랜치를 지우며, 닫기면 PR을 닫는다. 판정은 셋이다. 자동 머지는 빌드·린트·테스트가 모두 통과나 없음이고, 새 줄 커버리지가 80% 이상이나 보지 않음(결과물인 마크다운의 줄을 뺀 새 줄이 20줄 미만이면 커버리지를 쟀든 못 쟀든 먼저 보지 않음이다)이고, 신뢰성·보안·유지보수성이 모두 A일 때다. 닫기는 빌드·린트·테스트 가운데 실패가 있거나 보안이 C 이하일 때다. 그 밖(모름이 있을 때도 든다)은 머지 요청이다. 판정 스크립트가 `--changed-files`로 바뀐 파일 목록(한 줄에 경로 하나)을 받으면, 그 안에 워크플로 경로(`.github/workflows/`로 시작하는 경로)가 있을 때 자동 머지를 머지 요청으로 내린다. 닫기와 머지 요청은 그대로이고, 목록을 받지 않으면 목록 없이 판정한다. 이유: 판정 규칙은 숫자와 등급만 보므로 스크립트가 늘 같은 답을 내고, 에이전트에게는 머지 권한이 없다. 머지 권한이 없는 것은 등급을 막지 않으므로, PR이 바꾼 지시가 등급을 바꾸는 길은 `AGENTS.md` 되돌림과 PR 모드의 규칙으로 막는다(ADR-021). 워크플로 검사는 PR이 워크플로를 고쳐 건너뛸 수 있어서, 그 길은 사용자가 거는 ruleset과 CODEOWNERS가 PR을 연 계정이 코드 소유자가 아닐 때 막는다(ADR-023).

```

       → tasks가 진행 중이면 새 요청을 지금 tasks에 task로 더할지 묻고, 더하면 이미 있는 task 머리를 읽는다
       → docs/tasks/review.md나 eval.md가 있어 tasks 끝의 평가가 시작된 tasks면 더할지 묻지 않고 더하지 않는다고 알리고 끝난다)
→ 실행(첫 에이전트를 띄우기 전에 plan 모드가 켜져 있거나 쓰기가 막힐 권한 모드면 알리고 바꿀지 묻는다(확인할 수 없으면 그렇다고 적고 잇는다)
       → 기본 브랜치에서는 tasks/<이름> 브랜치를 만들거나 바꾸고, 기본 브랜치도 tasks/<이름>도 아닌 브랜치에서는 tasks/<이름>으로 바꿀지 묻는다(거절하면 실행하지 않고 끝난다)
       → tasks/<이름> 브랜치를 만들거나 바꾼 뒤, 계획의 커밋이 로컬 기본 브랜치에만 있고 그 커밋이 모두 tasks 브랜치에 있으면 그 커밋을 보여 주고 로컬 기본 브랜치를 origin의 것으로 되돌릴지 묻고, tasks 브랜치에 없는 커밋이 있으면 묻지 않고 그대로 둔다고 알린다
       → 실행 방식(task 하나씩, tasks 일괄)을 묻는다
       → phase마다 새 에이전트가 수행해 phase-N.md에 기록을 덧붙이고, 다른 새 에이전트가 통과 조건과 빌드·린트·테스트를 돌려 확인 절을 더한다
       → 확인이 통과하면 phase-N.md를 done-phase-N.md로 바꾼다
       → task의 phase가 모두 통과하면 또 다른 새 에이전트가 task 회고를 task 폴더의 retro.md에, tasks 끝에 볼 것을 docs/tasks/FRICTION.md에 적는다
       → 회고의 문제는 고칠 phase를 더해 고친다(task 하나씩은 승인받고, tasks 일괄은 묻지 않는다. 고치려면 계획의 목표나 완료 조건을 바꾸거나 좁혀야 하면 더하지 않고 멈춘다)
       → 띄운 에이전트마다, 물은 자리마다 docs/tasks/RUNLOG.md에 한 줄을 남기고, 회고와 코드 평가와 하네스 eval의 에이전트가 돌아오면 그 줄을 그 자리에서 RUNLOG.md만 넣는 커밋으로 넣는다)
→ tasks 끝(새 에이전트가 바뀐 코드를 평가해 docs/tasks/review.md에, 다른 새 에이전트가 하네스를 eval해 docs/tasks/eval.md에 적는다
       → 전체 보고와 고칠 안을 한 번에 묻는다
       → 승인받은 대로 plate 자체의 고칠 거리는 GitHub 이슈로 올리고, 미룬 소스 문제는 docs/BACKLOG.md에 적고, 고칠 것은 고침 task로 더해 같은 레일로 돌린다
       → docs/tasks/를 비운다
       → origin이 GitHub이면 tasks/<이름>을 푸시해 기본 브랜치로 가는 PR을 열지 묻는다(본문은 tasks의 요청과 목표와 전체 보고, plate 워크플로가 없으면 review.md의 마지막 평가 절을 PR 댓글로 달고, 그 평가 절의 글을 물을 때 함께 보여 준다)
       → origin이 없거나 GitHub의 것이 아니면 기본 브랜치로 합칠지 묻는다
       → 비운 뒤 PR이나 합침을 묻기 전에 끊겨 다시 부르면, tasks/<이름>에서 마지막 커밋이 <이름>: 비움일 때 비움 커밋의 부모에서 글을 읽어 PR·합침으로 간다)

PR(CI 워크플로가 있는 프로젝트에서 열리거나 갱신되면)
→ review 잡(읽기 권한만. AGENTS.md를 기준 브랜치의 것으로 되돌리고(없으면 지우고), 공개 마켓플레이스에서 받은 plate의 review가 PR 모드로 지침 파일과 결과물인 마크다운 절을 기준 브랜치에서 읽어 평가서 파일과 등급 묶음(구조화 출력)을 낸다. review 단계가 실패하면 실행 결과 파일의 오류 줄만 로그에 낸다)
→ verdict 잡(쓰기 권한. PR의 바뀐 파일 목록을 받아 판정 스크립트가 등급 묶음과 그 목록으로 자동 머지, 머지 요청, 닫기 가운데 하나를 고른다. 워크플로를 바꾼 PR은 자동 머지 대신 머지 요청이다
       → 평가서를 PR 댓글로 단다
       → 자동 머지면 merge commit으로 합치고 머리 브랜치를 지우고, 닫기면 PR을 닫고, 머지 요청이면 사람이 머지하도록 둔다)

정리 점검(사용자가 cleanup을 부르면. 셋업이 안 된 프로젝트면 점검하지 않고 끝난다)

→ 보고서(지난 docs/cleanup/ 보고서와 견줘 docs/cleanup/YYYY-MM-DD.md에 쓰고, AGENTS.md 문서 지도에 docs/cleanup/ 행이 없으면 더하고, 그 둘만 커밋한다)
→ 발견을 tasks로 만들지 묻는다
       → 동의하면 고른 발견을 계획(plan)에 넘기고, 고르지 않은 발견은 보고서에 "미룸"으로 적어 커밋한다
```
