# Architecture Decision Records

## 철학
하나씩 완성한다. 큰 계획을 한 번에 확정하지 않고, 만들기 전에 질문으로 구현 목표를 명확히 한다. 추측으로 적지 않는다.

각 항목의 "원장"은 단계 설계 문서의 결정 원장 번호다. 1~39는 1단계(`docs/tasks/001-setup/plan.md`), 40~100은 2단계(`docs/tasks/002-context/plan.md`), 101~153은 3단계(`docs/tasks/003-plan/plan.md`)의 것이다. 그 문서들은 v1.0에서 지워지므로(ADR-011, ADR-020, ADR-032) 결정의 내용은 이 문서에 모두 옮겨 적었다. 이유와 트레이드오프는 기록이 있는 것만 적었고, 기록이 없는 칸은 `{확인 필요}`로 두었다.

### ADR-001: 완전히 새로 시작한다
- **원장**: 1, 22, 31, 36
- **결정**: 옛 plate v0.3.0과 그 결정 기록은 구속력이 없다. 기존 레포를 쓰되 브랜치 `rail`에서 옛 파일을 전부 지우고 시작한다. 옛 내용은 태그 `legacy-0.3.0`으로 남긴다. GitHub 레포가 지워져 있어서 같은 이름의 비공개 레포로 다시 만들고 옛 파일을 커밋 하나(3c8bcb6)로 `main`에 올렸다. `main`을 `rail`로 바꾸는 일은 1단계 뒤에 따로 확인한다.
- **이유**: 이전의 실패가 둘이었다. 하네스가 완성되지 않았고(결정만 쌓임), 결과물이 의도와 달랐다(구현 목표가 불명확).
- **트레이드오프**: 옛 레포의 커밋 이력과 PR 기록은 남아 있지 않다. 파일 내용만 같다.

### ADR-002: 단계마다 질문하고 하나씩 완성한다
- **원장**: 5, 6, 9, 13, 35
- **결정**: 큰 계획을 한 번에 확정하지 않는다. 5단계(셋업 → 맥락 → 계획 → 실행 → 검증)를 하나씩 완성하고, 단계마다 만들기 전에 질문 라운드를 연다. 첫 단계는 플러그인 뼈대와 셋업만 만든다. 양이 많은 계획은 `plan.md`와 `TODO.md`로 나누고, 구현은 새 세션에서 TODO를 체크하며 진행한다.
- **이유**: 이전의 실패가 둘이었다. 하네스가 완성되지 않았고(결정만 쌓임), 결과물이 의도와 달랐다(구현 목표가 불명확).
- **트레이드오프**: 결과물을 빨리 확인하는 것을 포기했다.

### ADR-003: 막을 실패 둘과 파이프라인
- **원장**: 2, 3, 4, 8
- **결정**: 강제로 막을 실패는 둘이다: 긴 세션의 컨텍스트 팽창, 검증 없는 완료 선언. 예외 없이 모든 작업이 파이프라인을 거친다. 바깥은 고정 단계(계획 → 실행 → 검증)이고, 실행 안쪽은 계획이 정한 N개 phase다(ADR-022로 바뀜). 실행 phase는 메인이 조율하고 phase마다 새 컨텍스트의 에이전트가 수행하며 기록을 남긴다. 질문과 승인은 메인이 맡는다.
- **이유**: 컨텍스트의 신선함을 유지하고 할루시네이션을 막기 위해서다.
- **트레이드오프**: 결과물을 빨리 확인하는 것을 포기했다.

### ADR-004: 레일은 도구가 바뀌어도 같은 규격이다
- **원장**: 17, 20, 27, 33, 34
- **결정**: 우선 Claude Code, Codex, Grok Build에 맞추고 이후 넓힌다. 스킬 본문은 하나이고 도구별 매니페스트가 같은 폴더를 가리킨다. 각 단계는 Claude Code에서 만들고 Codex에서 같은 결과를 확인해야 완성이다(ADR-018로 바뀜). Grok Build는 설치한 시점부터 확인한다(ADR-018로 바뀜). 일치 기준은 빈 폴더는 완전 일치, 기존 프로젝트는 파일 목록·위치·지도 구간 일치다. Codex 확인용 로컬 마켓플레이스 등록과 설치는 확인 뒤에도 그대로 둔다.
- **이유**: 레일은 같은 규격으로 물품을 찍어내고, 레일을 돌리는 도구가 바뀌어도 똑같이 작동해야 한다. 그래서 레일 규격은 도구에 기대지 않는 파일로 두고 서브에이전트와 훅은 도구별 구현으로 둔다. Grok Build는 이 Mac에 설치돼 있지 않다. Codex에는 플러그인을 한 세션에만 불러오는 옵션이 없다.
- **트레이드오프**: Codex 매니페스트로 `.codex-plugin/plugin.json`을 쓴다. Codex 공식 문서는 새 패키지에 플러그인 루트의 `plugin.json`을 권하고 `.codex-plugin`은 호환용이라고 적는다.

### ADR-005: 플러그인과 셋업 스킬로 배포한다
- **원장**: 7, 28, 29
- **결정**: 배포는 플러그인으로 하고, 대상 프로젝트에는 셋업 스킬로 기준을 세운다. superpowers는 설치하지 않고 기법만 가져온다(절대 규칙을 단정문으로 적기, 승인 전 진행 금지). 옛 훅 2개(branch-guard, constitution)는 1단계에 가져오지 않는다.
- **이유**: 너무 가벼워도, 너무 무거워도 좋지 않다. 사용자가 생각한 수준의 울타리를 짓기 위해서다.
- **트레이드오프**: 하네스를 쉽게 완성해 볼 수 있지만 그러지 않았다.

### ADR-006: 하네스 기록은 모두 `docs/` 아래에 둔다
- **원장**: 10, 11, 23, 24, 25
- **결정**: 맥락은 `docs/*.md`, 작업 기록은 `docs/tasks/NNN-slug/{plan,phase-N,verify}.md`에 둔다. 작업 기록은 git에 커밋해 보존한다(ADR-022로 바뀜). 위치 규칙은 하네스 기록에만 적용하고 README, CHANGELOG 같은 일반 문서는 대상이 아니다. 지도에 없는 종류의 기록은 위치를 사용자에게 묻고 지도에 행을 더한 뒤 만든다. 셋업은 지도의 표식 구간만 교체한다.
- **이유**: 기록을 둘 위치가 정해져 있지 않으면 세션마다 다른 곳에 문서를 만들고, 다음 세션은 그 문서를 찾지 못한다.
- **트레이드오프**: 없음

### ADR-007: 위치 규칙은 `AGENTS.md`에, `CLAUDE.md`에는 임포트만 둔다
- **원장**: 14, 18, 37
- **결정**: 문서 지도는 프로젝트의 `AGENTS.md`에 넣고 `CLAUDE.md`는 `@AGENTS.md` 한 줄로 둔다. 내용이 있는 기존 `CLAUDE.md`는 `AGENTS.md`로 옮기기를 제안한다. 거절하면 기존 내용을 그대로 두고, `@AGENTS.md` 줄이 없을 때만 맨 위에 더한다.
- **이유**: Claude Code는 `CLAUDE.md`가 없을 때만 `AGENTS.md`를 읽는다. Codex와 Grok Build는 `AGENTS.md`를 자동으로 읽는다. 이미 있는 줄을 다시 더하지 않는 것은, 시험한 실제 프로젝트의 `CLAUDE.md`에 그 줄이 이미 있었고 더하면 거절한 사용자의 기존 내용을 고치게 되기 때문이다.
- **트레이드오프**: 파일은 적을수록 좋지만 에이전트의 범용성을 위해 포기했다.

### ADR-008: 셋업은 기존 프로젝트의 문서를 승인받은 만큼만 옮긴다
- **원장**: 15, 19, 32
- **결정**: 같은 역할의 기존 문서는 표준 위치로 옮기기를 제안하고 승인받은 것만 옮긴다. 여러 파일로 나뉜 기존 문서는 합치지 않고 지도에 경로만 적는다. git 레포가 아니면 `git init`을 제안한다. UI 프로젝트면 디자인 문서를 만든다.
- **이유**: 기존의 스타일을 파괴하고 작업 여건을 강요하는 구성이 아니라, 기존의 구성을 승계하는 구성을 원했다.
- **트레이드오프**: 하네스 아키텍처의 통일성을 포기했다.

### ADR-009: 문서 양식과 채우는 방식
- **원장**: 12, 16, 21
- **결정**: PRD·ARCHITECTURE·ADR 양식은 옛 plate의 것을 그대로 쓴다. 디자인 문서는 `docs/DESIGN.md`이고 Google의 DESIGN.md 규격을 따르며 UI 프로젝트일 때만 만든다. 맥락 채우기는 스캔과 질문 라운드로 하고 추측으로 적지 않는다.
- **이유**: 맥락 문서를 추측으로 채우면 틀린 내용이 다음 작업의 근거가 된다.
- **트레이드오프**: DESIGN.md 규격은 alpha라 절 구성이 바뀔 수 있다.

### ADR-010: 완성은 실제 실행으로 판정한다
- **원장**: 26, 38
- **결정**: 완성 판정은 빈 폴더와 기존 프로젝트 복제본에서 실제로 실행한 결과를 체크리스트로 확인해서 한다. 시험 폴더는 `/tmp/plate-rail-test`에 둔다(ADR-019로 바뀜).
- **이유**: 세션 임시 폴더는 실행 도중 회수된 일이 있어 시험 폴더를 두기에 맞지 않았다. 실제 실행으로 판정하는 이유는 특정 프로젝트에 강하게 결합되어 있는 하네스를 만들게 되는 것을 방지하기 위해서다.
- **트레이드오프**: 사용성을 빠르게 테스트해 보기가 힘들어졌다.

### ADR-011: 결정은 ADR에 남기고 단계 기록은 v1.0에서 지운다
- **원장**: 30, 39
- **결정**: 결정은 하네스 레포에 자기 셋업을 적용해 이 문서에 남긴다. 단계의 `plan.md`와 `TODO.md`는 `docs/tasks/001-setup/`에 두고 문서 지도에 행을 더하지 않는다. 하네스가 v1.0이 되면 이 파일들을 모두 지운다.
- **이유**: 사용자의 말: 하네스가 예정된 작업을 모두 끝내고 일부 추가 기능까지 끝내 v1.0이 되고 나서는 모두 지울 것이다.
- **트레이드오프**: 없음

### ADR-012: 맥락 채우기는 스킬 하나이고 남은 칸만 채운다
- **원장**: 40, 45, 47, 48, 58, 59, 72, 74, 96
- **결정**: 맥락 문서는 스킬 하나(`plate:context`)가 채운다. 순서는 PRD → ARCHITECTURE → ADR → DESIGN이고, DESIGN은 문서 지도에 행이 있을 때만 채운다. 채우는 것은 남은 칸(양식의 안내 글과 미룬 칸)뿐이다. 다시 부르면 남은 칸만 묻고 적힌 내용은 묻지도 고치지도 않는다. 적힌 내용을 고치는 일, 코드가 바뀌어 낡은 문서를 찾는 일, 새 ADR 항목을 더하는 일은 이 스킬의 일이 아니다. 양식에서 오지 않은 문서(문서 지도에 다른 경로로 적힌 문서, 폴더로 된 문서)는 건드리지 않고 보고에 적는다. 읽을 목록은 스킬 본문에 고정하고(UI 프로젝트에서는 토큰 파일을 더한다) 스캔을 다른 에이전트에게 맡기지 않는다. 커밋도 스테이징도 하지 않는다. 스킬 본문을 쓰면서 확인받지 않고 더한 다섯 가지는 2026-10-08에 확인받아 그대로 둔다: 읽을 것이 없는 칸은 질문으로 얻는다, ADR 후보가 없으면 후보를 고르는 물음을 건너뛴다, DESIGN의 `components`는 양식의 키대로 묻는다, 토큰 규칙의 세부와 tailwind 설정 파일의 대응(ADR-016).
- **이유**: {확인 필요}
- **트레이드오프**: 적힌 내용을 고치는 일, 낡은 문서를 찾는 일, 새 ADR 항목을 더하는 일을 맡는 단계가 아직 없다. 다음 단계의 질문 라운드에서 정한다. 스캔을 다른 에이전트에게 맡길지는 4단계에서 다시 본다. 이 레포의 2단계 결정은 이 문서에 손으로 더했다.

### ADR-013: 적힌 사실은 읽어서 적고, 해석은 확인받고, 의도는 묻는다
- **원장**: 41, 43, 44, 55, 56, 57, 63
- **결정**: 칸에 적을 내용을 셋으로 나눈다. 적힌 사실(파일에 그대로 적혀 있는 것)은 출처 경로를 괄호로 붙여 적는다. 해석(파일을 읽고 정리한 것)은 절 단위로 묶어 보여 주고 사용자가 확인한 것만 남긴다. 의도(어디에도 적혀 있지 않은 것)는 질문으로만 얻는다. 추천안은 저장소에 근거가 있을 때만 붙이고 근거 경로를 적는다. 답은 뜻을 바꾸지 않는 범위에서 문서 문체로 다듬고, 답에 없는 내용은 더하지 않는다. 사용자가 미룬 칸은 "확인 필요" 표시 하나로 적고 모름과 미정을 구분하지 않는다. 양식의 안내 글이 남아 있으면 끝나지 않은 것이다. 목록 칸의 개수는 답에 맞추고, 없다고 답한 칸은 "없음"으로 적는다.
- **이유**: 채우는 방식은 1단계에서 정해 두었다: 스캔과 질문 라운드로 채우고 추측으로 적지 않는다(ADR-009). 맥락 문서를 추측으로 채우면 틀린 내용이 다음 작업의 근거가 된다(context 스킬 본문의 "막는 실패").
- **트레이드오프**: {확인 필요}

### ADR-014: 문서마다 질문, 초안, 승인, 쓰기 순서로 한다
- **원장**: 42, 53, 68, 70, 71
- **결정**: 문서 하나마다 질문 → 초안 → 승인 → 쓰기 순서로 한다. 의도를 묻는 질문은 한 번에 하나만 내고, 고를 수 있는 답은 선택지로 낸다. 초안에서 고칠 곳을 말하면 고쳐서 다시 보여 주고, 승인받기 전에는 파일에 쓰지 않는다. 요청에 이미 답이 적혀 있는 물음은 다시 묻지 않는다. 도중에 그만하면 그 문서는 답한 칸까지 초안을 보여 주고 승인받아 쓰고, 묻지 않은 칸은 양식의 안내 글 그대로 둔다.
- **이유**: 의도를 신중하게 전달하고 파악하게 하고, 정확하게 기록하게 하기 위해서다.
- **트레이드오프**: 없음

### ADR-015: 기술 스택과 ADR 후보의 범위를 스킬 본문에 고정한다
- **원장**: 54, 91
- **결정**: 기술 스택은 빌드 매니페스트에 적힌 것만 적고 줄마다 그 매니페스트의 경로를 출처로 붙인다. 첫 줄은 언어와 런타임이고, 그 아래에 의존성을 적힌 순서대로 한 줄에 하나씩 이름과 버전 그대로 적는다. 테스트용·개발용으로 선언된 의존성, 빌드 플러그인, 매니페스트 밖에서 읽은 것(패키지 매니저, DB, 배포처)은 적지 않는다. ADR 후보는 다섯 범주(언어와 런타임, 프레임워크, 저장소(DB), 외부 서비스, 빌드·배포 방식)에서만 뽑고, 이 밖에 적어 둘 결정이 있는지 한 번 묻는다.
- **이유**: 기술 스택의 규칙은 2026-10-06의 실행에서 나왔다. 같은 프로젝트(badak-next-app)의 기술 스택이 Claude Code에서는 8줄에 매니페스트 밖에서 읽은 것(DB 없음, 배포처, 패키지 매니저)이 섞였고, Codex에서는 7줄에 묶는 방식이 달랐다. ADR 후보를 다섯 범주로 둔 이유는 정확히, 최소한의 필요한 정보만을 기록하기 위해서다.
- **트레이드오프**: 의존성이 목록으로 적히지 않은 매니페스트에서는 줄 수와 순서가 이 규칙만으로 정해지지 않는다. excel-viewer의 `build.gradle.kts`에서 `intellijPlatform` 블록의 조건문으로 된 선언은 풀어서 한 줄로 적혔고 `pluginVerifier()`는 적히지 않았다. `package.json`처럼 의존성이 목록인 매니페스트에서는 그대로 정해졌다.

### ADR-016: DESIGN의 토큰은 코드의 이름과 값을 그대로 옮긴다
- **원장**: 62, 73, 77, 78, 79, 80, 81, 82, 83, 84, 85, 93
- **결정**: 토큰 파일(CSS 변수, `@theme`, tailwind 설정)에 적힌 이름과 값을 DESIGN.md 규격의 네 범주(`colors`, `typography`, `rounded`, `spacing`)에 그대로 옮긴다. 양식의 예시 키는 쓰지 않고, 토큰이 코드에 없으면 양식의 키대로 하나씩 묻는다. 토큰 이름은 변수 이름에서 앞의 `--`와 범주 접두어를 뗀 것이다(`--color-primary`는 `colors.primary`). `typography`는 변수 하나를 속성 하나로 옮기고, 뗀 이름이 같은 변수는 한 토큰에 모은다. `--text-X--line-height` 꼴도 같은 토큰의 속성이다. 양식의 레벨은 만들지 않는다. 값은 적힌 그대로 옮긴다. `var(--이름)` 하나뿐인 값은 따라가서 끝에 적힌 값을 옮기고, `calc(…)` 같은 식은 계산하지 않고, 따라간 끝에 값이 없으면 질문한다. 접두어가 없는 변수는 값이 색이면 `colors`에 넣고 아니면 범주를 묻는다. `:root`와 `@theme`의 기본 값만 옮기고, 다른 선택자(`.dark` 등) 안의 값과 네 범주 밖의 토큰(그림자, 중단점 등)은 옮기지 않고 보고에 적는다. 토큰 파일은 있는데 변수가 없는 범주는 범주마다 한 번 묻고, 없다고 하면 앞머리에서 빼고 `omitted`에 적는다. 토큰을 코드에서 옮긴 프로젝트의 본문 Colors·Typography 절은 절마다 질문 하나로 묻고, 답에 나온 토큰만 토큰 이름을 항목 이름으로 써서 적는다. 앞머리는 YAML이라 출처를 주석으로 적고, 주석은 토큰 파일에서 옮긴 범주에만 붙인다. 토큰 참조(범주와 이름을 점으로 이어 중괄호로 감싼 것)는 남은 칸으로 세지 않는다(원장에 번호가 없다. 설계하면서 더했고 따로 확인받지 않았다). 규칙의 전문은 context 스킬 본문의 "DESIGN의 토큰" 절에 있다.
- **이유**: 출처 주석을 옮긴 범주에만 붙이는 것은 출처를 스캔으로 적은 사실에만 붙이는 규칙(ADR-013)과 같은 방향이다. 토큰 참조를 남은 칸으로 세지 않는 것은, 세면 다 채운 `docs/DESIGN.md`도 토큰 참조가 남아 있어 끝나지 않은 문서로 보이기 때문이다. 이름과 값을 그대로 옮기는 이유는 무엇이 필요한지 최소한만 전달할 수 있으면 되기 때문이다.
- **트레이드오프**: `calc(…)` 식을 그대로 옮기면 DESIGN.md 규격의 린터가 `rounded`와 `typography`의 치수에서 오류로 본다. 이것을 받아들였다. 다른 선택자 안의 값(다크 모드 등)과 네 범주 밖의 토큰은 문서에 옮겨지지 않는다. tailwind 설정 파일의 값을 옮기는 대응은 시험한 두 프로젝트에 그 파일이 없어 판정으로 확인되지 않았다.

### ADR-019: 2단계의 완성 판정과 시험 폴더

- **결정**: 시험은 헤드리스 실행에 답을 미리 주는 방식이 기본이고 답은 경우마다 파일 하나로 둔다. 여러 턴을 주고받는 시험은 한 경우(빈 폴더의 PRD)만 한다. ADR-010의 `/tmp/plate-rail-test`를 바꾼다. 이 레포 ADR의 미룬 칸은 완성 판정의 마지막에 context 스킬을 실제로 돌려 채운다. 그 판정은 `claude --plugin-dir plugins/plate`로 연 새 세션에서 `/plate:context`를 불러서 한다.
- **이유**: 시험 폴더를 옮긴 것은 `/tmp/plate-rail-test`가 2026-10-08의 재부팅으로 사라졌기 때문이다. 시험 폴더, 실행 결과, 답 파일, 판정 도구, 로그가 모두 없어졌고 판정 도구와 답 파일은 세션 기록에서 되살렸다. badak-next-app의 변형을 쓰는 것은 루트에 실제 디자인 문서 `DESIGN.md`가 있어서 그대로 셋업하면 같은 역할 문서로 판정되고 `docs/DESIGN.md` 양식이 생기지 않기 때문이다. 답을 미리 주는 방식을 기본으로 한 이유와 해석 칸을 기계 기준에서 뺀 이유는, 앞의 것은 없음이고 뒤의 것은 잘못된 작업의 기록이기 때문이다.
- **트레이드오프**: 해석 칸은 기계로 확인하지 않는다. 적힌 내용을 답 파일과 나란히 보여 주기만 한다. 2026-10-06에 통과한 판정은 2026-10-08에 고친 본문으로 다시 돌리지 않았다. finsight 원본은 그 뒤로 바뀌어서 복제본을 2026-10-06의 커밋 `bdff8d9`로 맞춰 쓴다.

### ADR-021: 계획은 스킬 하나가 맡고 문서는 `plan.md` 하나다
- **원장**: 101, 109, 110, 127, 135, 142
- **결정**: 계획은 스킬 하나(`plate:plan`)가 맡고 문서는 `plan.md` 하나다(다른 안은 "스킬 하나, 승인 두 번", "스킬 둘, 문서 둘(`spec.md`와 `plan.md`)"이었다). 작은 작업도 같은 양식으로 `plan.md`를 쓰고 phase가 하나다. 요청이 분명하면 질문 없이 초안을 보여 준다(다른 안은 "짧은 양식을 따로 둔다", "작은 작업은 계획을 건너뛴다"였다). 3단계에서는 부르면 동작하는 스킬만 만든다. 계획 없이 코드를 고치는 것을 막는 장치(`AGENTS.md`의 규칙, 훅)는 5단계 라운드에서 정하고, setup 스킬을 고치지 않는다. 승인해서 커밋한 계획을 고치는 길은 4단계 라운드에서 정하고, 3단계의 계획 스킬은 새 계획만 쓴다(다른 안은 "계획 스킬이 지금 맡는다", "고치지 않고 새 작업으로 만든다"였다). 스킬의 끝은 보고다(쓴 위치, 커밋, phase의 수, 끝나지 않은 다른 작업). 실행으로 이어갈지 묻는 물음은 4단계에서 더한다. 본문은 setup, context와 같은 방식으로 쓴다(한국어, 도구 이름 대신 동작, 양식은 본문 안).
- **이유**: {확인 필요}
- **트레이드오프**: 계획 없이 코드를 고치는 것을 막는 장치가 아직 없다. 승인해서 커밋한 계획을 고치는 길도 아직 없다. 앞의 것은 5단계, 뒤의 것은 4단계의 질문 라운드에서 정한다.

### ADR-022: phase마다 회고하고 통과한 phase는 지운다
- **원장**: 102, 103, 104, 105, 106, 144, 146
- **결정**: phase마다 TODO 목록을 둔다. 한 phase의 TODO가 모두 끝나면 회고할지 묻고, 회고에서 하네스의 문제점과 그 phase의 코드를 점검하고 테스트를 돌린다. 문제점이 잡히고 테스트가 통과하면 그 phase를 지운다. 사용자가 3단계 질문 라운드에서 더한 아이디어다. 사용자의 말: "task내의 각 페이즈별로 TODO를 모두 완료하면 회고할지 질문하고 회고를 통해서 하네스의 문제점부터 마친 작업내의 코드들을 점검하고 테스트코드 돌려보는 단계를 두는거지 문제점 잡히고 테스트 통과하면 해당 phase는 삭제하는거야". 지우는 것은 `plan.md`의 그 phase 절과 그 phase의 `phase-N.md` 둘이다(추천안은 "`plan.md`의 절만 지운다"였다. 다른 안은 "`phase-N.md`만", "지우지 않고 완료 표시"였다). phase가 모두 지워지면 작업 전체를 완료 조건에 대어 보는 검증을 한 번 하고 `verify.md`를 남긴다(다른 안은 "마지막 phase가 전체 검증", "회고가 검증을 대신한다"였다). 검증까지 통과한 작업의 폴더에는 머리만 남은 `plan.md`와 `verify.md`가 남는다(다른 안은 "`verify.md`만", "폴더째 지운다"였다). 끝나지 않은 작업은 `plan.md`에 `## Phase`로 시작하는 절이 남아 있는 작업 폴더다. 이 레포의 단계 기록(`docs/tasks/001-setup`부터 `003-plan`까지)은 그런 절이 없어 해당하지 않는다. ADR-003의 "실행 안쪽은 계획이 정한 N개 phase다"와 ADR-006의 "작업 기록은 git에 커밋해 보존한다"를 바꾼다. 바깥 단계(계획 → 실행 → 검증)는 ADR-003 그대로이고 실행 안쪽에 회고가 들어간다. setup이 넣는 문서 지도 구간의 글은 그대로 둔다. 3단계에서는 이 모양까지만 정하고 회고의 절차는 4, 5단계 라운드로 넘긴다(다른 안은 "`plan.md`에 걸리는 것만 정한다", "회고까지 3단계에서 만든다"였다).
- **이유**: {확인 필요}
- **트레이드오프**: 지난 phase의 근거는 git 이력에만 남는다. 그래서 지우기 전에 한 번은 커밋돼 있어야 한다. 회고의 절차(누가 점검하는지, 하네스의 문제점을 어디에 적는지, 회고를 건너뛰면 그 phase가 어떻게 되는지)는 아직 없다.

### ADR-024: 계획 스킬은 문서 지도를 따라 읽고 셋업과 맥락 채우기를 이름으로 부른다
- **원장**: 111, 112, 113, 114, 143
- **결정**: 셋업이 안 된 프로젝트에서 계획 스킬을 부르면 셋업을 할지 묻고, 승인하면 setup 스킬을 이름으로 불러 끝까지 따른 뒤 계획으로 돌아온다. 거절하면 아무것도 쓰지 않는다. 계획 스킬이 setup을 불렀으면 남은 칸을 채울지는 setup의 끝 물음이 묻는다. 계획 스킬은 그 물음을 다시 하지 않고 setup 스킬도 고치지 않는다. 맥락 문서에 안내 글이 남아 있으면 먼저 채울지 묻는다. 승인하면 context 스킬을 이름으로 부르고, 거절하면 적혀 있는 내용만 근거로 계획한다(다른 안은 "채워야 계획한다", "그냥 계획한다"였다). 확인 필요 표시만 남은 문서는 묻지 않는다. 문서 지도에 적힌 맥락 문서를 모두 읽고, 그다음 요청에 걸리는 코드만 읽는다. 읽을 문서를 스킬 본문에 고정하지 않는다(다른 안은 "본문에 목록을 고정한다", "'읽을 때' 칸으로 골라 읽는다"였다). 지도에 행이 더해지면 스킬을 고치지 않아도 그 문서를 읽는다. `docs/tasks/`의 지난 작업은 읽지 않고 번호만 센다. 요청에 걸리는 코드는 메인이 직접 읽는다. 에이전트에게 맡길지는 4단계에서 다시 본다.

### ADR-025: 작업 폴더의 번호와 이름, 커밋, 브랜치
- **원장**: 115, 116, 117, 145
- **결정**: 작업 폴더의 번호는 `docs/tasks/`의 폴더 가운데 가장 큰 번호의 다음이고 없으면 001이다. 이름은 스킬이 영어 소문자 낱말 1~3개로 짓고, 초안의 첫머리에 쓸 위치를 보여 주어 초안과 함께 승인받는다(다른 안은 "이름을 따로 묻는다", "번호만 쓴다"였다). 계획 스킬은 승인받아 쓴 `plan.md` 하나만 커밋하고 다른 변경은 스테이징하지 않는다(다른 안은 "실행 단계가 시작할 때 커밋한다", "커밋할지 묻는다"였다). 커밋 메시지는 `plan: NNN-slug`로 고정한다. git 레포가 아니면 커밋하지 않고 보고에 적는다. 계획 스킬은 브랜치를 건드리지 않고 지금 있는 브랜치에 커밋한다(다른 안은 "작업마다 브랜치를 만든다", "기본 브랜치일 때만 묻는다"였다).

### ADR-026: 끝나지 않은 작업이 있으면 새 작업의 실행은 worktree에서 한다
- **원장**: 128, 129
- **결정**: 끝나지 않은 작업이 있는데 새 요청으로 부르면 계획 스킬은 초안의 첫머리에 알리고 새 작업을 만든다(다른 안은 "새로 만들지 묻는다", "막는다"였다). 그 새 작업은 worktree에서 진행한다. worktree는 사용자가 더했다. 사용자의 말: "1번으로 하되 worktree내에서 진행". 계획 스킬은 지금 자리에 `plan.md`를 쓰고 커밋한다. 계획부터 worktree 안에서 쓰면 그 번호가 원래 자리에서 보이지 않아 다음 작업의 번호가 겹치기 때문이다(다른 안은 "계획부터 worktree 안에서", "안내하고 멈춘다"였다). worktree는 실행이 시작될 때 만들고, 위치와 브랜치 이름과 합치는 일은 4단계 라운드에서 정한다. 계획 스킬은 보고에 "worktree에서 실행한다"고 적기만 한다.
- **이유**: {확인 필요}
- **트레이드오프**: worktree의 위치, 브랜치 이름, 합치는 일이 정해지기 전이라 계획 스킬은 보고에 적기만 한다. 계획 스킬이 브랜치를 건드리지 않는다는 결정(ADR-025)에는 실행이 worktree를 만드는 경우에 예외가 붙는다. 끝나지 않은 작업이 쌓이는 것을 막을지는 5단계 라운드에서 정한다.

### ADR-027: `plan.md`의 머리, 조건, phase, TODO
- **원장**: 118, 119, 120, 121, 122, 136, 137, 138, 139, 140
- **결정**: `plan.md`의 머리에는 절 다섯을 둔다: 요청, 목표, 범위 밖, 완료 조건, 결정. 없는 절은 "없음"으로 적는다(다른 안은 "목표, 완료 조건만", "가정과 위험을 더한다"였다). 요청 절에는 스킬을 부를 때의 글을 그대로 옮긴다. 질문의 답은 결정에 적고, 사용자가 말하지 않은 이유는 지어 적지 않는다. 완료 조건과 통과 조건은 조건마다 확인 방법을 붙인다. 확인은 돌릴 명령과 기대 결과를 우선하고, 명령으로 볼 수 없는 것만 "무엇을 어디서 본다"로 적는다. 확인 방법을 적을 수 없는 조건은 조건으로 적지 않는다(다른 안은 "명령으로 확인할 수 있는 것만", "문장 목록만"이었다). 완료 조건마다 그것을 이루는 phase가 적어도 하나 있다. phase 절에는 넷을 적는다: 목표, 읽을 것, TODO, 통과 조건(다른 안은 "읽을 것을 두지 않는다", "고칠 파일 목록을 더한다"였다). phase 절의 제목은 `## Phase N: 이름`이고, 앞 phase가 지워져도 번호를 다시 매기지 않는다. 뒤 phase가 앞 phase의 결과를 쓰면 그 위치를 읽을 것에 경로로 적는다. phase를 나누는 기준은 셋이다: 따로 확인할 수 있는 결과 하나를 낸다, 머리와 그 절만 읽고 할 수 있다, 앞 phase가 통과한 상태에서 시작한다. 숫자 상한은 두지 않고, 판정에서 phase가 너무 커지는 것이 보이면 그때 더한다(다른 안은 "TODO 7개 상한을 더한다", "정해진 층으로 나눈다"였다). TODO 항목은 무엇이 어떻게 바뀌는지를 결과로 적고, 고칠 파일을 알면 끝에 경로를 붙인다. 코드는 적지 않는다(다른 안은 "코드 수준까지 적는다", "제목만 적는다"였다). 통과 조건의 확인이 아직 없는 테스트를 가리키면 그 테스트를 쓰는 일을 같은 phase의 TODO에 넣는다. 양식의 전문은 plan 스킬 본문의 "`plan.md`의 양식"과 "적는 규칙" 절에 있다.
- **이유**: {확인 필요}
- **트레이드오프**: {확인 필요}

### ADR-028: 요청이 맥락 문서와 어긋나면 묻고, 맥락 문서를 고치는 일은 계획이 TODO로 넣는다
- **원장**: 125, 126
- **결정**: 요청이 맥락 문서와 어긋나면 계획 스킬은 어긋난 곳을 보여 주고 셋 중에 고르게 한다: 요청을 고친다, 문서를 바꾸기로 하고 진행한다, 그만둔다. 고른 것은 결정에 적는다(다른 안은 "계획하지 않고 멈춘다", "알리기만 하고 계획한다"였다). 작업 때문에 맥락 문서를 고쳐야 하면 계획이 그 일을 해당 phase의 TODO로 넣는다. 고치는 것은 실행 단계다(다른 안은 "검증 단계가 끝에 맡는다", "둘 다 한다"였다). 2단계에서 미룬 물음 둘(적힌 내용을 고치는 일과 새 ADR 항목을 더하는 일을 어느 단계가 맡는가, ADR-012)의 답이다.
- **이유**: {확인 필요}
- **트레이드오프**: 계획이 TODO로 넣지 못한 문서 고치기가 있을 수 있다. 검증이 맥락 문서의 빠뜨림을 한 번 더 볼지는 5단계 라운드에서 정한다. 코드가 바뀌어 낡은 문서를 찾는 일(ADR-012)은 3단계에서 정하지 않았다.

### ADR-029: 질문은 추측 없이 쓸 수 있을 때까지만 하고 초안은 한 번에 승인받는다

### ADR-030: 판정에서 본 것대로 계획 스킬의 규칙을 고친다
- **원장**: 148, 149, 150, 151, 152, 153
- **결정**: 2026-10-08의 완성 판정에서 본 것대로 계획 스킬의 규칙 다섯을 고치거나 더했다. 초안에 대한 답이 승인인지 분명하지 않으면 쓰지 않고 승인인지 다시 묻는다(다른 안은 "지금처럼 승인으로 받고 보고에 알린다"였다). 계획 스킬은 프로젝트 밖에도 만들지 않고, 계획에 적는 확인 명령을 미리 돌려 보지 않고 적는다(다른 안은 "임시 폴더에서만 허용하고 끝나면 지운다", "지금처럼 둔다"였다). 초안을 답글로 보여 준 뒤에 받은 답만 승인이다. 요청과 함께 미리 받은 승인은 승인으로 치지 않고, 초안을 적은 답글에서 멈춰 답을 기다린다. 물음의 답을 미리 주는 것은 그대로 통한다(ADR-029). 이 규칙은 처음에 "승인을 미리 받았어도 초안을 보여 준 뒤에 쓴다"로 적었다가 바꾼 것이다(다른 안은 "초안을 적는 일을 번호가 다른 단계로 뗀다", "되돌리고 알려진 한계로 적는다"였다). TODO를 결과로 적는 규칙(ADR-027)에 예를 한 줄 붙인다. 예는 판정의 요청에 없는 낱말로 적는다(다른 안은 "지금처럼 두고 4단계에서 다시 본다"였다). 사용자에게 묻지 않고 추천안으로 정한 결정은 끝에 "(추천안으로 정함)"을 붙인다. 이것과 함께 낸 다른 안 "기기 상태를 근거로 삼지 않는다", "고른 것은 결정에 적는다", "고치지 않는다"는 고르지 않았다.
- **이유**: 모두 판정의 실행에서 본 것이다. 승인인지 다시 묻게 한 것은 여러 턴 판정에서 스킬이 "추천안으로 한다."를 승인으로 받아 썼기 때문이다. 프로젝트 밖에 만들지 않게 한 것은 스킬이 확인 명령을 미리 돌려 보려고 `/tmp`에 임시 git 레포를 만들려 했기 때문이다. 미리 받은 승인을 승인으로 치지 않게 한 것은 승인을 미리 주면 초안을 보여 주지 않고 바로 썼기 때문이다. 처음 적은 글로는 같은 판정을 아홉 번 돌려 한 번만 초안을 보여 줬다. 레포 밖 복사본에서 두 후보를 세 번씩 시험했더니 초안을 적는 일을 번호가 다른 단계로 뗀 것은 두 번, 미리 준 승인을 승인으로 치지 않는 것은 세 번 초안을 적었다. TODO의 예를 붙인 것은 한 판정에서 TODO를 결과가 아니라 할 일로 적었기 때문이다. 추천안 표시를 붙인 것은 두 판정의 결정에 표시가 없어 사용자가 고른 것과 스킬이 고른 것이 갈리지 않았기 때문이다.
- **트레이드오프**: 미리 적은 승인이 통하지 않는다. 그래서 헤드리스 판정은 초안이 나온 뒤 같은 세션의 다음 턴으로 승인을 보낸다. 이 규칙을 넣기 전에 한 턴으로 돌린 여섯 경우(큰 요청, 다시 부르기, ADR 항목이 생기는 요청, 맥락을 채우지 않은 폴더, 셋업하지 않은 폴더, git 레포가 아닌 폴더)는 고친 본문으로 다시 돌리지 않았다. 판정에서 보고도 고치지 않기로 한 것이 넷 있다: 기기 상태를 살펴 결정의 이유로 적는다, 묻지 않고 맥락 문서에서 골라 정한 것이 결정에 남지 않는다, ADR 항목의 이유와 트레이드오프를 추천안으로 적는다, 뼈대를 첫 기능과 한 phase에 묶기도 하고 따로 떼기도 한다.

### ADR-031: 3단계의 완성 판정
- **원장**: 130, 131, 132, 134, 147
- **결정**: 완성 판정은 빈 폴더로만 한다(추천안은 "2단계의 시험 폴더(`ctx-ev`, `ctx-badak`)를 이어 쓴다"였다). 판정은 열 경우로 한다: 작은 요청, 그 결과의 커밋, 큰 요청, 다시 부르기, 맥락 문서와 어긋나는 요청, ADR 항목이 생기는 요청, 맥락을 채우지 않은 폴더, 셋업하지 않은 폴더, 여러 턴, git 레포가 아닌 폴더(다른 안은 "형식에 걸리는 것만"이었다). 판정 방식은 2단계와 같다(ADR-019).
