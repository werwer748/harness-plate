# PRD: harness-plate

## 목표
에이전트가 어떤 도구로 일하든 같은 규격(단계 순서, 기록 위치와 형식, 통과 조건)으로 작업하게 하는 하네스 "레일"을 만든다(ADR-004). 막을 실패는 둘이다: 긴 세션의 컨텍스트 팽창, 검증 없는 완료 선언. 막는 장치는 규칙 구간이 기본이고 Claude Code 훅이 테스트 먼저와 코드 파일(`.md`가 아닌 파일)의 계획 없는 편집, 에이전트가 기본 브랜치에 하는 푸시를 더 막는다. `.md` 파일(결과물인 마크다운도 든다)의 계획 없는 편집은 훅이 막지 않고 규칙 구간이 막는다(ADR-027). 규칙 구간은 셋업이 `AGENTS.md`에 넣는 작업 규칙(계획부터 세우고, task는 회고가 통과해야 끝나고, tasks는 끝의 코드 평가와 하네스 eval을 담은 보고가 나와야 끝난다)이고, 스킬 본문의 절차와 함께 막는다.

## 사용자
개인용이다(가정으로 둔 것). 프로젝트에 플러그인으로 설치하고, 그 프로젝트의 모든 작업을 하네스의 파이프라인으로 진행한다(ADR-005).

## 핵심 기능
단계별로 하나씩 완성한다.
1. 셋업: 프로젝트에 하네스 문서의 위치 기준을 세운다. 1단계에서 만들었다.
2. 맥락: 스캔과 질문 라운드로 맥락 문서를 채운다. 추측으로 적지 않는다. 2단계에서 만들었다.
3. 계획: 요청 하나를 tasks로 계획해 tasks 머리(`docs/tasks/plan.md`)와 task 폴더마다의 머리(`plan.md`)와 phase마다의 `phase-N.md`로 남긴다. 추측으로 정하지 않고 묻는다. 3단계에서 만들었고 `010-tasks-cycle`에서 tasks > task > phase로 나눴다.
4. 실행: 계획이 정한 phase마다 새 컨텍스트의 에이전트가 수행해 그 phase의 `phase-N.md`에 기록을 덧붙이고, 다른 새 에이전트가 확인한다. 확인이 통과한 phase의 파일은 `done-phase-N.md`로 이름을 바꾼다. 4단계에서 만들었고 `010-tasks-cycle`에서 확인을 수행과 나눴다.
5. task 회고: task의 phase가 모두 통과하면 새 컨텍스트의 에이전트가 task 전체를 완료 조건과 맥락 문서에 대어 보고 `retro.md`에 기록을 남기고, tasks 끝에 볼 것을 `docs/tasks/FRICTION.md`에 적는다. 회고가 통과하지 않은 task는 끝나지 않는다. 5단계의 검증을 `010-tasks-cycle`에서 회고와 합쳤다.
6. TDD와 엣지케이스: 테스트가 있는 프로젝트에서 테스트 먼저인 phase는 실패하는 테스트 → 구현 → 통과 순서로 수행하고 두 출력을 기록에 남긴다. plan은 phase마다 테스트 먼저를 적고 엣지케이스를 논의할지 묻는다. Claude Code 훅이 코드 파일(`.md`가 아닌 파일)의 테스트 먼저와 계획 없는 편집을 막고, `.md` 파일(결과물인 마크다운도 든다)은 막지 않는다(ADR-027). 6단계에서 만들었다.
7. 자동 사이클: run이 시작할 때 첫 에이전트를 띄우기 전에 plan 모드가 켜져 있거나 쓰기가 막힐 권한 모드면 알리고 바꿀지 묻고(확인할 수 없으면 그렇다고 적고 잇는다), 실행 방식을 묻는다. task 하나씩은 task 회고가 끝날 때마다 묻고, tasks 일괄은 묻지 않고 모든 task를 처리하며 회고에서 나온 문제는 고칠 phase를 더해 고친다. 어느 방식이든 막힘, 계획이 틀림(회고의 문제를 고치려면 계획의 목표나 완료 조건을 바꾸거나 좁혀야 할 때와, 고칠 파일이 완료 조건이 돌린 시각이나 본문 해시로 보는 파일인데 고친 뒤 그 확인을 다시 참으로 둘 길이 계획에 없을 때와, 마지막 회고 절에 고칠 쪽이 계획인 문제(결정이나 완료 조건이 정한 동작이 목표를 해친다)가 있을 때도 든다), 같은 확인이나 회고의 세 번 실패, 띄운 에이전트가 같은 자리에서 연달아 세 번째로 결과 없이 돌아온 것(남겨야 할 기록 절, 확인 절, 회고 절, `review.md`, `eval.md`가 없다. 그 전에는 같은 자리를 다시 띄우고 `RUNLOG.md`에 `다시 띄움: 결과 없음`을 남기며, `review.md`가 없으면 하네스 eval로 가지 않는다)에서는 멈추고 원인과 해결책을 논의한다. 멈춘 자리에서 계획을 고치면 고칠 때마다 결정에 줄 하나를 더하고, 커밋 전에 그 줄이 있는지 본다. 띄운 에이전트마다, 물은 자리마다 `docs/tasks/RUNLOG.md`에 한 줄을 남기고, 회고와 코드 평가와 하네스 eval의 에이전트가 돌아오면 그 줄을 그 자리에서 `RUNLOG.md`만 넣는 커밋으로 넣는다. `010-tasks-cycle`에서 만들었다.
8. 평가: 모든 task가 끝나면 새 에이전트가 tasks에서 바뀐 코드를 다섯 범주(신뢰성, 보안, 유지보수성, 테스트 적절성, 기능 적합성)로, 다른 새 에이전트가 하네스를 여섯 기준(결과 성공, 일관성, 효율, 규칙 준수, 사람 개입률, 실패 양상)으로 A~E로 매긴다. 코드의 통과선은 Sonar way다. run이 전체 보고와 함께 고칠지 한 번에 묻고, 고치면 고침 task를 더해 같은 레일로 돌리고, 문턱을 넘은 plate 자체의 고칠 거리만 GitHub 이슈로 올리고(ADR-025), 미룬 소스 문제와 문턱을 넘지 않은 하네스 고칠 거리와 감수한 것은 `docs/BACKLOG.md`에 적는다. 세 기준(피해, 일반성, 고침의 꼴)을 넘지 않은 하네스 고칠 거리는 "eval에만"으로 eval.md에만 남고, 사용자가 고치거나 올리자고 하지 않는 한 고침 task, 이슈, BACKLOG, 감수 어디에도 두지 않는다. 사용자가 그러자고 하면 이 프로젝트만의 것은 고침 task로, plate 자체의 것은 이슈로 옮기고, 다시 빼면 eval에만으로 돌아간다. 소스 문제가 없고 하네스 고칠 거리가 모두 eval에만이나 감수이면 run은 고칠 것이 없다고 적고 묻지 않는다(ADR-026). tasks 끝의 평가는 `010-tasks-cycle`에서 만들었다. `docs/tasks/`를 비운 뒤 origin이 GitHub이면 run이 tasks 브랜치를 푸시해 기본 브랜치로 가는 PR을 열지 묻고(본문에 tasks의 요청과 목표, 전체 보고), plate의 CI 워크플로가 있으면 CI 에이전트가 PR을 평가해 판정 스크립트가 자동 머지, 머지 요청, 닫기 가운데 하나를 고르며(워크플로를 바꾼 PR은 판정이 머지 요청으로 내려 사람이 머지한다. setup은 CODEOWNERS를 쓰고 ruleset 거는 법을 알린다, ADR-023), 없으면 로컬의 코드 평가를 PR 댓글로 단다. origin이 GitHub이 아니거나 없으면 기본 브랜치로 합칠지 묻는다. PR과 합침은 늘 `tasks/<이름>`을 다루므로 run은 기본 브랜치도 `tasks/<이름>`도 아닌 브랜치에서 시작하면 바꿀지 묻고, 비운 뒤 묻기 전에 세션이 끊겨 다시 부르면 `tasks/<이름>`의 마지막 커밋이 `<이름>: 비움`일 때 PR·합침으로 간다. cleanup 브랜치에서 계획해 tasks 머리에 `**보낼 곳**:` 줄이 있는 tasks는, 비운 뒤 `tasks/<이름>`을 보낼 곳에 로컬로 합칠지 먼저 묻고(squash하지 않고 `<이름>: 보낼 곳으로 합침` 합침 커밋을 만들고, 충돌하면 되돌리고, 합치면 `tasks/<이름>`을 지운다), 합친 뒤 `tasks/<이름>` 대신 보낼 곳을 기본 브랜치로 보내는 PR이나 합침을 묻는다. 보낼 곳이 로컬에 없으면 합치지도 PR을 열지도 않고 알린 뒤 보고로 끝나고, 다시 부르면 비운 뒤의 재개로 보낼 곳으로 합치는 자리부터 잇는다. 보낼 곳으로 합친 뒤 끊기면 보낼 곳 브랜치의 마지막 커밋이 `<이름>: 보낼 곳으로 합침`일 때 PR·합침으로 간다. PR과 CI는 011에서 만들었다.
9. 정리·리팩터링: 코드베이스를 정기·비정기로 살펴 정리하는 스킬을 둔다. 사용자가 cleanup 스킬을 부르면 여섯 기준(보안, 성능, 신뢰성, 유지보수성, 기능 적합성, 기존 작업 정합성)마다 새 에이전트가 따로 살피고 서로의 발견을 교차 검토해 `docs/cleanup/YYYY-MM-DD.md`(같은 날의 보고서가 작업 트리나 아직 합쳐지지 않은 로컬 cleanup 브랜치에 있으면 번호를 붙인다)에 보고서를 쓰고, 발견을 tasks로 만들지 물어 동의하면 고른 발견을 plan에 넘긴다. 어느 브랜치에서 부르든 보고서를 쓰기 전에 그 HEAD에서 `cleanup/<보고서 이름>` 브랜치를 묻지 않고 만들어(같은 이름이 있으면 번호를 붙인다) 보고서와 미룸을 거기에만 커밋한다. 고른 발견이 없으면 origin이 GitHub일 때 그 브랜치를 푸시해 기본 브랜치로 가는 PR(본문은 보고서 파일)을 열지, 그 밖이면 기본 브랜치에 합칠지 묻는다. 코드를 고치지 않는다. cleanup 스킬로 만들었다.

9단계까지 만들어 1.0.0을 냈다.

## 범위 밖
- 파이프라인을 건너뛰는 예외 경로. 예외 없이 모든 작업이 파이프라인을 거친다.
- 옛 plate v0.3.0의 결정과 장치를 이어받는 것. 완전히 새로 시작한다.
- superpowers를 설치해 기대는 것. 기법만 가져온다(ADR-005).
- README, CHANGELOG 같은 일반 문서의 위치 관리. 위치 규칙은 하네스 기록에만 적용한다.
- 여러 파일로 나뉜 기존 문서를 하나로 합치는 것. 지도에 경로만 적는다.
- 검증 없는 종료를 막는 훅. v1.0 뒤에 한다.
- v1.0 전에 다른 도구(Codex, Grok Build)에서 같은 결과를 확인하는 것. 완성 판정은 Claude Code로만 하고, 다른 도구로 넓히는 일은 v1.0 뒤에 한다(ADR-018).
