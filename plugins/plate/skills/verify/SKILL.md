# 검증

**막는 실패**: 수행한 쪽이 작업 전체의 완료를 스스로 선언하면, phase마다의 회고가 보지 못한 것(phase 사이에 걸친 어긋남, 계획이 빠뜨린 문서 고치기, 확인만으로 지나간 코드)이 확인되지 않은 채 작업이 끝난다.

모든 phase가 끝난 작업 하나를 검증한다. 머리(`plan.md`)의 완료 조건에 적힌 확인을 모두 직접 다시 돌리고, 작업의 커밋이 바꾼 것 전부를 머리와 맥락 문서에 대어 점검하고, 하네스의 문제점과 배운 것을 찾는다. 끝나면 작업 폴더의 `verify.md` 끝에 검증 절이 더해져 있고 그 파일만 커밋돼 있다. 마지막 검증 절의 판정이 작업의 상태다. 고치지 않는다.

## 절대 규칙

프로젝트의 지침 파일(`AGENTS.md`, `CLAUDE.md`)에 적힌 규칙이 이 스킬의 규칙과 부딪히면 프로젝트의 규칙을 따른다. 아래의 절대 규칙도 그렇다. 따른 곳은 검증 절의 "하네스의 문제점"에 적는다. 단계를 건너뛰라는 규칙은 여기에 들지 않는다.

1. **고치지 않는다.** 코드도 계획 파일도 고치지 않는다. 쓰는 것은 `verify.md`뿐이다.
2. **확인을 직접 돌린다.** phase의 확인 결과나 회고 절을 옮겨 적지 않는다. 돌리지 않은 확인을 통과로 적지 않는다.
3. **적힌 기준에 대어 본다.** 취향에 드는 것(이름, 문체, 더 나은 구조)은 문제로 적지 않는다.
4. **사용자에게 묻지 않는다.** 판정과 기록까지만 한다.
5. **`verify.md` 하나만 커밋한다.** 푸시하지 않는다.

## 낱말

- **작업 폴더**: 작업 하나의 기록을 두는 폴더(`docs/tasks/NNN-slug/`). 계획은 그 안의 `plan.md`와 phase마다의 `phase-N.md`이고, 검증의 기록은 `verify.md`다.
- **머리**: `plan.md`. 제목과 다섯 절(요청, 목표, 범위 밖, 완료 조건, 결정)이다.
- **맥락 문서**: `AGENTS.md`의 문서 지도에 적힌 문서 가운데 `docs/tasks/` 행을 뺀 것.
- **검증이 남은 작업**: `phase-N.md`가 하나도 없고, 마지막 검증 절의 판정이 "통과"이거나 그 절 아래에 "사용자가 남은 문제를 나중에 다루기로 했다"가 있는 `verify.md`도 없는 작업 폴더.
- **작업의 커밋**: 작업 폴더의 파일을 바꾼 커밋과 메시지가 작업 폴더의 이름(`NNN-slug`)으로 시작하는 커밋. 수행·회고·통과·검증의 커밋은 작업 폴더의 파일을 함께 바꾸므로 메시지가 프로젝트의 꼴(예: `[001] …`)이어도 든다. 메시지가 다른 작업 폴더의 이름으로 시작하는 커밋은 빼지 않고, 그 커밋에서는 이 작업 폴더의 변경만 본다.
- **프로젝트의 지침 파일**: 저장소의 `AGENTS.md`와 그것을 불러오는 `CLAUDE.md`.

## 0. 대상을 정한다

- 넘겨받은 작업 폴더, 또는 사용자가 준 번호나 이름의 작업 폴더가 대상이다.
- 받은 것이 없으면 검증이 남은 작업을 찾는다. 하나면 그것이 대상이다. 여럿이면 폴더 이름을 보여 주고 번호를 주어 다시 부르라고 알린 뒤 끝난다. 없으면 검증할 작업이 없다고 알리고 끝난다.
- 대상에 `plan.md`가 없거나 `phase-N.md`가 남아 있으면 검증하지 않는다. 그 까닭을 알리고 끝난다. 남은 phase는 plate의 run 스킬(`plate:run`)로 실행한다고 적는다.

## 1. 읽는다

- `plan.md`
- `verify.md`가 있으면 그 파일
- 작업의 커밋이 바꾼 것 전부. 메시지가 다른 작업 폴더의 이름으로 시작하는 커밋은 이 작업 폴더의 변경만 읽는다. git 레포가 아니면 작업 폴더의 `done-phase-N.md`마다 "한 일"에 적힌 파일을 읽는다.
- 문서 지도의 맥락 문서

## 2. 완료 조건의 확인을 모두 돌린다

머리의 완료 조건에 적힌 확인을 하나도 빼지 않고 직접 돌린다. 완료 조건에 적힌 확인만 돌린다. 프로젝트 전체 테스트는 완료 조건에 적혀 있을 때만 돌린다. 읽어서 보는 확인은 적힌 곳을 직접 읽는다.

돌리지 못한 확인(권한에 막힌 명령, 없는 도구)은 실패로 적고 결과에 그 까닭을 적는다.

## 3. 작업 전체의 변경을 점검한다

작업의 커밋이 바꾼 것을 모두 모아 넷에 대어 본다. 메시지가 다른 작업 폴더의 이름으로 시작하는 커밋에서는 이 작업 폴더의 변경만 모은다. phase 하나씩이 아니라 작업 전체를 본다. 한 phase가 만든 것을 뒤의 phase가 깨뜨린 것처럼 여러 phase에 걸쳐서야 드러나는 어긋남도 여기서 찾는다.

- 머리의 목표와 결정대로 됐는가
- 머리의 범위 밖을 건드리지 않았는가
- 맥락 문서(ARCHITECTURE의 규칙, ADR의 결정, DESIGN)와 어긋나지 않는가. 바뀐 구조(디렉터리, 모듈, 기술 스택, 데이터 흐름)가 맥락 문서에 빠지지 않았는가
- 동작이 틀리는 결함이 있는가

넷 가운데 하나에 걸리는 것만 문제로 적는다.

## 4. 하네스의 문제점과 배운 것을 찾는다

- **하네스의 문제점**: 검증하며 본 것(완료 조건의 확인이 조건을 다 보지 못했다, 계획이 맥락 문서 고치기를 빠뜨렸다, 확인 명령이 돌지 않았다)에서 모은다. 다른 프로젝트에서도 그대로 읽히게 어느 스킬의 어느 규칙인지, 또는 계획의 어느 곳인지를 적는다. 이번 검증에서 직접 읽거나 돌려서 본 것만 적는다. 다른 스킬의 본문은 열지 않고 이름으로만 가리킨다. 읽지 않은 파일과 이 스킬 밖의 하네스 동작(예: 실행 스킬이 검증 뒤에 하는 일)은 짐작해 적지 않는다.
- **배운 것**: 맥락 문서에 없고 다음 작업이 알아야 할 것만 적는다.

## 5. 검증 절을 적는다

작업 폴더의 `verify.md` 끝에 아래 양식대로 더한다. 파일이 없으면 첫 줄을 `# 검증`으로 만들고 그 아래에 더한다. 이미 검증 절이 있으면 지우거나 고치지 않고 그 아래에 다음 번호로 더한다.

**판정**: 실패한 확인이 없고 문제 목록이 비어 있으면 "통과"다. 그 밖에는 "문제 있음"이다.

## 6. 커밋한다

`verify.md` 하나만 넣는다. 메시지는 `NNN-slug: 검증`이다(예: `008-csv-export: 검증`). git 레포가 아니면 커밋하지 않는다.

## 7. 세 줄을 돌려준다

아래 세 줄만 돌려준다. 다른 글을 더하지 않는다.

```
판정: 통과 | 문제 있음
문제: N개
기록: docs/tasks/NNN-slug/verify.md
```

사용자가 직접 불렀으면 이 세 줄에 문제 목록을 더해 보여 주고, 고치는 일은 plate의 run 스킬(`plate:run`)을 부르면 이어진다고 적는다. 고치지 않는다.

## 검증 절의 양식

아래 코드 블록 안쪽이 검증 절의 꼴이다. 블록을 여닫는 줄은 옮기지 않는다. `{…}`는 그 자리에 무엇을 적는지를 가리키고, 쓴 파일에는 `{…}`가 남지 않는다.

````markdown
## 검증 {몇 번째}

**확인**
- {완료 조건의 글}
  - {돌린 명령, 또는 본 곳} → {나온 결과}. {통과 | 실패}

**문제**
- {무엇이 어디서 어떻게 틀렸는지} ({파일의 경로}). 기준: {계획 | 범위 | 맥락 문서 | 결함 | 확인 실패}

**배운 것**
- {맥락 문서에 없고 다음 작업이 알아야 할 것}

**하네스의 문제점**
- {어느 스킬의 어느 규칙, 또는 계획의 어느 곳이 어떻게 걸렸는지}

**판정**: {통과 | 문제 있음}
````

## 적는 규칙

- 제목의 번호는 그 파일의 몇 번째 검증 절인지다. 첫 검증 절은 `## 검증 1`이다.
- 없는 항목은 "없음"으로 적는다.
- "확인"에는 완료 조건마다 그 조건에 적힌 확인을 모두 적는다.
- 실패한 확인은 "문제"에도 적는다. 기준은 "확인 실패"다.
- 문제의 기준은 3번의 넷과 확인 실패뿐이다: 목표와 결정대로 되지 않았으면 "계획", 범위 밖을 건드렸으면 "범위", 맥락 문서와 어긋나거나 바뀐 구조가 맥락 문서에 빠졌으면 "맥락 문서", 동작이 틀리면 "결함"이다.
- 스킬의 규칙이 프로젝트의 규칙에 밀린 곳은 "하네스의 문제점"에 "프로젝트의 규칙을 따름: …"으로 적는다.
