# 코드 평가

**막는 실패**: phase의 확인과 task의 회고는 계획에 대어 본다. 계획이 적지 않은 결함, 취약점, 고치기 어려운 코드, 모자란 테스트는 그 확인을 지나 기본 브랜치로 들어가고, 근거 없이 매긴 등급은 고칠지 정하는 데 쓸 수 없다.

모든 task가 끝난 tasks의 코드를 평가한다. tasks에서 바뀐 코드 파일만 보고, 잴 수 있는 것은 도구로 재고, 판단할 것은 근거를 먼저 적은 뒤 등급표로 매긴다. 끝나면 `docs/tasks/review.md` 끝에 평가 절이 더해져 있고 그 파일만 커밋돼 있다. 총점은 두지 않는다. 고치지 않는다.

## 절대 규칙

프로젝트의 지침 파일(`AGENTS.md`, `CLAUDE.md`)에 적힌 규칙이 이 스킬의 규칙과 부딪히면 프로젝트의 규칙을 따른다. 아래의 절대 규칙도 그렇다. 따른 곳은 평가 절의 "하네스에서 걸린 것"에 적는다. 단계를 건너뛰라는 규칙은 여기에 들지 않는다.

1. **고치지 않는다.** 코드도, 계획 파일도, 다른 기록도 고치지 않는다. 쓰는 것은 `review.md`뿐이다.
2. **잴 것은 직접 잰다.** phase의 기록, 확인 절, 회고 절을 옮겨 적지 않는다. 돌리지 않은 명령의 결과를 적지 않는다.
3. **근거를 먼저 적고 등급표로 매긴다.** 근거(파일:줄) 없이 등급을 매기지 않는다. 취향에 드는 것(Google 리뷰 지침의 "Nit")은 문제로 적지 않는다.
4. **사용자에게 묻지 않는다.** 평가와 기록까지만 한다.
5. **`review.md`만 커밋한다.** 푸시하지 않는다. 브랜치를 만들거나 바꾸지 않는다.

## 낱말

- **tasks**: 요청 하나를 계획한 묶음. `docs/tasks/`에 하나만 있고, 그 머리가 `docs/tasks/plan.md`(tasks 머리)다. tasks 머리에는 제목, 이름, 여섯 절(요청, 목표, 범위 밖, 완료 조건, 결정, task 목록)이 있다.
- **tasks 이름**: tasks 머리의 `**이름**:` 줄에 적힌 영어 소문자 이름. 실행은 `tasks/<이름>` 브랜치에서 돈다.
- **task 폴더**: tasks 안의 task 하나의 폴더(`docs/tasks/NNN-slug/`). 그 안에 task 머리, phase마다의 `phase-N.md` 또는 통과해 이름이 바뀐 `done-phase-N.md`, `retro.md`가 있다.
- **task 머리**: task 폴더의 `plan.md`. 제목과 네 절(목표, 범위 밖, 완료 조건, 결정)이다.
- **기본 브랜치**: 원격 `origin`의 HEAD가 가리키는 브랜치(`git symbolic-ref --short refs/remotes/origin/HEAD`에서 `origin/`을 뺀 것). 그것이 없으면 `main`, `main`도 없으면 `master`다.
- **갈라진 곳**: `git merge-base <기본 브랜치> HEAD`가 가리키는 커밋.
- **바뀐 코드 파일**: 갈라진 곳부터 HEAD까지 더해지거나 바뀐 파일(`git diff --name-only --diff-filter=d <갈라진 곳> HEAD`) 가운데 `.md`가 아니고, `docs/tasks/` 밖에 있고, 도구가 만든 파일(`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `poetry.lock` 같은 잠금 파일, 빌드 산출물)이 아닌 것.
- **새 줄**: 바뀐 코드 파일에 갈라진 곳 뒤로 더해진 줄. 수는 `git diff --numstat <갈라진 곳> HEAD -- <바뀐 코드 파일>`의 더한 줄을 합한 것이다.
- **명령 절**: `docs/ARCHITECTURE.md`의 `## 명령` 절. `- 설치: {명령}`, `- 빌드: {명령}`, `- 린트: {명령}`, `- 테스트: {명령}` 네 줄이고, 없는 명령은 "없음"으로 적혀 있다. tasks 끝의 코드 평가는 설치를 돌리지 않는다.
- **맥락 문서**: `AGENTS.md`의 문서 지도에 적힌 문서 가운데 `docs/tasks/` 행을 뺀 것.
- **심각도**: 신뢰성과 보안의 문제 하나가 얼마나 무거운지. 막힘, 높음, 중간, 낮음 넷이고 Sonar의 심각도(Blocker, High, Medium, Low)를 따른다. 뜻은 5번의 심각도 표에 있다.
- **보안 핫스팟**: 그 자체로 취약점은 아니지만 안전한지 사람이 보고 정해야 하는 코드(셸 명령 실행, 밖에서 들어온 경로나 입력의 사용, 암호화, 인증, 권한 같은 것).
- **측정 못함**: 잴 도구가 없거나 돌리지 못해 재지 못한 것. 까닭을 함께 적는다. 실패가 아니다.
- **판단 못함**: 근거가 모자라 등급표의 어느 칸인지 정하지 못한 것. 까닭을 함께 적는다. 실패가 아니다.
- **Sonar way 게이트**: 새 코드에 대는 SonarQube의 기본 통과선. 조건은 넷(새 문제 0개, 새 보안 핫스팟 모두 검토, 새 줄 커버리지 80% 이상, 새 줄 중복 3% 이하)이고, 새 줄이 20줄 미만이면 커버리지와 중복은 보지 않는다.
- **소스 문제**: 이 평가가 찾은, 프로젝트 소스에서 고칠 것. 고칠지 묻는 자리에서 이 목록을 쓴다.
- **프로젝트의 지침 파일**: 저장소의 `AGENTS.md`와 그것을 불러오는 `CLAUDE.md`.

## 0. 대상을 정한다

- `docs/tasks/plan.md`가 없으면 평가하지 않는다. 평가할 tasks가 없다고 알리고 끝난다.
- `phase-N.md`가 남은 task 폴더가 있으면 평가하지 않는다. 그 폴더를 알리고, 남은 phase는 plate의 run 스킬(`plate:run`)로 실행한다고 적고 끝난다.
- 지금 브랜치가 기본 브랜치이면 평가하지 않는다. tasks 브랜치(`tasks/<이름>`)에서 다시 부르라고 알리고 끝난다.
- git 레포가 아니면 task 폴더마다 `done-phase-N.md`의 "한 일"에 적힌 파일 가운데 바뀐 코드 파일의 뜻(`.md`가 아니다, `docs/tasks/` 밖이다, 도구가 만든 파일이 아니다)에 드는 것을 대상으로 하고, 그 파일의 줄을 모두 새 줄로 센다.

## 1. 읽는다

- tasks 머리와 task 폴더마다의 task 머리
- 문서 지도의 맥락 문서. 명령 절도 여기서 읽는다.
- 바뀐 코드 파일마다 갈라진 곳부터의 diff(`git diff <갈라진 곳> HEAD -- <파일>`)와 그 파일 전체
- 바뀐 코드 파일을 시험하는 테스트 파일. 바뀐 코드 파일에 들지 않아도 읽는다.

0번의 git 레포가 아닌 경우 말고는 task 폴더의 기록(`done-phase-N.md`, `retro.md`)과 `docs/tasks/FRICTION.md`, `docs/tasks/RUNLOG.md`를 읽지 않는다. 등급은 기록이 아니라 코드와 도구의 결과로 매긴다.

## 2. 잰다

아래를 차례로 직접 돌리고 돌린 명령과 결과를 적는다. 프로젝트에 설정됐거나 이 환경에 설치된 도구만 쓰고 새로 설치하지 않는다. 도구가 없거나 돌지 않으면 "측정 못함"이다. 재면서 만든 파일(커버리지 데이터 같은 것)은 끝나기 전에 지운다.

1. **명령 절**: 빌드, 린트, 테스트를 이 순서로 돌린다. "없음"으로 적힌 명령, 명령 절이 없거나 줄이 빠진 명령은 돌리지 않고 결과를 "없음"으로 적는다. "없음"은 실패가 아니다.
2. **커버리지**: 커버리지 도구로 테스트를 돌려 새 줄 가운데 테스트가 지나간 줄의 비율을 잰다. 도구가 파일 단위의 결과만 내면 바뀐 코드 파일의 커버리지를 적고 "파일 단위"라고 밝힌다.
3. **중복**: 중복 검사 도구로 새 줄 가운데 중복된 줄의 비율을 잰다.
4. **정적 분석**: 린트 밖의 정적 분석(타입 검사, 복잡도 검사 같은 것)을 돌린다. 바뀐 코드 파일에 걸린 결과만 문제로 옮긴다.
5. **보안 검사**: 의존성 취약점 검사와 보안 규칙 검사를 돌린다. 바뀐 코드 파일에 걸린 결과만 문제로 옮긴다.

## 3. 완료 조건의 확인을 모두 돌린다

tasks 머리의 완료 조건에 적힌 확인을 하나도 빼지 않고 직접 돌린다. 명령이 아니라 "무엇을 어디서 본다"로 적힌 확인은 그곳을 직접 읽고 본 것을 적는다. 돌리지 못한 확인(권한에 막힌 명령, 없는 도구)은 "측정 못함"으로 적고 까닭을 적는다.

## 4. 판단한다

바뀐 코드 파일의 새 줄을 모두 읽고, 그 파일 전체와 맥락 문서에 대어 Google 리뷰 지침의 항목으로 본다. 항목은 범주마다 아래와 같다.

| 범주 | Google 리뷰 지침의 항목 | 보는 것 |
|---|---|---|
| 신뢰성 | 기능 | 동작이 틀리는 곳. 엣지케이스, 동시성, 오류 처리를 함께 본다 |
| 보안 | 없음 (Sonar의 보안 범주를 따른다) | 취약점(주입, 비밀 노출, 권한 건너뛰기 같은 것)과 보안 핫스팟 |
| 유지보수성 | 설계, 복잡도, 이름, 주석, 스타일, 일관성, 문서 | 고치기 어렵게 하는 곳. 설계는 맥락 문서의 구조와 규칙에, 스타일과 일관성은 린트 설정, 맥락 문서의 규칙, 주변 코드에 대어 본다 |
| 테스트 적절성 | 테스트 | 바뀐 동작마다 테스트가 있는가, 코드가 깨지면 그 테스트가 실패하는가, 테스트가 단순한가 |

- 찾은 문제마다 파일:줄, 무엇, 항목을 근거로 적는다. 신뢰성과 보안의 문제에는 심각도를, 유지보수성의 문제에는 고치는 데 드는 시간을 분으로 어림해 붙인다. 2번의 도구가 낸 문제도 같이 적는다.
- 명령 절의 실패도 문제다. 빌드 실패는 신뢰성의 막힘이고, 실패한 테스트는 테스트마다 신뢰성의 문제이며 심각도는 그 테스트가 보는 동작으로 정한다. 린트 위반은 유지보수성의 문제다.
- 보안 핫스팟마다 파일:줄과 판단(안전, 취약점, 판단 못함)을 적는다. 취약점이면 보안의 문제로도 적는다.
- 문제가 없는 범주는 무엇을 읽거나 돌려 문제가 없다고 봤는지를 근거로 적는다.
- 문제로 적지 않는 것: 취향, 바뀐 코드 파일 밖의 코드, tasks 머리와 task 머리의 결정이 정한 것, 그 결정이 바꾸기로 한 맥락 문서의 줄과 어긋나는 것.

## 5. 등급을 매긴다

범주마다 근거를 모두 적은 뒤에 아래 등급표에서 그 근거가 드는 칸을 찾아 매긴다. 어느 칸에도 들지 못하면 "판단 못함"이다. 바뀐 코드 파일이 없으면 기능 적합성 말고 네 범주는 "판단 못함"이고 근거는 "바뀐 코드 파일 없음"이다.

**심각도 표**

| 심각도 | 신뢰성 | 보안 |
|---|---|---|
| 막힘 | 주된 기능이 동작하지 않거나 데이터를 잃거나 망가뜨린다 | 바로 악용해 시스템이나 데이터를 내준다 |
| 높음 | 흔한 입력이나 경로에서 틀린 결과를 낸다 | 조건이 갖춰지면 악용해 권한을 건너뛰거나 데이터를 읽는다 |
| 중간 | 드문 입력이나 경로(엣지케이스, 동시성)에서 틀린 결과를 낸다 | 악용이 어렵거나 피해가 작다 |
| 낮음 | 지금 드러나지 않지만 틀린 결과로 이어질 수 있다(오류를 삼킨다 같은 것) | 바로 악용할 길은 없지만 방어가 모자라다 |

**등급표**

| 등급 | 신뢰성 | 보안 | 유지보수성 | 테스트 적절성 | 기능 적합성 |
|---|---|---|---|---|---|
| A | 문제 0개 | 문제 0개 | 부채 비율 5% 이하 | 새 줄 커버리지 90% 이상이고, 바뀐 동작마다 깨지면 실패할 테스트가 있다 | 완료 조건의 확인이 모두 통과한다 |
| B | 가장 무거운 문제가 낮음 | 가장 무거운 문제가 낮음 | 10% 미만 | 75% 이상이고, 테스트가 빠진 동작은 엣지케이스뿐이다 | 실패한 확인이 있지만 결과물의 동작은 맞다(확인 명령이 틀렸다, 기록이나 문서만 어긋난다) |
| C | 가장 무거운 문제가 중간 | 가장 무거운 문제가 중간 | 20% 미만 | 60% 이상이고, 주된 동작 가운데 테스트가 없는 것이 있다 | 완료 조건 하나 이상이 일부만 이뤄졌다 |
| D | 가장 무거운 문제가 높음 | 가장 무거운 문제가 높음 | 50% 미만 | 60% 미만이거나, 주된 동작의 절반 넘게 테스트가 없다 | 완료 조건 하나 이상이 이뤄지지 않았다 |
| E | 가장 무거운 문제가 막힘 | 가장 무거운 문제가 막힘 | 50% 이상 | 바뀐 동작에 테스트가 하나도 없다 | 목표의 주된 기능이 동작하지 않는다 |

- 유지보수성의 부채 비율은 부채 ÷ (새 줄 수 × 30분)이다. 부채는 유지보수성 문제마다 어림한 분의 합이다.
- 테스트 적절성은 커버리지와 판단이 다른 칸을 가리키면 낮은 쪽으로 매긴다. 커버리지가 측정 못함이면 판단만으로 매기고 그렇다고 적는다.
- 기능 적합성은 돌린 확인으로 매긴다. 측정 못함인 확인은 근거에 그렇다고 적고, 하나도 돌리지 못했으면 "판단 못함"이다.

## 6. 게이트를 본다

Sonar way 게이트의 조건마다 통과 여부를 정한다.

- **새 문제 0개**: 신뢰성, 보안, 유지보수성의 문제가 0개이면 통과다.
- **새 보안 핫스팟 모두 검토**: 판단이 "판단 못함"인 핫스팟이 없으면 통과다. 핫스팟이 없어도 통과다.
- **새 줄 커버리지 80% 이상**: 새 줄이 20줄 미만이면 "보지 않음"이다. 2번의 커버리지가 측정 못함이면 "측정 못함"이다.
- **새 줄 중복 3% 이하**: 새 줄이 20줄 미만이면 "보지 않음"이다. 2번의 중복이 측정 못함이면 "측정 못함"이다.

실패한 조건이 없으면 게이트는 통과다. "측정 못함"과 "보지 않음"은 실패가 아니다.

## 7. 평가 절을 적는다

`docs/tasks/review.md` 끝에 아래 양식대로 더한다. 파일이 없으면 첫 줄을 `# 코드 평가`로 만들고 그 아래에 더한다. 이미 평가 절이 있으면 지우거나 고치지 않고 그 아래에 다음 번호로 더한다.

## 8. 커밋한다

게이트가 실패여도 커밋한다. `review.md` 하나만 넣는다. 이미 스테이징돼 있던 다른 변경이 있어도 커밋에는 이 파일만 넣는다. 메시지는 `<tasks 이름>: 코드 평가`다(예: `project-setup: 코드 평가`). git 레포가 아니면 커밋하지 않는다.

## 9. 네 줄을 돌려준다

아래 네 줄만 돌려준다. 다른 글을 더하지 않는다.

```
등급: 신뢰성 {A~E | 판단 못함}, 보안 {A~E | 판단 못함}, 유지보수성 {A~E | 판단 못함}, 테스트 적절성 {A~E | 판단 못함}, 기능 적합성 {A~E | 판단 못함}
게이트: 통과 | 실패
문제: N개
기록: docs/tasks/review.md
```

`문제`는 소스 문제의 수다. 사용자가 직접 불렀으면 이 네 줄에 소스 문제 목록을 더해 보여 주고, 고치는 일은 plate의 run 스킬(`plate:run`)을 부르면 이어진다고 적는다. 고치지 않는다.

## 기록의 양식

아래 코드 블록 안쪽이 `review.md`에 더하는 평가 절의 꼴이다. 블록을 여닫는 줄은 옮기지 않는다. `{…}`는 그 자리에 무엇을 적는지를 가리키고, 쓴 파일에는 `{…}`가 남지 않는다.

````markdown
## 평가 {몇 번째}

**대상**
- 범위: `{갈라진 곳의 짧은 해시}`({기본 브랜치}에서 갈라진 곳)부터 `{HEAD의 짧은 해시}`까지
- 바뀐 코드 파일 {수}개, 새 줄 {수}줄
  - `{파일의 경로}` +{더한 줄 수}

**잰 것**
- 빌드: `{돌린 명령}` → {나온 결과}. {통과 | 실패}
- 린트: `{돌린 명령}` → {나온 결과}. {통과 | 실패}
- 테스트: `{돌린 명령}` → {나온 결과}. {통과 | 실패}
- 커버리지: `{돌린 명령}` → 새 줄 {수}줄 가운데 {수}줄, {비율}%
- 중복: `{돌린 명령}` → 새 줄 {수}줄 가운데 {수}줄, {비율}%
- 정적 분석: `{돌린 명령}` → {바뀐 코드 파일에 걸린 결과}
- 보안 검사: `{돌린 명령}` → {바뀐 코드 파일에 걸린 결과}

**완료 조건**
- {tasks 머리의 완료 조건의 글}
  - {돌린 명령, 또는 본 곳} → {나온 결과}. {통과 | 실패 | 측정 못함}

**범주**
- 신뢰성
  - 근거: `{파일:줄}` {무엇} ({Google 리뷰 지침의 항목}, {심각도})
  - 등급: {A~E} — {등급표의 어느 칸에 들었는지}
- 보안
  - 핫스팟: `{파일:줄}` {무엇} → {안전 | 취약점 | 판단 못함}
  - 근거: `{파일:줄}` {무엇} ({심각도})
  - 등급: {A~E} — {등급표의 어느 칸에 들었는지}
- 유지보수성
  - 근거: `{파일:줄}` {무엇} ({Google 리뷰 지침의 항목}, {고치는 데 드는 분}분)
  - 부채 비율: {부채}분 ÷ ({새 줄 수}줄 × 30분) = {비율}%
  - 등급: {A~E} — {등급표의 어느 칸에 들었는지}
- 테스트 적절성
  - 근거: `{파일:줄}` {무엇}
  - 등급: {A~E} — {등급표의 어느 칸에 들었는지}
- 기능 적합성
  - 근거: 완료 조건 {번호} {통과 | 실패 | 측정 못함}: {무엇}
  - 등급: {A~E} — {등급표의 어느 칸에 들었는지}

**Sonar way 게이트**
- 새 문제 0개: {신뢰성, 보안, 유지보수성의 문제 수}개. {통과 | 실패}
- 새 보안 핫스팟 모두 검토: {판단한 수}/{핫스팟 수}. {통과 | 실패}
- 새 줄 커버리지 80% 이상: {비율}%. {통과 | 실패 | 측정 못함 | 보지 않음}
- 새 줄 중복 3% 이하: {비율}%. {통과 | 실패 | 측정 못함 | 보지 않음}
- 게이트: {통과 | 실패}

**소스 문제**
1. {무엇이 어떻게 틀렸는지} (`{파일:줄}`). 범주: {신뢰성 | 보안 | 유지보수성 | 테스트 적절성 | 기능 적합성}

**하네스에서 걸린 것**
- {어느 스킬의 어느 규칙, 또는 tasks 머리의 어느 곳 때문에 무엇이 걸렸는지}
````

## 적는 규칙

- 제목의 번호는 그 파일의 몇 번째 평가 절인지다. 첫 평가 절은 `## 평가 1`이다.
- 항목의 순서를 바꾸지 않는다. 적을 것이 없는 항목은 "없음"으로 적는다.
- "잰 것"에서 "없음"인 명령은 `- 빌드: 없음`처럼, 재지 못한 것은 `- 커버리지: 측정 못함 — {까닭}`처럼 적는다.
- 범주마다 근거를 등급보다 먼저 적는다. 근거 줄은 찾은 것마다 하나씩이다.
- 정하지 못한 등급은 `- 등급: 판단 못함 — {까닭}`처럼 적는다.
- 총점, 평균, 범주를 합친 등급을 적지 않는다.
- "소스 문제"에는 다섯 범주의 근거에 적은 문제를 하나에 한 줄씩 모두 옮기고 번호를 붙인다. 실패한 완료 조건의 확인도 들고, 그 줄의 파일:줄은 그 확인이 보는 파일이다. 고칠지 묻는 자리에서 이 번호로 가리킨다.
- 하네스(plate의 스킬, 훅, 계획)의 문제는 "소스 문제"에 넣지 않고 "하네스에서 걸린 것"에 적는다. 명령 절이 없거나 줄이 빠졌다, 완료 조건의 확인이 돌지 않았다 같은 것이다.
- 스킬의 규칙이 프로젝트의 규칙에 밀린 곳은 "하네스에서 걸린 것"에 "프로젝트의 규칙을 따름: …"으로 적는다.
