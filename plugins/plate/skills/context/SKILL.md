# 맥락 채우기

**막는 실패**: 맥락 문서를 추측으로 채우면 틀린 내용이 다음 작업의 근거가 되고, 비워 두면 세션마다 프로젝트를 처음부터 다시 파악한다.

셋업이 만든 하네스 문서의 남은 칸을 채운다. 저장소에서 읽을 수 있는 것은 읽어서 적고, 읽어서 알 수 없는 것은 사용자에게 묻는다. 끝나면 대상 문서에 양식의 `{…}` 안내 글이 없고, 사용자가 미룬 칸만 `{확인 필요}`로 남는다. 이미 적힌 내용은 고치지 않는다.

## 절대 규칙

1. **확인이나 답을 받지 않은 해석과 의도를 문서에 적지 않는다.** 그럴듯해도, 저장소에 근거가 있어도 예외가 없다.
2. **승인받지 않은 초안을 파일에 쓰지 않는다.**
3. **남은 칸이 아닌 곳은 고치지 않는다.** 대상이 아닌 문서는 읽기만 하고 건드리지 않는다.
4. **커밋하지 않는다.** 스테이징도 하지 않는다.

## 낱말

- **남은 칸**: 양식의 `{…}` 안내 글, 또는 `{확인 필요}`. `docs/DESIGN.md`의 토큰 참조(`{colors.primary}`처럼 중괄호 안이 영문, 숫자, 점, 하이픈뿐인 것)는 남은 칸이 아니다.
- **대상 문서**: `docs/PRD.md`, `docs/ARCHITECTURE.md`, `docs/ADR.md`, `docs/DESIGN.md` 가운데 문서 지도에 그 위치로 적혀 있고 남은 칸이 있는 문서. 남은 칸이 없는 문서, 지도에 다른 경로로 적힌 문서, 폴더로 된 문서는 대상이 아니다.
- **적힌 사실**: 파일에 그대로 적혀 있는 것. 의존성 이름과 버전, 폴더 이름, 설정 값, README 문장, 토큰 이름과 값.
- **해석**: 파일을 읽고 정리한 것. 폴더의 역할, 패턴과 규칙, 데이터 흐름, 코드에서 드러나는 결정.
- **의도**: 어디에도 적혀 있지 않은 것. 목표, 사용자, 범위 밖, 결정의 이유와 트레이드오프, 화면의 분위기.

## 0. 셋업이 됐는지 본다

`AGENTS.md`에 문서 지도 구간(`<!-- plate:docs-map:start -->`으로 시작하는 구간)이 있으면 1번으로 간다. 없으면 셋업을 먼저 할지 묻는다.

- 승인하면 plate의 setup 스킬(`plate:setup`)을 불러 그 절차를 끝까지 따르고 1번으로 돌아온다. 이때 setup의 끝 물음(이어서 채울지)은 하지 않는다.
- 거절하면 아무것도 쓰지 않고 끝난다.

## 1. 대상 문서를 정한다

문서 지도에서 네 문서의 위치를 읽고, 표준 위치에 있는 문서마다 남은 칸을 센다. 대상 문서가 없으면 채울 것이 없다고 보고하고 끝난다.

## 2. 스캔한다

아래 목록만 읽는다. 목록 밖의 소스 파일은 해석을 확인하는 데 필요한 것만 연다. 읽을 것이 없는 빈 프로젝트는 이 단계를 건너뛴다.

- `README`
- 빌드 매니페스트(`package.json`, `pyproject.toml`, `build.gradle.kts` 등)
- 최상위와 한 단계 아래의 폴더 목록
- 진입점 파일
- 설정 파일
- `AGENTS.md`
- 최근 커밋 제목 30개
- 문서 지도에 `docs/DESIGN.md` 행이 있으면 토큰 파일(CSS 변수가 적힌 파일, `@theme` 블록, tailwind 설정)

## 3. 문서를 하나씩 채운다

순서는 PRD → ARCHITECTURE → ADR → DESIGN이고 대상 문서만 한다. 칸마다 얻는 방법은 "칸의 분류" 절에 있다. 문서 하나마다 아래 순서로 한다.

1. **적힌 사실**로 채울 칸은 출처 경로와 함께 초안에 넣는다.
2. **해석**으로 채울 칸은 절 단위로 묶어 보여 주고 맞는지 묻는다. 고칠 곳을 말하면 고쳐서 다시 보여 준다. 확인받은 것만 초안에 남긴다.
3. **의도**를 묻는 칸은 질문을 하나씩 낸다. 한 번에 질문 하나만 내고, 답을 받은 뒤에 다음 질문을 낸다. 저장소에 근거가 있으면 추천안을 붙이고 근거 경로를 적는다. 근거가 없으면 추천안 없이 묻는다. 고를 수 있는 답은 선택지로 낸다.
4. 문서의 초안 전체를 보여 주고 승인받는다. 고칠 곳을 말하면 고쳐서 다시 보여 준다. **승인받은 뒤에 파일에 쓴다.**

적힌 사실이나 해석으로 얻는 칸인데 저장소에 읽을 것이 없으면 질문으로 얻는다.

## 4. 보고한다

- 쓴 문서
- 남은 칸과 그 위치(파일과 절)
- 대상이 아니었던 문서와 그 까닭

## 답을 적는 규칙

- 사용자의 답은 뜻을 바꾸지 않는 범위에서 문서 문체(평서문)로 다듬는다. 답에 없는 내용은 더하지 않는다.
- 사용자가 미룬 칸(모른다, 아직 안 정했다)은 `{확인 필요}`로 적는다. 둘을 구분하지 않는다.
- 사용자가 없다고 답한 칸은 "없음"으로 적는다. ADR에 적을 결정이 없으면 철학만 남기고 항목 자리에 "아직 적은 결정이 없다"를 적는다.
- 목록 칸(핵심 기능, 범위 밖, 기술 스택, ADR 항목)의 개수는 답에 맞춘다. 양식의 개수는 예시다. 절 제목과 순서는 바꾸지 않는다.
- 스캔으로 적은 사실에만 출처 경로를 괄호로 붙인다(예: `- Kotlin 2.0, JVM 21 (build.gradle.kts)`). `docs/DESIGN.md`의 앞머리는 YAML이라 출처를 주석으로 적는다.
- ADR 번호는 있는 번호 뒤에 잇는다.
- 요청에 이미 답이 적혀 있는 물음은 다시 묻지 않는다.
- 다시 불렀을 때는 남은 칸만 묻는다. 적힌 내용은 묻지도 고치지도 않는다.
- 도중에 사용자가 그만하자고 하면, 그 문서는 답한 칸까지 초안을 보여 주고 승인받아 쓴다. 아직 묻지 않은 칸은 양식의 `{…}` 그대로 둔다. 뒤 문서로 가지 않고 보고한다.

## 칸의 분류

| 문서 | 칸 | 얻는 방법 |
|---|---|---|
| PRD | 프로젝트명 | 질문. `README` 제목이나 빌드 매니페스트의 이름이 있으면 추천안 |
| PRD | 목표, 사용자, 핵심 기능, 범위 밖 | 질문. `README`에 적혀 있으면 추천안 |
| ARCHITECTURE | 기술 스택 | 적힌 사실(빌드 매니페스트) |
| ARCHITECTURE | 디렉터리 구조 | 폴더 이름은 적힌 사실, 역할은 해석 |
| ARCHITECTURE | 패턴과 규칙 | 해석. 규칙의 이유는 질문 |
| ARCHITECTURE | 데이터 흐름 | 해석 |
| ADR | 철학 | 질문 |
| ADR | 항목 | 아래 "ADR 항목"을 따른다 |
| ADR | 항목의 이유, 트레이드오프 | 질문. `README`, 커밋 제목, 주석에 적혀 있으면 추천안 |
| DESIGN | 앞머리의 `name`, `description` | `name`은 PRD의 프로젝트명, `description`은 질문 |
| DESIGN | 앞머리의 `colors`, `typography`, `rounded`, `spacing` | 토큰 파일에 있으면 적힌 사실. 아래 "DESIGN의 토큰"을 따른다 |
| DESIGN | 앞머리의 `components` | 양식의 키대로 질문. 답이 옮긴 토큰을 가리키면 토큰 참조(`{colors.primary}`)로 적는다 |
| DESIGN | 본문의 Colors, Typography | 질문. 아래 "DESIGN의 토큰"의 끝을 따른다 |
| DESIGN | 본문의 나머지 절 | 질문 |

### ADR 항목

1. 스캔에서 아래 다섯 범주에 드는 결정의 후보를 뽑아 출처 경로와 함께 한 번에 보여 주고, 남길 것을 고르게 한다. 이 다섯 범주 밖에서는 후보를 내지 않는다. 후보가 없으면 이 물음은 건너뛴다.
   - 언어와 런타임
   - 프레임워크
   - 저장소(DB)
   - 외부 서비스
   - 빌드·배포 방식
2. 이 밖에 적어 둘 결정이 있는지 한 번 묻는다.
3. 남기기로 한 항목마다 이유와 트레이드오프를 묻는다.

### DESIGN의 토큰

토큰 파일은 CSS 변수(`--이름: 값`)가 적힌 파일이다. 토큰 파일에 변수가 있으면 아래 규칙으로 앞머리에 옮기고, 양식의 예시 키(`primary`, `headline-lg`, `sm` 등)는 쓰지 않는다. 토큰 파일이 없거나 변수가 하나도 없으면 양식의 키대로 하나씩 묻는다.

**옮길 변수**

- `:root` 블록과 `@theme` 블록(`@theme inline` 포함)에 적힌 변수만 옮긴다. 이 값이 기본 값이다.
- 다른 선택자(`.dark` 등)나 미디어 쿼리 안에서 다시 정한 값은 옮기지 않는다.

**이름과 범주**: 변수마다 아래 순서로 맞춰 본다.

1. 네 범주 밖의 접두어(`--shadow-`, `--inset-shadow-`, `--drop-shadow-`, `--text-shadow-`, `--blur-`, `--perspective-`, `--aspect-`, `--ease-`, `--animate-`, `--breakpoint-`, `--container-`)로 시작하면 옮기지 않는다.
2. 아래 표의 꼴에 맞으면 그 자리로 옮긴다. `X`가 토큰 이름이다. 긴 꼴부터 맞춰 본다.

   | 변수 이름 | 옮기는 곳 |
   |---|---|
   | `--color-X` | `colors.X` |
   | `--radius-X` | `rounded.X` |
   | `--spacing-X` | `spacing.X` |
   | `--font-X` | `typography.X.fontFamily` |
   | `--font-weight-X` | `typography.X.fontWeight` |
   | `--text-X` | `typography.X.fontSize` |
   | `--text-X--line-height` | `typography.X.lineHeight` |
   | `--text-X--letter-spacing` | `typography.X.letterSpacing` |
   | `--text-X--font-weight` | `typography.X.fontWeight` |
   | `--leading-X` | `typography.X.lineHeight` |
   | `--tracking-X` | `typography.X.letterSpacing` |

3. 어느 쪽도 아니면 앞의 `--`만 뗀 것이 토큰 이름이다. 값이 CSS 색(`#hex`, `rgb()`·`hsl()`·`oklch()` 같은 색 함수, 색 이름)이면 `colors`에 넣는다. 색이 아니면 그런 변수를 모아 한 번에 보여 주고 변수마다 범주(`rounded`, `spacing`, 옮기지 않음)를 묻는다.

- `typography`는 변수 하나를 속성 하나로 옮긴다. `X`가 같은 변수는 한 토큰에 모은다. 양식의 레벨(`headline-lg` 등)은 만들지 않는다.
- 두 변수가 같은 토큰이 되면 하나만 적는다(`--color-primary: var(--primary)`와 `--primary`는 둘 다 `colors.primary`다). 값이 서로 다르면 표의 꼴에 맞는 변수의 값을 적는다.
- 범주 안의 순서는 토큰 파일에 처음 나온 순서다.
- tailwind 설정 파일의 `theme`에 적힌 값도 같은 자리로 옮긴다: `colors.X` → `colors.X`, `borderRadius.X` → `rounded.X`, `spacing.X` → `spacing.X`, `fontFamily.X`·`fontSize.X`·`fontWeight.X`·`lineHeight.X`·`letterSpacing.X` → `typography.X`의 같은 이름 속성.

**값**

- 적힌 글자 그대로 옮긴다. 단위를 바꾸거나 계산하지 않는다. `calc(…)` 같은 식도 식 그대로 옮긴다.
- 값 전체가 `var(--이름)` 하나이면 그 변수의 기본 값을 따라가서 끝에 적힌 값을 옮긴다.
- 따라간 끝에 값이 없으면(토큰 파일에 그 변수가 없거나 자기 자신을 가리킨다) 그 값을 질문한다. 스캔한 파일에 근거가 있으면 추천안과 경로를 붙인다. 끝에 닿은 변수가 같으면 한 번만 묻는다.
- 여러 줄에 걸친 값은 줄바꿈과 그 앞뒤의 공백을 빈칸 하나로 바꿔 한 줄로 적는다.
- 값은 큰따옴표로 감싼다. 값 안에 큰따옴표가 있으면 작은따옴표로 감싼다.

**변수가 없는 범주**: 네 범주 가운데 옮긴 토큰이 하나도 없는 범주는 범주마다 한 번 묻는다(예: "코드에 `spacing` 토큰이 없다. 정해 둔 값이 있는가").

- 값을 답하면 답한 이름과 값으로 적는다.
- 없다고 답하면 그 범주의 키를 앞머리에서 빼고, `description` 다음 줄에 `omitted` 목록을 두어 범주 이름을 적는다.
- 미루면 양식의 칸을 모두 `{확인 필요}`로 적는다.

**출처**: 토큰 파일에서 옮긴 범주는 범주 키의 바로 윗줄에 `# 출처: <토큰 파일 경로>` 주석을 둔다.

**옮기지 않은 것**: 다른 선택자 안의 값, 네 범주 밖의 변수, 옮기지 않기로 한 변수는 보고에 "옮기지 않은 것"으로 적는다. 본문의 절을 물을 때 추천안의 근거로 쓸 수 있다.

**본문의 Colors와 Typography**: 토큰을 토큰 파일에서 옮겼으면 절마다 질문을 하나만 낸다. 옮긴 토큰 이름을 보여 주고 어떤 것을 어디에 쓰는지 묻는다. 답에 나온 토큰만, 토큰 이름을 항목 이름으로 써서 적는다(예: `- **primary**: 주요 버튼에 쓴다.`). 토큰을 질문으로 채웠으면 양식의 항목대로 하나씩 묻는다.

앞머리의 키 이름과 `omitted`, 토큰 참조는 google-labs-code/design.md의 규격(alpha)을 따른다.
