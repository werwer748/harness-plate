## Assessment

The direction is sound, but four gaps should be resolved before treating the plan as implementation-ready. The strongest choices are keeping the main agent responsible, loading context only when needed, preferring built-in features, and adding machinery after observed failures.

Scope: `HANDOFF.md`, all six axis documents, `docs/rules.md`, `docs/decisions.md`, and both reference/research documents were reviewed. Relevant official Claude Code documentation was checked, and the Bash pipeline issue below was reproduced locally. This was a design review, not an end-to-end validation of the harness or a recomputation of historical session metrics.

## 1. Unattended execution has an unresolved completion contract

**Plan references:** [Execution](docs/axes/4-execution.md), decision 6; [Verification](docs/axes/5-verification.md), decisions 1–2; [Rules](docs/rules.md), unattended-execution expansion conditions.

Execution permits stepping away with `/goal` and auto mode, while verification requires the harness to determine completion and calls for a fresh-context reviewer for unattended work. The plan does not yet specify how that path satisfies those requirements.

The `/goal` evaluator judges conversation evidence; it cannot independently inspect files or run checks. This limitation is already acknowledged in the research appendix. The gap is translating it into an operational completion contract.

**Recommendation:** Before enabling this path, define which checks must pass, who runs them, what evidence is required, how the reviewer is invoked, and how incomplete work is reported. This does not by itself require a custom executor.

Source: [Official `/goal` documentation — effective conditions](https://code.claude.com/docs/en/goal#write-an-effective-condition).

## 2. The listed retry limits are not equivalent

**Plan references:** [Rules](docs/rules.md), repetition row; [Execution](docs/axes/4-execution.md), decision 3.

The plan groups Stop-hook caps, goal conditions, and spending limits together as platform limits. These mechanisms have different meanings:

- The eight-consecutive-block Stop-hook cap overrides the hook after repeated blocking without progress. It does not establish successful completion.
- A turn or time limit written into a goal condition is evaluated by a model from the conversation.
- A spending limit bounds resource use; exhausting it does not imply the task passed verification.

**Recommendation:** Keep one owner for retries, but separately define resource limits and terminal outcomes such as `passed`, `blocked`, and `budget_exhausted`. Identify which limits are actually enforced in the chosen execution mode. Ending a run must not automatically count as successful completion.

Sources: [Stop-hook cap behavior](https://code.claude.com/docs/en/hooks-guide#stop-hook-hits-the-block-cap), [goal-condition limits](https://code.claude.com/docs/en/goal#write-an-effective-condition).

## 3. `bash -e` can incorrectly pass a failed acceptance check

**Plan reference:** [Planning](docs/axes/3-planning.md), decision 2, which standardizes unattended acceptance checks on `bash -e`.

A failing command piped through a successful command can appear successful. This matters for test output piped through `tee`, for example.

Locally reproduced during the review:

```sh
bash -e -c 'false | cat'
# Exit status: 0

bash -e -o pipefail -c 'false | cat'
# Exit status: 1
```

**Recommendation:** Use `bash -e -o pipefail` for acceptance scripts and make checks return explicit failure statuses. `pipefail` addresses this pipeline case; it is not a substitute for correctly written acceptance checks.

## 4. The measurement loop needs a small task-level record

**Plan references:** [Rules](docs/rules.md), progression steps 2–4; [Improvement](docs/axes/6-improvement.md), decision 3; [Research](docs/research-2026-10-04.md), session aggregation and limitations.

Selecting sessions with high cache reads or subagent usage identifies investigation targets, but does not establish inefficiency. The research already acknowledges that these are token totals rather than monetary costs, and session measurements rather than task measurements.

The plan calls for manually recording interventions and later defects per task, but does not specify where those records live or how they connect to session data. Splitting a task into several sessions could make individual sessions look cheaper without reducing total work.

**Recommendation:** Define a lightweight record containing task identity, linked session IDs, outcome, elapsed time, interventions, discovered defects, and enabled mechanisms. Use it to distinguish expensive useful work from avoidable repetition. Keep token categories separate and avoid claiming monetary savings from raw totals alone. A simple row per task is enough to start; a new analytics system is unnecessary.

## Suggested v0.1 completion criterion

Keep the existing scope of basic workflow plus records. Add a concrete completion criterion:

> The basic workflow has been used on real work, its results are traceable, and those records support a decision to retain or change a mechanism.

No additional orchestration layer is justified by this review alone. Findings 1–3 concern the unattended path and should be resolved before relying on it; finding 4 improves the baseline measurement work already planned.
